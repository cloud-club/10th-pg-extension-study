# 왜 PostgreSQL이 나왔는가?

## 결론부터

PostgreSQL은 MySQL을 대체하려고 시작된 제품이 아니다.

1970년대 UC Berkeley의 INGRES 연구팀은 관계형 모델과 선언적 질의를 실제로 사용할 수 있는 DBMS로 구현했다. 이후 CAD, 지리 정보, 그래픽처럼 기존의 정수·문자열 중심 업무 데이터로는 다루기 어려운 분야가 등장했고, INGRES에 새로운 기능을 계속 덧붙이는 방식도 한계에 도달했다. 연구팀은 관계형 모델을 버리는 대신 **데이터 타입·함수·연산자·인덱스 접근 방식까지 확장할 수 있는 새로운 DBMS**를 설계했고, 이것이 POSTGRES의 출발이다.[1][2]

```text
INGRES
관계형 모델과 선언적 질의를 실제 시스템으로 구현
        ↓
INGRES 후기
분산 DB·추상 데이터 타입 등 새로운 기능을 계속 실험
        ↓
기존 구조에 새 기능을 계속 붙이기 어려워짐
        ↓
POSTGRES
관계형 모델은 유지하면서 DBMS 자체를 확장 가능하게 재설계
        ↓
Postgres95
PostQUEL 대신 SQL 도입
        ↓
PostgreSQL
POSTGRES의 확장 철학과 SQL을 계승
```

## 1. 이름부터 구분하기

이 문서에서는 다음 네 단계를 같은 것으로 취급하지 않는다.

| 이름 | 의미 |
| --- | --- |
| **INGRES** | UC Berkeley가 만든 초기 관계형 DBMS |
| **POSTGRES** | INGRES 이후에 새로 설계한 후속 연구 DBMS |
| **Postgres95** | POSTGRES에 SQL 인터프리터를 추가한 오픈소스 버전 |
| **PostgreSQL** | 1996년부터 사용한 현재 프로젝트 이름 |

`POSTGRES`는 말 그대로 **Post-Ingres**, 즉 “INGRES 이후의 시스템”이라는 의미다.[2][4]

## 2. INGRES는 무엇을 해결했는가?

### 당시의 핵심 문제

관계형 DB 이전의 많은 시스템에서는 애플리케이션이 데이터의 물리적인 연결과 탐색 순서를 알아야 했다.

```text
부서 레코드를 찾는다
→ 연결된 직원 레코드의 주소를 따라간다
→ 직원 데이터를 순서대로 읽는다
→ 조건에 맞는 레코드를 직접 골라낸다
```

이런 방식에서는 파일 구조나 데이터 연결 방식이 바뀌면 애플리케이션도 함께 수정해야 한다.

### INGRES의 답

INGRES는 사용자에게 데이터를 **관계형 테이블**로 보여 주고, QUEL이라는 고수준 비절차적 언어를 제공했다. 사용자는 데이터가 물리적으로 어디에 저장됐는지, 어떤 알고리즘으로 찾을지를 지정하지 않고 원하는 결과를 표현할 수 있었다.[1]

```text
사용자
“어떤 데이터가 필요한가?”를 표현

DBMS
“어떻게 데이터를 찾을 것인가?”를 결정
```

INGRES가 구현하려던 핵심은 다음과 같다.

1. **관계형 모델**: 데이터를 관계, 즉 테이블의 형태로 다룬다.
2. **데이터 독립성**: 논리적인 데이터 표현을 물리적인 저장 구조와 분리한다.
3. **선언적 질의**: 사용자는 탐색 절차가 아니라 원하는 결과를 작성한다.
4. **실용적인 구현**: 관계형 모델을 UNIX와 C 위에서 동작하는 실제 다중 사용자 DBMS로 만든다.[1]

이 철학은 PostgreSQL만의 독특한 철학이 아니다. 오늘날 MySQL과 Oracle Database를 포함한 일반적인 RDBMS도 관계형 모델, 선언적 질의, 데이터 독립성을 공유한다.

## 3. INGRES가 성공했는데 왜 새 시스템이 필요했나?

INGRES가 실패해서 POSTGRES를 만든 것은 아니다. 오히려 INGRES가 관계형 DBMS의 가능성을 보여 준 뒤, 연구팀이 더 넓은 문제를 해결하려 하면서 기존 구조의 한계가 드러났다.

### 3.1 계속 추가된 실험적 기능

Berkeley 연구팀은 1978년 이후 INGRES에 다음과 같은 기능을 실험적으로 추가했다.

- 분산 데이터베이스
- 순서가 있는 관계
- 추상 데이터 타입
- QUEL 자체를 데이터 타입처럼 사용하는 기능
- 새로운 애플리케이션 프로그래밍 인터페이스 구상

그러나 기존 INGRES는 이러한 기능을 처음부터 고려해 설계된 시스템이 아니었다. 새로운 기능을 계속 덧붙이면서 코드가 복잡해졌고, 초기 설계 결정과 충돌하는 아이디어도 생겼다. POSTGRES 설계 논문은 기존 시스템에 큰 기능을 추가하기가 매우 어려워졌기 때문에 새로운 DBMS를 만들기로 했다고 설명한다.[2]

### 3.2 업무 데이터 밖의 새로운 요구

기존 관계형 DBMS는 다음과 같은 전형적인 업무 데이터에 적합했다.

```text
고객 번호
직원 이름
부서 코드
상품 가격
주문 수량
```

그러나 연구팀이 다루려던 새로운 분야의 데이터는 더 복잡했다.[2][4]

- CAD와 반도체 회로 설계
- 지도와 지리 정보
- 선, 원, 사각형, 다각형 같은 공간 객체
- 그래픽 데이터
- 프로그래밍 환경
- 과학 데이터

예를 들어 지도 시스템에서 `polygon`을 저장하고 검색하려고 한다고 생각해 보자.

기존 DBMS가 정수와 문자열만 제대로 이해한다면 애플리케이션이 다음을 모두 직접 처리해야 한다.

```text
polygon을 여러 숫자 컬럼이나 별도 테이블로 분해
→ 객체를 다시 조립
→ 두 polygon이 겹치는지 애플리케이션에서 계산
→ 공간 검색에 적합하지 않은 일반 인덱스 사용
```

연구팀이 원한 것은 다음과 같은 구조였다.

```text
DBMS가 polygon이라는 타입을 이해
+ polygon 전용 함수를 등록
+ 겹침·포함 같은 연산자를 등록
+ 공간 검색에 맞는 인덱스 방식을 연결
```

즉 문제는 단순히 “컬럼 종류가 부족하다”가 아니었다. **새로운 데이터 종류를 추가할 때마다 DBMS 코어를 직접 고쳐야 하는 구조**가 문제였다.

## 4. 핵심 결정: 관계형 모델을 버리지 않는다

복잡한 객체를 다루려면 객체지향 DB처럼 완전히 다른 모델로 갈 수도 있었다.

POSTGRES 연구팀은 그 길을 선택하지 않았다. 기존 관계형 모델과 선언적 질의의 장점은 유지하되, 관계형 DB가 이해할 수 있는 타입과 동작을 사용자가 추가할 수 있게 만들려고 했다. 최초 설계 목표에도 관계형 모델을 가능한 한 적게 변경한다고 명시돼 있다.[2]

```text
버린 것
고정된 타입과 고정된 동작만 제공하는 닫힌 구조

유지한 것
관계형 테이블과 선언적 질의

추가한 것
새 타입·함수·연산자·인덱스 방식의 확장 지점
```

이 결정을 나중에 **객체-관계형(Object-Relational)** 접근이라고 부르게 된다. POSTGRES의 대표적인 주제는 객체지향 프로그래밍의 일부 아이디어를 관계형 데이터 모델과 선언적 질의 안으로 가져오는 것이었다.[4]

## 5. POSTGRES의 여섯 가지 설계 목표

최초의 POSTGRES 설계 논문은 다음 목표를 제시했다.[2]

### 5.1 복잡한 객체 지원

기존의 단순한 숫자와 문자열을 넘어 CAD, 지도, 그래픽에서 사용하는 복잡한 데이터를 자연스럽게 저장하려 했다.

핵심은 모든 데이터를 무조건 여러 개의 평평한 테이블로 분해하는 대신, 애플리케이션에 자연스러운 복합 구조도 DB 안에서 다룰 수 있게 하는 것이었다.

### 5.2 사용자 확장성

POSTGRES의 가장 중요한 목표다.

사용자가 다음 요소를 추가할 수 있게 하려 했다.

- 데이터 타입
- 함수
- 연산자
- 집계 동작
- 인덱스 접근 방식

새로운 도메인이 등장할 때 DBMS 제작자가 코어에 기능을 넣어 줄 때까지 기다리는 것이 아니라, 해당 분야의 개발자가 필요한 타입과 동작을 DB에 등록할 수 있게 하려는 것이다.[2][4]

### 5.3 능동형 데이터베이스

데이터가 변경되면 DB가 규칙에 따라 자동으로 반응하는 기능을 연구했다.

- alert
- trigger
- rule
- forward chaining과 backward chaining

일반적인 DB가 요청받은 명령만 수행하는 수동적인 저장소라면, 능동형 DB는 특정 사건을 감지해 추가 동작을 수행한다.

### 5.4 복구 구조 단순화

장애 복구를 위한 DBMS 코드를 단순화하는 것도 초기 목표였다. 당시 POSTGRES는 데이터를 덮어쓰지 않고 새 버전을 남기는 방식과 기존과 다른 로그 구조를 실험했다.[2][4]

다만 이 초기 실험을 현대 PostgreSQL의 저장·복구 구현과 완전히 같은 것으로 보면 안 된다. 현대 PostgreSQL은 WAL을 사용하며, 초기 연구 아이디어가 모두 그대로 유지된 것은 아니다.

### 5.5 새로운 하드웨어 활용

당시 미래 기술로 여겨졌던 다음 하드웨어를 활용하려 했다.

- 광학 디스크
- 여러 프로세서를 가진 워크스테이션
- DB 처리를 위한 전용 VLSI 하드웨어

이 목표는 POSTGRES가 특정 시점의 업무용 DB만 복제한 것이 아니라 차세대 범용 DBMS를 연구하려 했다는 점을 보여 준다.[2]

### 5.6 관계형 모델 유지

새 기능을 추가하면서도 Codd의 관계형 모델을 가능한 한 그대로 유지하려 했다.

이 목표가 중요하다. POSTGRES의 방향은 “관계형 DB를 버리고 객체 DB를 만들자”가 아니라 다음에 가까웠다.

> 관계형 DB의 단순함과 선언적 질의는 유지하면서, 관계형 DB가 다룰 수 있는 세계를 넓히자.

## 6. INGRES와 POSTGRES의 철학 차이

| 구분 | INGRES | POSTGRES |
| --- | --- | --- |
| 중심 질문 | 관계형 모델을 실제 DBMS로 구현할 수 있는가? | 관계형 DB 자체를 새로운 분야에 맞게 확장할 수 있는가? |
| 핵심 가치 | 관계형 모델, 데이터 독립성, 선언적 질의 | 관계형 모델 유지 + 사용자 확장성 |
| 주요 데이터 | 전형적인 업무 데이터 | 업무 데이터 + CAD·지도·그래픽·과학 데이터 |
| 타입 | 비교적 고정된 기본 타입 | 사용자 정의 타입과 복잡한 객체 |
| 연산 | DBMS가 제공하는 동작 중심 | 사용자 정의 함수와 연산자 |
| 인덱스 | DBMS가 미리 제공한 접근 방식 | 새로운 타입에 맞는 접근 방식 확장 |
| 자동 동작 | 전통적인 DB 기능 | rule·trigger·alert를 적극적으로 연구 |
| 관계 | PostgreSQL과 같은 제품은 아님 | 현재 PostgreSQL의 직접적인 코드·설계 조상 |

요약하면 다음과 같다.

```text
INGRES
“관계형 DB를 실제로 작동하게 만들자”

POSTGRES
“관계형 DB를 고정된 제품이 아니라 확장 가능한 플랫폼으로 만들자”
```

## 7. POSTGRES에서 PostgreSQL까지

### 1986: POSTGRES 구현 시작

Michael Stonebraker 교수가 이끄는 UC Berkeley 연구팀이 구현을 시작했다. 최초 설계 논문은 Michael Stonebraker와 Lawrence A. Rowe가 작성했다.[2][3]

### 1987~1991: 연구 시스템 발전

- 1987년 최초 데모 시스템 가동
- 1989년 Version 1 외부 배포
- 1990년 새로운 rule system을 적용한 Version 2
- 1991년 여러 storage manager와 개선된 query executor를 포함한 Version 3

이후 Berkeley 프로젝트는 연구보다 프로토타입 유지와 외부 사용자 지원에 많은 시간이 들어가기 시작했고 Version 4.2를 끝으로 공식 종료됐다.[3]

### 1994: Postgres95

Andrew Yu와 Jolly Chen이 POSTGRES에 SQL 인터프리터를 추가했다. 기존 질의 언어 PostQUEL을 SQL로 바꾸고, 코드를 정리해 오픈소스로 공개했다.[3]

### 1996: PostgreSQL

`Postgres95`라는 이름이 장기적으로 적절하지 않다고 판단해, POSTGRES 계보와 SQL 지원을 함께 나타내는 `PostgreSQL`로 이름을 변경했다.[3]

```text
POSTGRES
연구 DBMS, PostQUEL 사용
        ↓
Postgres95
SQL 인터프리터 추가
        ↓
PostgreSQL
커뮤니티 기반 오픈소스 RDBMS
```

## 8. 초기 철학이 현재 어디에 남아 있나?

현대 PostgreSQL은 함수, 집계 함수, 데이터 타입, 연산자, 인덱스용 operator class 등을 사용자가 추가할 수 있다. 관련 객체들을 하나의 패키지로 묶어 extension으로 설치하는 구조도 제공한다.[6][7]

```text
초기 POSTGRES의 생각
DB 코어를 수정하지 않고 새로운 타입과 동작을 추가
        ↓
현대 PostgreSQL
사용자 정의 함수·타입·연산자·인덱스 연동
        ↓
extension
관련 SQL 객체와 코드를 설치·관리 가능한 단위로 패키징
```

여기서 주의할 점이 있다.

> `CREATE EXTENSION` 명령이 1986년부터 존재했던 것은 아니다.

초기부터 이어진 것은 **DBMS 코어를 직접 수정하지 않고 새로운 데이터와 동작을 추가할 수 있어야 한다는 설계 철학**이다. `CREATE EXTENSION`은 그 철학을 현대 PostgreSQL에서 설치·버전 관리 가능한 패키지 형태로 다루는 장치다.[6][7]

## 9. MySQL과 출발점 비교

POSTGRES와 MySQL은 처음부터 서로 경쟁하려고 만들어진 제품이 아니다. POSTGRES 구현은 1986년에 시작됐고, MySQL은 그보다 뒤에 자체 ISAM 기반 데이터 처리 루틴에 적합한 SQL 인터페이스를 만들려는 실용적인 필요에서 출발했다.[2][3][5]

| 질문 | POSTGRES | MySQL |
| --- | --- | --- |
| 기존 기반 | Berkeley INGRES 연구 | 자체 저수준 ISAM 데이터 처리 루틴 |
| 직접적인 문제 | 복잡한 데이터와 새로운 분야를 기존 DB 구조로 확장하기 어려움 | mSQL이 필요한 속도와 유연성을 제공하지 못함 |
| 해결 방향 | 관계형 DB 자체에 확장 지점을 설계 | 자체 데이터 루틴을 위한 새 SQL 인터페이스 구현 |
| 대표 구조 | 타입·함수·연산자·접근 방식 확장 | SQL 서버와 선택 가능한 스토리지 엔진 |

이 역사만으로 현대 제품의 성능이나 안정성을 단정하면 안 된다. 두 제품 모두 오랜 기간 크게 발전했다. 역사는 현재의 차이를 이해하는 출발점이지, 현재의 우열을 자동으로 결정하는 근거가 아니다.

## 10. 자주 생기는 오해

### “PostgreSQL은 MySQL의 단점을 고치려고 나왔다”

아니다. POSTGRES가 먼저 시작됐고 해결하려던 문제도 MySQL과 무관했다.[2][3][5]

### “INGRES가 곧 PostgreSQL의 초기 버전이다”

아니다. INGRES는 연구 철학의 선행 프로젝트이고, POSTGRES는 기존 INGRES를 계속 수정하지 않고 새로 설계한 후속 시스템이다. 현재 PostgreSQL의 직접적인 코드 계보는 POSTGRES에서 이어진다.[2][3]

### “POSTGRES는 관계형 모델을 버리고 객체 DB를 만들었다”

아니다. 복잡한 객체와 사용자 확장성을 추가했지만, 관계형 모델은 가능한 한 유지하는 것이 명시적인 목표였다.[2]

### “초기 설계가 현대 PostgreSQL에 그대로 남아 있다”

아니다. 확장 철학과 일부 핵심 아이디어는 이어졌지만, SQL 도입과 저장·복구 구조를 포함해 많은 부분이 교체되고 발전했다.[3][4]

### “연구 프로젝트였으니 실무보다 이론을 우선했다”

아니다. 출발은 연구 프로젝트였지만 CAD, 지도, 과학 데이터 등 당시 실제 응용 분야의 문제를 해결하려 했고, 초기부터 외부 사용자와 실제 응용 사례가 있었다.[2][3]

## 11. 발표할 때 사용할 답변

### 10초 답변

> PostgreSQL은 기존 INGRES에 복잡한 데이터와 새로운 기능을 계속 붙이기 어려워지자, 관계형 모델은 유지하면서 타입·함수·연산자·인덱스 방식을 확장할 수 있도록 새로 설계한 POSTGRES에서 시작됐습니다.

### 1분 답변

> PostgreSQL의 조상인 INGRES는 관계형 모델과 선언적 질의를 실제 DBMS로 구현한 Berkeley 연구 프로젝트였습니다. 이후 CAD와 지도처럼 기존 정수·문자열만으로 다루기 어려운 데이터가 등장했고, INGRES에 분산 DB와 추상 데이터 타입 같은 기능을 계속 붙이면서 기존 구조의 한계가 드러났습니다. 그래서 연구팀은 관계형 모델을 버리는 대신 사용자 정의 타입·함수·연산자·인덱스 접근 방식과 rule·trigger를 지원하는 새로운 시스템을 설계했습니다. 이것이 1986년에 구현을 시작한 POSTGRES입니다. 1994년에 SQL 인터프리터를 붙인 Postgres95가 나왔고, 1996년에 PostgreSQL로 이름을 변경하면서 현재의 오픈소스 프로젝트로 이어졌습니다.
