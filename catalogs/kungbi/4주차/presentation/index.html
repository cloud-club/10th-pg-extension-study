인덱스는 행을
어떻게 찾을까?

PostgreSQL의 heap/TID와 InnoDB의 clustered/secondary index

PostgreSQL 18 · 일반 heap/B-treeMySQL 8.4 · InnoDB공통 조회 경로

MVCC에서는 과거 버전을 어디에 두는지 살펴봤다면, 이번에는 인덱스가 행을 무엇으로 찾아가며, 행이 바뀔 때 무엇을 고치는지를 본다.

ORIENTATION

오늘의 질문

비교의 중심은 “어느 DB가 무조건 빠른가?”가 아니다. 먼저 각 DB에서 검색 키가 실제 행까지 어떤 경로로 이어지는지 확인하고, 그 차이가 UPDATE와 버전 관리에 어떤 영향을 주는지 따라간다.

이 자료의 전개

  • 공통 바탕: 인덱스에서 실제 행까지의 경로
  • MVCC 차이: PostgreSQL의 tuple version과 InnoDB의 Undo
  • 별도 주제: B-tree 저장 방식과 행 접근 순서 최적화

SHARED VOCABULARY

행 · 행 버전 · 인덱스 항목을 구분하자

개념주문 예시뜻
논리적 행주문 id=9001애플리케이션이 같은 주문이라고 보는 한 건
행 버전paid였던 모습, shipped인 모습UPDATE 전후 MVCC가 다루는 저장 상태
인덱스 항목customer_id=42 → 위치 정보검색 키와 행을 찾아가는 정보의 연결

주문 9001의 상태를 바꿔도 논리적인 주문이 새로 생기는 것은 아니다. 내부에 새 행 버전이 생길 수 있고, 구현에 따라 새 인덱스 항목이 필요할 수도 있다. “새 버전”과 “새 인덱스 항목”은 서로 다른 개념이다.

ROW LOOKUP

PK와 보조 키, 실제 행까지 가는 경로

PK 검색

PostgreSQLPK B-tree → TID → heap tuple
⇄
InnoDBclustered PK B-tree → 리프의 행 레코드

보조 키 검색

PostgreSQL보조 B-tree → TID → heap tuple
⇄
InnoDB보조 B-tree → PK → clustered PK B-tree → 행

PostgreSQL은 인덱스와 heap이 분리되어 있다. InnoDB에서는 PK 인덱스가 clustered index이며, 리프에 행 레코드가 저장된다. InnoDB 보조 인덱스는 행을 찾는 데 사용할 PK를 저장한다.[PG index access][InnoDB index types]

POSTGRESQL · TID

TID는 또 다른 인덱스가 아니라 heap의 위치다

customer_id 인덱스
  42 ─────→ TID (8, 3)
                 │
                 ▼
             heap page 8
               item 3: 주문 9001의 tuple version

TID(Tuple Identifier)는 heap 페이지 번호와 페이지 안 항목 번호로 된 위치 정보다. 따라서 PostgreSQL PK 조회는 PK B-tree → TID → heap이며, TID를 찾는 두 번째 인덱스를 다시 타지 않는다. ctid는 tuple version의 물리적 위치이므로 UPDATE 뒤 달라질 수 있고, 영구적인 주문 ID로 사용하면 안 된다.[PG system columns][PG page layout]

주의: 탐색 경로의 단계 수만으로 실제 디스크 I/O나 어느 DB가 빠른지를 결론낼 수 없다. 캐시, 키 길이, 데이터 분포, UPDATE 패턴과 실행 계획이 함께 작용한다.
