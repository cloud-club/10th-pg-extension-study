POSTGRESQL B-TREE

Deduplication은 중복 행이 아니라 인덱스 표현을 압축한다

논리적으로 같은 키가 여러 개:
  42 → TID A
  42 → TID B
  42 → TID C

중복 키 압축 예:
  42 → [TID A, TID B, TID C]

PostgreSQL B-tree의 deduplication은 같은 키 값을 반복 저장하는 대신, 여러 TID를 posting list로 묶어 인덱스 공간을 줄일 수 있는 기법이다. 행이나 tuple version을 병합해 삭제하는 기능은 아니다.[PG B-tree]

PRIMARY KEY SHAPE

순차 정수 PK와 무작위 UUIDv4

이 비교에서 “무작위 UUID”는 UUIDv4다. UUIDv7처럼 시간 정렬성을 갖는 형식은 같은 사례로 묶지 않는다.[RFC 9562]

순차 정수와 UUIDv4 비교에서는 키 길이와 삽입 순서가 함께 달라질 수 있다. 이 비교만으로 두 요인 중 하나의 효과라고 단정하지 말고, 실제 데이터와 workload에서 측정한다.

ROW ACCESS ORDER

Bitmap Heap Scan과 MRR은 읽을 위치의 순서를 조정한다

POSTGRESQL · BITMAP HEAP SCAN

찾은 TID:
  (3,2), (20,5), (8,1), (3,9)

페이지별로 묶기:
  3:{2,9} → 8:{1} → 20:{5}

heap 방문:
  3 → 8 → 20

Bitmap Index Scan이 TID를 모으고, Bitmap Heap Scan이 페이지별로 방문할 수 있게 한다. Bitmap은 임시 위치표다. 행을 이동하거나 MVCC 가시성 규칙을 바꾸지 않는다.[PG bitmap scans]

INNODB · MULTI-RANGE READ (MRR)

보조 인덱스가 찾은 PK:
  31, 8, 57

MRR 버퍼에서 정리:
  8, 31, 57

정리한 순서로 clustered index 접근

MRR은 보조 인덱스에서 얻은 PK를 모아 clustered record를 읽는 순서를 개선하려는 최적화다. 레코드 자체를 재배치하지 않는다.[InnoDB MRR]

두 엔진 모두: Bitmap/MRR이 위치 접근 순서를 조정한 뒤에도, PostgreSQL은 heap tuple에 대해 snapshot 가시성을 판정하고 InnoDB는 필요하면 Undo를 사용한다. 위치 정렬 최적화와 MVCC 버전 관리는 별개의 층이다.

TAKEAWAYS

네 문장으로 마무리

01PostgreSQL 인덱스는 TID로 heap tuple version을 찾고, InnoDB의 clustered PK index 리프에는 현재 행 레코드가 있다.
02PostgreSQL은 tuple의 xmin/xmax와 snapshot을 바탕으로 보이는 버전을 고른다. TID 숫자의 대소가 버전 순서를 뜻하지 않는다.
03HOT은 새 tuple version을 만들면서, 조건이 맞으면 인덱스 항목 추가를 생략하고 같은 페이지 안의 연결을 재사용한다.
04InnoDB는 clustered record와 Undo를 사용해 버전을 처리한다. 실제 성능은 키, 데이터 분포, 조회·UPDATE 패턴과 실행 계획을 함께 측정한다.
