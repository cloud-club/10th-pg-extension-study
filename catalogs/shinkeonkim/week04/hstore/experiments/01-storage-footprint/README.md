# 실험 01 — 저장 크기: hstore · jsonb · EAV

2026-09-21, PostgreSQL 16.15 / hstore 1.8, Docker(공유 CPU 3개). [bench.py](bench.py)

## 검증할 것

같은 속성 묶음을 hstore, jsonb, 행 단위(EAV, `(id, key, value)` + PK)로 저장했을 때의 행당 저장 크기와 전체 크기는 어떻게 다른가? 키가 많아지면 압축과 TOAST가 어떻게 달라지는가? 다르다면 원인은 무엇인가?

## 방법

- 키 개수 K ∈ {5, 20, 100, 500}, 값 종류 두 가지: **낮음**(10종류 단어 반복, 압축이 잘 됨) / **무작위**(md5 12자리, 압축이 잘 안 됨). 키 이름은 `attr_001` 형식 8자.
- 행 5000개(K=500은 2000개). 값은 `md5`·인덱스로 결정적으로 생성한다.
- 측정: `avg(pg_column_size(attrs))`, 압축된 행 수, 힙·TOAST·전체 크기(`pg_total_relation_size`, EAV는 PK 인덱스 포함).
- **공식 검증**: 행 하나의 저장 크기를 `4 + 4 + 4×2×쌍 + 문자열`로 계산해 저장 형태(짧은 헤더 −3 / 인라인 / 압축 / TOAST 외부 −4)로 모두 설명되는지 assert.
- **원인 대조**(K ≥ 100): (1) 같은 값을 `COMPRESSION lz4`로 저장, (2) 같은 키·값 문자열에 *끝 위치 배열*과 *길이 배열*을 각각 붙인 bytea를 pglz·lz4로 압축.
- 3회 반복. 크기 지표는 모든 회차가 같아야 하며 sync 스크립트가 검사한다.

## 해석

- **K ≤ 20에서 hstore와 jsonb는 바이트까지 같다.** 두 형식 모두 쌍마다 엔트리 2개(8B)를 쓴다.
- **K ≥ 100에서 hstore는 덜 압축된다.** 같은 문자열인데 끝 위치 배열(1, 3, 4, 7, …)은 반복이 없어 압축이 안 되고, 길이 배열은 패턴이 반복돼 잘 줄어든다. 실제 hstore(lz4 6,124B)는 끝 위치 합성본(6,140B)과, 실제 jsonb(1,943B)는 길이 합성본과 같은 자리에 있다. jsonb 소스(`src/include/utils/jsonb.h` 119~128행)의 주석도 ‘offset만 저장하면 압축이 안 돼서 길이를 저장한다’고 적고 있다.
- EAV는 행마다 튜플 헤더와 인덱스 항목이 붙어 같은 데이터에 hstore의 3~7배를 쓴다.
- **확인된 범위:** 합성 대조는 ‘배열의 종류가 압축률을 좌우한다’는 것을 보인다. hstore 바이트를 직접 바꿔 본 것은 아니다.

## 한계

- 값 분포 두 가지, 키 이름 8자. 실제 데이터에서는 `pg_column_size`를 직접 재 봐야 한다.
- 저장 형태는 1번 행 기준이다(K=500·낮음에서 hstore 2000행 중 압축된 행은 200).
- PostgreSQL 16.15(`default_toast_compression = pglz`)에서만 측정했다.
