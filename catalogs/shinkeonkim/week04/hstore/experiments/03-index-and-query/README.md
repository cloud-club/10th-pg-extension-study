# 실험 03 — 인덱스별 크기·조회·삽입 비용

2026-09-21, PostgreSQL 16.15 / hstore 1.8. [bench.py](bench.py)

## 검증할 것

hstore 인덱스(GIN, GiST siglen 16/128, btree 식 인덱스)와 jsonb GIN(`jsonb_ops`, `jsonb_path_ops`)의 크기·생성 시간·조회 시간·삽입 비용은? 어떤 쿼리를 어떤 인덱스가 도와주는가?

## 방법

- 20만 행, 행당 속성 12개(color 8종, size 5종, brand 40종, material 10종, sku_grp 1000종, 무작위 6개, 0.1%에만 `promo`). 인덱스 설정마다 같은 데이터를 복사해 만든다(`CREATE TABLE ... AS SELECT * FROM base`).
- 쿼리 5종: 2키 포함 흔함(2.5%), 2키 포함 좁음(0.25%), 값 하나 포함(0.1%), 키 존재 `?`(0.1%), `-> 'brand' = ...`(2.5%). **모든 설정에서 결과 행 수가 같은지 assert**한 뒤 시간을 잰다.
- 시간: `EXPLAIN (ANALYZE, BUFFERS)`의 실행 시간, 첫 실행 제외 7회의 중앙값. 실행 계획 노드와 `Rows Removed by Index Recheck`도 기록.
- 삽입: 인덱스가 있는 테이블에 2만 행 삽입 시간과 WAL.
- 5회 반복(새 컨테이너), 표는 중앙값.

## 결과

| 인덱스 | 크기 | 생성 (최소~최대) | 2만 행 삽입 | 삽입 WAL |
| --- | ---: | ---: | ---: | ---: |
| 없음 | — | — | 0.18 s | 9.6 MB |
| hstore GIN | 71.9 MB | 6.4 s (6.2~6.5) | 0.65 s | 33.4 MB |
| GiST(siglen 16) | 10.4 MB | 4.3 s (4.2~4.4) | 0.56 s | 12.1 MB |
| GiST(siglen 128) | 35.4 MB | 9.6 s (9.4~9.7) | 1.16 s | 20.4 MB |
| btree 식 `(attrs->'brand')` | 1.4 MB | 0.23 s (0.21~0.26) | 0.22 s | 11.1 MB |
| jsonb GIN (`jsonb_ops`) | 71.9 MB | 3.5 s (3.4~5.0) | 0.59 s | 33.5 MB |
| jsonb GIN (`jsonb_path_ops`) | 52.5 MB | 1.8 s (1.8~2.5) | 0.52 s | 36.4 MB |

쿼리 시간(ms, 중앙값):

| 쿼리 | 없음 | GIN | GiST 16 | GiST 128 | btree 식 | jsonb GIN | jsonb path |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 2키 포함 흔함 | 14.4 | 6.2 | 11.2 | 13.0 | 14.1 | 6.7 | 5.7 |
| 2키 포함 좁음 | 13.3 | 2.3 | 14.0 | 7.4 | 17.9 | 2.4 | 1.5 |
| 값 하나 포함 | 13.5 | 0.9 | 20.2 | 21.4 | 16.4 | 0.9 | 0.5 |
| 키 존재 `?` | 12.9 | 0.6 | 12.5 | 5.8 | 15.6 | 0.7 | 14.9(순차) |
| `->` 동등 | 15.6 | 16.6(순차) | 17.5(순차) | 18.0(순차) | **6.0** | 17.9(순차) | 15.6(순차) |

## 해석

- GIN은 선택도가 높을수록 이득이 크다(0.1% 조건에서 13.5 → 0.9ms). 2.5% 조건에서는 이득이 작다(14.4 → 6.2ms).
- GiST(siglen 16)는 작지만(GIN의 1/7) 손실이 커서 재검사로 걸러 내는 행이 많다. 값 하나 포함에서 순차 스캔(13.5ms)보다 느렸다(20.2ms). siglen을 128로 키우면 크기와 정밀도가 그 중간이다.
- `->` 동등 비교는 GIN·GiST가 도와주지 않는다. btree 식 인덱스는 1.4MB로 가장 작고 그 쿼리만 빠르다(6.0ms).
- hstore GIN과 jsonb `jsonb_ops` GIN은 크기(71.9MB)와 조회 시간이 사실상 같다. **생성 시간은 hstore GIN(6.4초)이 jsonb GIN(3.5초)의 약 1.8배**였다. `jsonb_path_ops`는 더 작고(52.5MB) 빠르지만 `?`를 지원하지 않는다.
- GIN 유지 비용: 2만 행 삽입이 인덱스 없음의 3.7배, WAL 3.5배.

## 한계

- 데이터가 캐시에 올라 있는 상태(첫 실행 제외)의 밀리초 단위 값이라 VM 잡음이 크다. 상대 비교로 읽는다.
- 20만 행 규모. 큰 데이터의 디스크 I/O와 GIN 펜딩 리스트 동작은 재지 않았다.
- 삽입은 단일 클라이언트 `INSERT ... SELECT` 한 번이다.
