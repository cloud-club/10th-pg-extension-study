# 실험 04 — 같은 hstore 행을 동시에 갱신하면

2026-09-21, PostgreSQL 16.15 / hstore 1.8, pgbench 클라이언트 8개 × 50회. [bench.py](bench.py)

## 검증할 것

같은 행의 서로 다른 키(또는 같은 키)를 여러 세션이 동시에 고칠 때 갱신이 유실되는가? 어떤 방식이 유실을 막는가? 한 행에 쓰기가 몰리면 처리량은 어떻게 되는가?

## 방법

- 클라이언트 8개가 각자 50번, 총 400번. 키 추가 시나리오는 `nextval`로 **매번 다른 키**를 넣으므로 기대값은 키 400개다. 카운터 시나리오는 키 `cnt` 하나를 400번 올린다.
- 방식: ① 읽고(`SELECT`) → 앱에서 합쳐 → `UPDATE`(자동 커밋) ② 같은 일을 한 트랜잭션(READ COMMITTED) ③ `SELECT ... FOR UPDATE` 후 쓰기 ④ `SET attrs = attrs || ...` ⑤ ④를 REPEATABLE READ에서.
- 읽고-쓰기의 앱 값은 pgbench `\gset`으로 실제 세션 변수에 받아 다음 문장에 넣는다(문장 사이에 다른 세션이 끼어들 수 있다).
- 경합 실험: 원자적 카운터 UPDATE를 행 1개 vs 행 1000개(무작위), 클라이언트 1·2·4·8·16, 각 4초. 실행 후 카운터 합이 처리 건수와 같은지 assert.
- **assert:** `attrs || ...`·`FOR UPDATE`·원자적 카운터는 매 회차 유실 0이어야 한다. 하나라도 어기면 그 회차는 저장되지 않는다.
- 10회 반복(새 컨테이너).

## 결과 (10회, 중앙값 · 최소~최대)

키 추가 (기대 400):

| 방식 | 성공 | 남은 키 | TPS |
| --- | ---: | ---: | ---: |
| 읽고-쓰기 (자동 커밋) | 400 | **62.5** (51~70) | 8,445 |
| 읽고-쓰기 (한 트랜잭션) | 400 | **64** (55~76) | 7,156 |
| `FOR UPDATE` 후 쓰기 | 400 | 400 (400~400) | 4,835 |
| `attrs \|\| ...` | 400 | 400 (400~400) | 8,251 |
| `attrs \|\| ...` REPEATABLE READ | 92.5 (76~108) | 92.5 | 3,702 |

카운터 (기대 400):

| 방식 | 최종 값 |
| --- | ---: |
| 읽고 → 앱에서 +1 → 쓰기 | **59** (50~75) |
| UPDATE 안에서 +1 | 400 |
| `FOR UPDATE` 후 +1 | 400 |
| UPDATE 안에서 +1, REPEATABLE READ | 82 (68~114) — 성공한 수와 같다, 나머지 318은 40001 오류 |

경합 (원자적 카운터 UPDATE, TPS):

| 클라이언트 | 1 | 2 | 4 | 8 | 16 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 행 1개 | 9,097 | 11,720 | 10,936 | 10,638 | 8,258 |
| 행 1000개 | 9,073 | 12,545 | 21,925 | 36,095 | 42,982 |

## 해석

- **잠금 단위는 행이다.** hstore 안의 키는 잠금 대상이 아니다. 같은 행의 다른 키를 바꾸는 UPDATE도 서로 기다린다(lab 04에서 `wait_event_type = Lock` 확인).
- **앱에서 읽어 합친 값을 통째로 쓰면 유실된다.** 400건 중 남은 키가 51~76개. 오류가 없으므로 조용히 사라진다. 한 트랜잭션 안에서 해도 같다.
- **값을 UPDATE 안에서 계산하면 안전하다.** 기다리던 UPDATE는 커밋된 최신 행으로 식을 다시 계산한다(READ COMMITTED). 10회 모두 유실 0.
- **REPEATABLE READ는 유실 대신 오류로 거절한다.** 재시도 없이 실행했으므로 성공은 400 중 76~108건뿐이다. 실서비스에서는 40001 재시도가 필요하다.
- **행 1개에 몰리면 처리량이 늘지 않고 지연만 는다**(클라이언트 16: 1.9ms). 행을 분산하면 CPU가 허락하는 만큼 늘어난다(측정 환경 CPU 3개).

## 한계

- 격리된 컨테이너 안에서 pgbench와 서버가 같은 CPU를 나눈다. TPS 절대값은 일반화하지 않는다.
- 서버 크래시·복제 지연·분산 환경은 다루지 않았다.
- `SERIALIZABLE`은 측정하지 않았다.
