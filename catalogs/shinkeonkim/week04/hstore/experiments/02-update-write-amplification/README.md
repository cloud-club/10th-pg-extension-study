# 실험 02 — 키 하나를 바꿀 때 쓰는 양 (쓰기 증폭)

2026-09-21, PostgreSQL 16.15 / hstore 1.8. [bench.py](bench.py)

## 검증할 것

hstore 컬럼에서 키 하나를 바꾸는 UPDATE는 얼마나 쓰는가? 키 개수, GIN 인덱스, jsonb·일반 열·EAV와 비교하면? 키 하나를 읽는 데는 얼마나 걸리는가?

## 방법

- 행 1000개, K ∈ {5, 50, 500}. 각 행의 `attr_001` 값을 바꾸는 UPDATE를 행마다 한 번(1000건).
- 비교: `hstore ||`, `hstore h['k']=`, `hstore || + GIN`, `jsonb_set`, 열 K개 테이블의 열 하나, EAV 행 하나.
- 측정: UPDATE 1건당 WAL 바이트(`pg_wal_lsn_diff`), 힙·TOAST 증가량, HOT 비율(`pg_stat_user_tables`), 1000건 실행 시간.
- 신뢰도: autovacuum 테이블 단위 비활성, 1차 패스로 페이지를 먼저 건드려 FPW 소진 뒤 2차 패스를 측정, **측정 구간 체크포인트 수가 변하지 않았음을 assert**, UPDATE 건수 = 통계의 `n_tup_upd`.
- 읽기: `EXPLAIN (ANALYZE, TIMING OFF)`로 1000행에서 키 하나를 읽는 실행 시간의 중앙값(첫 실행 제외 7회).
- 5회 반복(WAL 바이트는 매회 같았다).

## 결과 (UPDATE 1건당 WAL)

| | K=5 | K=50 | K=500 |
| --- | ---: | ---: | ---: |
| hstore `\|\|` | 176 B | 692 B | 15,806 B |
| hstore `h['k']=` | 176 B | 639 B | 15,803 B |
| hstore `\|\|` + GIN | 635 B | 10,489 B | 113,609 B |
| jsonb `jsonb_set` | 176 B | 692 B | 9,241 B |
| 일반 테이블 열 하나 | 177 B | 182 B | 6,784 B |
| EAV 행 하나 | 176 B | 176 B | 176 B |

K=500: hstore의 TOAST 증가는 1000건에 16.4MB(UPDATE당 약 16KB = 값 전체), jsonb 8.3MB. GIN이 있으면 HOT 비율이 모든 K에서 0.00. K=50에서 hstore·jsonb의 HOT 비율은 0.64.

키 하나 읽기(1000행, ms, 중앙값):

| | K=5 | K=50 | K=500 |
| --- | ---: | ---: | ---: |
| hstore `->` | 0.24 | 0.53 | 2.75 |
| jsonb `->>` | 0.08 | 0.36 | 10.28 |
| 일반 열 | 0.06 | 0.23 | 1.18 |
| EAV (PK 1000번) | 0.22 | 1.86 | 9.36 |

## 해석

- **키 하나를 바꿔도 값 전체를 새로 쓴다.** 키가 5→50→500으로 늘면 hstore의 WAL이 176→692→15,806B. EAV는 176B로 그대로.
- **첨자와 `||`는 같다.** 키 하나만 바꿀 때 비용 차이가 없다(문서의 ‘여러 키는 `||`가 낫다’는 다른 이야기).
- **GIN이 있으면 훨씬 비싸다.** K=500에서 113,609B(7.2배). 새 튜플이 되면서 키·값 항목 1,000개를 다시 등록하고, 인덱스 열이 바뀌어 HOT도 못 쓴다.
- **jsonb는 압축된 만큼 적게 쓰지만 읽기가 느리다.** K=500에서 jsonb 9,241B(hstore 15,806B)이지만 읽기 10.28ms(hstore 2.75ms). 이 데이터(12자리 해시)에서 jsonb는 압축되고 hstore는 압축되지 않는다.
- 일반 테이블의 열 500개짜리 행은 행 하나가 페이지 하나에 가까워 UPDATE마다 새 페이지가 필요해 비싸다(힙 +8.2MB, HOT 0). ‘열이 항상 싸다’는 뜻이 아니다.
