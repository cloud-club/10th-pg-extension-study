# 심화 04 · 공간, 실행 계획, 갱신과 운영

## 초기 집계와 재사용을 분리하기
[Lab 04](lab-performance.md)는 정확한 원본 COUNT DISTINCT, 원본에서 HLL 생성, 저장된 일별 스케치 병합을 비교합니다. 세 번째가 읽는 행 수가 적은 것은 앞서 스케치를 만들었기 때문입니다. 최초 집계·저장·갱신 비용과 오류를 함께 설명해야 합니다.

## 그룹 수와 메모리
스케치 하나의 binary 크기에 그룹 수를 곱하면 저장 규모의 첫 모델을 만들 수 있습니다. 하지만 집계 상태는 저장된 압축 bytes와 다를 수 있습니다. 해시 테이블·정렬·워커·메모리 문맥을 포함한 peak RSS를 pg_column_size로 대체하지 않습니다. GROUP BY 키가 폭증하면 작은 스케치도 큰 비용을 만들 수 있습니다.
설치 소스에는 집계 계획에 관여하는 hook와 hll.force_groupagg 설정이 있습니다. 실제 적용값·GroupAggregate/HashAggregate·Sort·임시 I/O를 확인합니다. 본 Lab은 병렬 worker를 0으로 통제했고 병렬 합산의 성능·메모리 검증은 별도 과제입니다.

## 갱신 SQL의 정확성
```sql
UPDATE daily_users
SET sketch=hll_union(sketch,:new_sketch)
WHERE day=:day;
```
개념적인 parameterized UPDATE입니다. 앱에서 값을 읽고 합친 뒤 오래된 스케치를 덮어쓰는 read-modify-write는 다른 갱신을 잃을 수 있습니다. DB 안의 갱신·트랜잭션·잠금·충돌 정책을 검토합니다. 스케치의 중복 입력 성질이 업무 업데이트의 동시성 오류를 자동 해결하는 것은 아닙니다.

## 신선도와 보존
지연 이벤트가 어제 날짜로 도착하면 어제 스케치를 갱신하고 그 기간의 결과도 다시 읽어야 합니다. 데이터 삭제·ID 정책 변경에는 원본 보존 또는 재생성 가능한 더 작은 단위가 필요합니다. 원본을 모두 버린 후 정확한 새 차원 분석을 요구하면 스케치만으로 답하지 못할 수 있습니다.

## 진단 순서
결과 의미·계약 → 정확한 기준값 → 오차 분포 → 처리 행 수 → 초기 생성·반복 시간 → 저장 공간 → 동시 부하와 갱신 실패 순서로 조사합니다. 평균뿐 아니라 원시 표본과 범위를 보관하고 논문 모델·Lab 관측·운영 보장을 분리합니다. [측정 결과](results.md)와 [근거](resources.md)로 이어집니다.
