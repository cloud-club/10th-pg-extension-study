# 기본 02 · 정확한 계산은 무엇을 기억할까?

## 명단을 들고 세는 방법
이미 본 학생 번호를 집합에 보관하면 새 번호인지 확인할 수 있습니다. 고유 학생이 많아질수록 이 방식의 보관 공간도 커집니다. 번호를 정렬한 뒤 이웃한 중복을 제거하는 방법도 있지만 정렬 작업에 비용이 듭니다. 이는 설명용 모델이며 PostgreSQL이 모든 쿼리에서 같은 자료구조를 사용한다는 뜻은 아닙니다.

## SQL에서는 계획을 확인하기
```sql
EXPLAIN (ANALYZE,BUFFERS)
SELECT count(DISTINCT user_id) FROM hll_lab.events;
```
Lab의 전용 데이터가 준비된 뒤 실행합니다. Aggregate·입력 scan·정렬·임시 I/O 등 실제 계획을 읽습니다. 인덱스가 있거나 데이터가 이미 정렬된 경우, work_mem·병렬 설정이 다른 경우는 별도로 비교합니다. 정확한 집계를 항상 전체 메모리 집합이라고 단정하지 않습니다.

## 언제 근사가 의미 있을까?
| 요구 | 선택 기준 |
| --- | --- |
| 결제 대상 명단·정산 인원 | 정확한 원본·제약·계산 필요 |
| 대시보드의 큰 방문 규모 | 허용 오차와 공간·시간 비교 |
| 월간·주간 반복 집계 | 요약을 재사용·병합할 수 있는가? |
| 특정 사용자 존재 확인 | 개수 추정과 다른 문제 |

가령 100만 명과 101만 명의 차이를 허용하는 화면이라도 50명과 51명의 차이가 중요한 업무가 있습니다. “근사라서 빠르다”보다 어떤 오류를 허용하는지부터 적습니다.

## 숫자를 저장할까, 다시 합칠 수 있는 요약을 저장할까?
COUNT DISTINCT 결과 10,000이라는 숫자에는 누가 다른 날짜에도 왔는지 정보가 없습니다. HLL 스케치는 원본 명단을 대신 보관하는 것이 아니라, 같은 ID의 해시가 병합에서 중복 효과를 만들지 않도록 개수 추정용 통계를 남깁니다. “이미 계산한 숫자”와 “다른 요약과 합쳐 다시 숫자를 읽을 수 있는 객체”를 구분합니다.

## 비용의 세 층
원본 읽기, 요약 만들기, 만들어진 요약을 재사용하기를 나눕니다. 원본에서 HLL을 처음 만들 때도 입력을 읽고 해시를 계산합니다. 요약을 미리 저장하면 이후 질문에서 읽는 행 수가 줄지만 처음 생성·갱신 비용을 지불했습니다. [Lab 04](lab-performance.md)는 이 비용을 구분합니다.
