# Lab 04 · 초기 집계와 저장된 스케치 재사용

## 비교할 세 질문
```sql
SELECT count(DISTINCT user_id) FROM hll_lab.events;
SELECT hll_cardinality(hll_add_agg(hll_hash_integer(user_id),11,5,-1,1))
FROM hll_lab.events;
SELECT hll_cardinality(hll_union_agg(sketch)) FROM hll_lab.daily;
```
앞의 두 쿼리는 원본 210,000행, 마지막은 일별 스케치 7행을 읽습니다. 정확한 결과와 근사 결과는 같아야 하는 속도 경주가 아닙니다. HLL 원본 집계와 저장 스케치 병합이 같은 추정값을 만드는지는 Lab 02에서 확인합니다.

## 측정 기준
방식별 예열 2회·본 측정 10회, 순서를 회차별로 순환합니다. EXPLAIN (ANALYZE,BUFFERS,FORMAT JSON)의 Execution Time을 저장합니다. 병렬 worker=0, work_mem·버전·패키지를 기록하며 앱의 결과 전송·화면 지연과 구분합니다.
일별 스케치를 만드는 CREATE TABLE AS도 EXPLAIN ANALYZE로 실제 실행하고 계획·서버 시간을 저장했습니다. 초기 생성 비용은 단일 실행이므로 반복 중앙값과 같은 신뢰도로 표현하지 않습니다. 표 크기는 pg_total_relation_size입니다.

## 그림 1 · 반복 측정값과 중앙값
![실측 · 방식별 예열 2회 후 서버 시간 10표본. 세로축은 로그 축, 점은 각 실행, 검은 선은 중앙값입니다.](/hll/plots/lab04-read-times.svg)
정확 원본 집계와 원본 HLL 생성은 둘 다 210,000행을 읽습니다. 일별 병합은 이미 만든 스케치 7행만 읽어 훨씬 짧았습니다. 로그 축의 같은 높이 차이는 같은 밀리초 차이가 아니라 같은 배수 차이입니다. 스케치 병합이 원본 생성보다 빠른 것은 조회 알고리즘만 바꾼 공정한 동일 작업 비교가 아니라 사전 계산을 재사용한 결과입니다.
시행별 점을 남겨 이번 예열 환경의 흔들림을 보여줍니다. 앱 응답 시간·p99·WAN·동시 부하를 측정한 값은 아닙니다.

## 그림 2 · 초기 생성까지 포함해 생각하기
![합산 모델 · 정확 집계와 원본 HLL 생성의 반복 중앙값, 일별 스케치 생성의 단일 실측값과 병합 중앙값으로 계산한 조회 1·10·100회 비용입니다.](/hll/plots/lab04-amortization.svg)
사전 계산의 초기 생성 시간 약 31.27ms도 더했습니다. 한 번만 조회하면 스케치 생성·저장이 필요한 이유부터 검토해야 하고, 같은 질문을 반복하면 병합 재사용의 비용 구조가 달라집니다. 그림은 실측 숫자로 계산한 모델이며 조회 100회를 실제 서비스에서 실행한 총시간이 아닙니다.
계산식은 매번 정확 집계=N×정확 집계 중앙값, 매번 원본 HLL=N×원본 HLL 중앙값, 사전 생성 후 재사용=생성 단일 시간+N×병합 중앙값입니다. 원본 변화에 대한 갱신·정리·저장·실패 비용은 모델에서 제외돼 있습니다. 초기 생성 단일 측정의 신뢰도를 반복 중앙값과 같게 표시하지 않습니다.

## 함께 읽을 계획
scan 출력 행 수·Aggregate·Sort·버퍼·temp I/O·worker를 확인합니다. HLL이 입력 스캔을 없앴는지, 미리 계산한 스케치가 스캔 대상을 줄였는지 구분합니다. 저장 bytes를 집계 메모리로 주장하지 않습니다.
