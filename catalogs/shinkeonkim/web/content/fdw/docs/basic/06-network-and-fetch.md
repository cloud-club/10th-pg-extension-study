# 06. RTT·대역폭·fetch

## 이 장에서 얻을 것

왕복 대기와 데이터 전송을 따로 계산한다. fetch_size가 해결하는 부분과 해결하지 못하는 부분을 구분한다. 웹의 계산기는 실제 벤치마크와 분리한 가정 모델이다.

## 1. RTT와 대역폭의 차이

RTT는 요청이 갔다가 응답이 돌아오는 왕복 시간이다. 대역폭은 단위 시간에 옮길 수 있는 데이터량이다. 도서관에 전화하는 데 걸리는 시간과 트럭에 몇 권을 실어 운반할 수 있는지는 다른 질문이다.

작은 데이터를 수천 번 요청하면 RTT가 중요해진다. 한 번에 큰 본문을 많이 받으면 전송 바이트와 대역폭이 중요해진다. 두 경우 모두 단순히 “네트워크가 느리다”고 부르면 개선 방향을 찾기 어렵다.

## 2. postgres_fdw가 행을 묶어 받는다

SELECT 스캔은 원격 커서를 사용해 결과를 묶음으로 가져올 수 있다. fetch_size는 한 번에 가져올 행 수이며 기본값은 100이다. 앱이 결과를 10만 번 요청한다는 뜻이 아니라 DB 사이에서 여러 FETCH가 일어날 수 있다는 뜻이다.

```sql
ALTER SERVER school_remote OPTIONS (ADD fetch_size '1000');
-- 이미 옵션이 존재하면 ADD 대신 SET으로 바꾼다.
ALTER SERVER school_remote OPTIONS (SET fetch_size '100');
```

테이블 수준 fetch_size가 있으면 server 수준보다 우선한다. 설정 하나를 바꿨는데 특정 표가 그대로라면 표의 옵션도 확인한다. 읽기 fetch_size와 쓰기 batch_size는 다른 설정이다.

## 3. 교육용 계산

반환 행 수 N, fetch_size F, RTT R을 가정한다. 결과를 끝까지 순차적으로 읽는 단순 모델의 데이터 묶음 수는 ceil(N/F), 왕복 대기 성분은 ceil(N/F) × R이다.

예시 N=10,000, F=100, R=20ms이면 100묶음·2초다. F=1,000이면 10묶음·0.2초다. 이 숫자는 설정값으로 계산한 가정이며 실제 실행 시간이나 실제 FETCH 횟수의 측정값이 아니다. 커서 생성·종료 확인·트랜잭션·실행 계획 비용은 제외했다.

큰 F가 유리해 보이는 이유는 RTT를 내는 횟수를 줄이기 때문이다. 원격 표 읽기나 GROUP BY의 CPU 연산 자체를 F가 없애주지는 않는다.

## 4. 전송 바이트도 계산한다

한 행 평균 1KB를 10만 행 옮긴다고 가정하면 논리적 데이터만 약 100MB다. 100MB/s의 유효 전송률이라면 데이터 전송 성분만 약 1초다. 프로토콜·TLS·텍스트 변환·압축 여부·겹쳐 실행되는 구간을 제외한 설명용 계산이다.

pg_column_size는 PostgreSQL 내부 값 크기를 보는 도구다. 이를 네트워크 실제 바이트로 그대로 부르면 안 된다. 실제 전송량은 네트워크 계측이나 드라이버/프로토콜 수준 관측을 추가해야 한다.

## 5. 큰 fetch가 항상 낫지 않은 이유

큰 묶음은 행 버퍼와 변환 작업을 한꺼번에 늘릴 수 있다. payload가 긴 표, 작은 LIMIT에서 일찍 중단하는 쿼리, 여러 동시 backend에서는 메모리와 불필요한 선취를 함께 본다. 총 지연뿐 아니라 첫 결과 시간·메모리·동시 부하도 비교한다.

가장 먼저 할 개선은 필요 없는 행과 열을 이동하지 않는 것이다. 원격 필터·원격 집계와 SELECT 열 축소를 확인한 뒤 fetch_size를 조정하면 원인과 처방이 연결된다.

## 6. 복습

질문: fetch_size를 10배로 늘리면 전체 쿼리가 10배 빨라질까?

답: 왕복 대기 부분이 줄 수 있다. 전체 시간에는 원격 계산·전송량·로컬 처리가 있으므로 10배 향상을 보장하지 않는다.

질문: 최종 count(*)가 한 행인데 fetch_size 비교가 별 의미 없는 이유는?

답: 원격 집계가 됐다면 반환 행이 한 행이어서 많은 FETCH가 필요 없다. 전체 원본 행을 실제로 받는 쿼리와 구분한다.
