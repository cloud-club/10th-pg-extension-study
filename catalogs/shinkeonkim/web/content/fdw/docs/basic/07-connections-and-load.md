# 07. 연결·세션·동시 부하

## 이 장에서 얻을 것

앱 요청 수, 로컬 backend 수, 원격 연결 수를 구분한다. 처리량과 p95를 읽는 기초를 쌓는다. 한 번 빠르게 실행한 결과를 서비스 전체 성능으로 확대하지 않는다.

## 1. 세션은 연결이 유지되는 기간이다

앱 풀의 연결 하나는 로컬 PostgreSQL backend 하나를 사용한다. 그 backend가 원격 표를 처음 읽으면 원격 연결을 열고 기본적으로 이후 조회에 재사용한다. 별도 로컬 backend가 이 연결을 전역으로 공유하는 것은 아니다.

로컬 backend 20개가 모두 같은 server·mapping을 사용했다고 가정하면 그 목적지에 원격 연결 20개가 남을 수 있다. 각 backend가 목적지 두 개에 접속했다면 조합 수가 늘어난다. 실제 연결 수는 어느 backend가 어떤 목적지를 사용했는지에 달려 있다.

## 2. 연결 수의 설명용 상한

```text
FDW 연결 예산 ≈ 원격을 사용하는 로컬 backend 수
              × backend당 실제 접촉한 server/user mapping 조합 수
```

여기에 원격의 일반 앱 연결·관리 연결·여유 슬롯을 더한다. 이 식은 용량을 생각하는 가정 모델이며 열린 연결의 실제 관측값은 아니다. connection 객체 수가 많아도 모든 연결이 바쁜 것은 아니므로 idle과 active도 구분한다.

## 3. 연결 유지의 이익과 비용

keep_connections=true는 연결 재사용으로 인증·TLS·수립 비용을 줄인다. 대신 오래 살아 있는 로컬 세션이 원격 슬롯을 점유할 수 있다. false는 트랜잭션 종료 후 연결을 닫아 슬롯 점유를 줄일 수 있지만 다음 요청에 연결 수립 비용을 다시 낸다.

```sql
SELECT * FROM postgres_fdw_get_connections();
```

이 함수는 실행한 로컬 세션의 FDW 연결만 보여준다. 전체 앱 풀 연결을 한 번에 열거하는 전역 관측 도구가 아니다. 전체 상태는 원격 pg_stat_activity와 application_name을 함께 사용한다.

## 4. 처리량과 지연은 다르다

처리량은 초당 완료 요청 수다. 지연은 요청당 소요 시간이다. 평균 지연이 괜찮아도 일부 요청이 길게 대기할 수 있으므로 p50·p95·p99를 본다. p95는 관측 요청의 95%가 그 시간 이하였다는 뜻이다.

요청 10개만으로 p99를 계산하면 극단 값 하나를 대략 읽는 수준이다. 이 자료의 작은 반복 실험은 중앙값·최소·최대 중심으로 보고, 부하 실험에서는 충분한 시간과 요청 수를 기록한다. 서로 다른 측정 범위를 같은 지표 이름으로 숨기지 않는다.

## 5. 동시성을 높였는데 더 느려졌다

원격 CPU·디스크·잠금·연결 슬롯은 무한하지 않다. 동시 요청을 늘려 처리량이 처음에는 증가해도 자원이 포화하면 대기만 커질 수 있다. 로컬에는 원격 응답을 기다리는 backend가 쌓이고 앱 풀 대기도 늘어난다.

따라서 SQL 실행 시간 외에 앱 풀 대기, 연결 수립, 전체 요청 시간도 구분한다. pg_stat_statements는 앱 풀에 들어가기 전 대기를 측정하지 않는다. 원격 통계만 보아도 사용자 전체 응답 시간을 알 수 없다.

## 6. 복습

질문: psql 하나에서 get_connections 결과가 한 행이면 서비스 전체도 연결 하나일까?

답: 아니다. 그 psql 세션만 관측한 것이다. Lab 05는 여러 로컬 세션을 열어 원격에서 연결이 여러 개 생기는지 확인한다.

질문: 원격 대기 이벤트가 보이면 네트워크가 문제일까?

답: 원격 SQL의 CPU·I/O·잠금 때문일 수도 있다. 기다리는 위치와 원인을 구분한다.
