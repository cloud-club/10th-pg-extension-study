# 실험 07 — 라벨 필터링 검색: DiskANN 네이티브 라벨 필터 vs HNSW + `iterative_scan`

PostgreSQL 16.15 / pgvector 0.8.6 / pgvectorscale 0.9.1, Docker(공유 CPU 3개, RAM 3.8GiB). [bench.py](bench.py)

> **정정(2026-10-05, 이 실험을 웹 자료로 옮기다가 발견)**: 이 실험의 첫 판은 "HNSW 는 `iterative_scan` 을 어떤 값으로 둬도 0행, DiskANN 만 10행"이라는 극적인 결론을 냈다. **그 데이터는 50,000행 중 서로 다른 벡터가 10개뿐이었다** - 실험 01 의 "측정 중 겪은 함정" 2번에 직접 기록해 둔 스칼라 서브쿼리 InitPlan 버그를 이 실험에서 다시 만들었다. 서로 다른 벡터 50,000개로 다시 재니 결론이 바뀌었다(아래). 첫 판의 조건도 `duplicate_bug` 데이터셋으로 그대로 다시 재서 "무슨 일이 있었나"를 함께 남긴다. 첫 판 원본은 [results/run-duplicate-bug.json](results/run-duplicate-bug.json).

## 왜 이 실험이 필요했는가

[pgvectorscale lab](../../pgvectorscale/labs/01-install-and-diskann/)에서 DiskANN 의 라벨 필터링(`vector_smallint_label_ops`)이 지정 라벨만 돌려주는 것은 확인했다. 하지만 그것만으로는 "DiskANN 을 쓸 이유"가 되지 않는다 - pgvector HNSW 도 `WHERE` 필터 + `hnsw.iterative_scan`(AWS 공식 프로덕션 가이드가 `relaxed_order` 를 권장값으로 제시)으로 같은 질문에 답할 수 있다. "같은 필터 검색을 두 방법으로 하면 정확도와 비용이 각각 어떻게 다른가"를 직접 잰다.

## 가설

**H1(HNSW 기본값).** `hnsw.iterative_scan = off`(기본값)이면, 필터를 통과하는 후보가 `ef_search` 안에 거의 없을 때 k 개보다 적게 돌려준다 - AWS 가이드의 경고.
**H2(iterative_scan).** `relaxed_order`·`strict_order` 로 켜면 k 개를 채운다.
**H3(비용).** 둘 다 k 개를 채운다면, 라벨을 인덱스 안에서 거르는 DiskANN 이 더 적은 버퍼로 끝날 것이다.

## 방법

- 32차원, 라벨 10개 × 5,000행(총 50,000행). 라벨 `L` 의 중심은 "L번째 차원만 10.0, 나머지 0.0", 행마다 차원당 ±0.4 균등 노이즈. 행은 라벨 순서로 적재.
- 질의 20개는 모두 **라벨 1 중심 근처**에 둔다(전역 최근접 이웃이 거의 다 라벨 1). 필터는 **라벨 10**. 라벨 2~10 의 중심은 질의에서 모두 같은 거리(≈ 14.1)라 "가장 먼" 라벨이 따로 있는 것은 아니다 - 질의가 속한 군집이 아닌 다른 군집을 필터로 고른 것이다.
- **정답**: 인덱스를 쓰지 않는 Seq Scan 으로 구한 정확한 필터 top-10.
- 비교: HNSW(`USING hnsw (embedding vector_l2_ops)`) + 같은 `WHERE`, `hnsw.iterative_scan ∈ {off, relaxed_order, strict_order}` / DiskANN(`USING diskann (embedding vector_l2_ops, labels)`). 인덱스는 하나씩만 둔다.
- 지표: 질의당 반환 행 수, 라벨이 틀린 행 수, recall@10(정답과의 교집합), **반환 결과의 평균 거리**, 20개 질의를 `LATERAL` 로 묶은 `EXPLAIN (ANALYZE, BUFFERS)` 의 질의당 버퍼·시간(3회 중앙값).
- 같은 절차를 `duplicate_bug` 데이터셋(첫 판의 생성 방식 그대로)에도 적용한다. 생성 직후 `count(DISTINCT embedding)` 을 기록하고, 본 측정 데이터는 전부 서로 다른지 assert 한다.

## 결과 — 본 측정 (`correct`, 서로 다른 벡터 50,000개)

| 설정 | 반환 행/질의 | 라벨 틀림 | recall@10 | 결과 평균 거리 | 버퍼/질의 | ms/질의 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| HNSW, `iterative_scan=off`(기본값) | **0** | - | 0.000 | - | 1,071 | 0.17 |
| HNSW, `relaxed_order` | 10 | 0 | 0.385 | 13.781 | 27,753 | 11.90 |
| HNSW, `strict_order` | 10 | 0 | 0.165 | 13.815 | 28,151 | 11.98 |
| DiskANN 라벨 필터 | 10 | 0 | 0.060 | 13.880 | **5,652** | **1.33** |

거리 기준선: 정답 top-10 의 평균 거리 **13.718**, 라벨 10 전체의 거리 분포 13.342(최소) · 14.267(중앙값) · 15.223(최대). 빌드: HNSW 2.0초, DiskANN 122.6초. HNSW 인덱스 스캔은 필터 없이 끝까지 돌리면 50,000행 전부에 닿았다(그래프가 끊어져 있지 않다).

## 결과 — 첫 판의 데이터 (`duplicate_bug`, 서로 다른 벡터 10개)

| 설정 | 반환 행/질의 | 버퍼/질의 | ms/질의 |
| --- | ---: | ---: | ---: |
| HNSW, `off` / `relaxed_order` / `strict_order` | **0 / 0 / 0** | 224 / 255 / 255 | 0.10 / 0.12 / 0.12 |
| DiskANN 라벨 필터 | 10 | 1,056 | 0.22 |

이 데이터에서는 HNSW 인덱스 스캔이 **필터 없이도 50,000행 중 476행에만 닿고 끝났다** - 라벨마다 완전히 같은 벡터 5,000개가 이웃 목록을 거리 0 인 복제본으로 채워, 그래프가 군집 안에 갇힌 조각으로 끊어진 것으로 본다. 첫 판의 "어떤 설정으로도 0행"은 이 때문이었다. (이 데이터에서는 라벨 10 안의 점이 전부 같은 벡터라 recall@10 은 동률 끊기에 따라 결정되므로 싣지 않는다.)

## 가설 검증

**H1 - 채택.** 기본값에서 HNSW 는 20개 질의 모두 0행이었다. `ef_search`(40) 범위 안의 후보는 전부 라벨 1 이고, 필터가 그걸 다 버린다(질의당 1,071 버퍼만 읽고 끝남).

**H2 - 채택.** `relaxed_order`·`strict_order` 모두 20개 질의 전부 10행을 채웠고 라벨이 틀린 행도 없었다. AWS 가이드의 처방이 이 데이터에서는 그대로 통한다.

**H3 - 채택.** 같은 10행을 얻는 데 DiskANN 은 질의당 5,652 버퍼·1.33ms, HNSW `relaxed_order` 는 27,753 버퍼·11.90ms 였다(버퍼 4.9배, 시간 9.0배). 다만 **품질은 공짜가 아니었다**: 결과의 평균 거리는 HNSW 13.781, DiskANN 13.880 으로 HNSW 쪽이 정답(13.718)에 더 가깝다. 정답과 라벨 10 중앙값(14.267) 사이의 간격을 100% 로 보면 HNSW 는 11%, DiskANN 은 30% 지점이다.

## 해석

- **결론은 "HNSW 는 못 푼다"가 아니라 "비용과 품질의 트레이드오프"다.** 기본 설정 그대로면 HNSW 는 필터 검색에 빈 결과를 낸다(이건 실제 함정이다). `iterative_scan` 을 켜면 해결되지만, 필터를 통과하는 후보가 질의 근처에 없을 때는 그래프를 넓게 훑어야 해서 비싸진다. DiskANN 의 라벨 인덱스는 같은 일을 약 9배 싸게 하되, 결과가 조금 덜 가깝다.
- recall@10 은 이 설계에서 약한 지표다. 라벨 10 의 점들은 질의에서 13.3~15.2 로 거의 같은 거리라, "정확한 top-10" 은 근소한 차이의 동률 경쟁이 된다. 그래서 recall(0.385 vs 0.060)만 보면 DiskANN 이 형편없어 보이지만, 거리로 보면 둘 다 무작위로 고른 라벨 10 점(중앙값 14.267)보다 훨씬 가까운 점을 돌려줬다. 두 지표를 함께 싣는 이유다.
- **완전 중복 벡터가 대량으로 있으면 HNSW 그래프가 끊어질 수 있다** - 첫 판의 실수가 우연히 보여준 현상이다. 같은 문서를 여러 번 넣었거나, 빈 문자열·기본값 임베딩이 많이 쌓인 테이블이라면 실무에서도 비슷한 일이 생길 수 있다. 다만 이 관찰은 "군집마다 완전히 같은 벡터 5,000개"라는 극단적인 합성 조건 하나에서만 확인했다 - 중복이 얼마나 많아야 문제가 되는지는 재지 않았다. DiskANN 은 같은 데이터에서 10행을 돌려줬다.

## 한계

- 합성 데이터 한 가지(군집 10개, 군집 사이 거리가 매우 큼)다. 실제 임베딩처럼 라벨과 벡터 분포가 느슨하게만 연관된 경우, 필터를 통과하는 후보가 질의 근처에 섞여 있어 HNSW 의 비용이 훨씬 작을 수 있다.
- 1회 실행이다. HNSW 빌드는 비결정적이라 recall·거리가 실행마다 조금씩 흔들린다(이 README 작성 직전 실행에서 `relaxed_order` 의 recall 은 0.305 였다).
- `hnsw.ef_search`·`diskann.query_search_list_size` 는 기본값으로 고정했다. 품질과 비용을 맞춰 놓고 비교하려면 두 손잡이를 함께 스윕해야 한다 - 다음 과제.
- DiskANN 빌드가 HNSW 의 약 60배(122.6초 vs 2.0초) 걸렸다 - 실험 02 의 빌드 비용 결과와 방향이 같다.
