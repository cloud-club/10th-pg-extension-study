# 실험 01 — ANN 튜닝 파라미터에 따른 recall@10 vs 비용

2026-10-04, PostgreSQL 16.15 / pgvector 0.8.6 / pgvectorscale 0.9.1, Docker(공유 CPU 3개, RAM 3.8GiB). [bench.py](bench.py)

## 왜 이 실험이 필요했는가

`pgvector.md`·`pgvectorscale.md`(17회차)는 "HNSW/IVFFlat/DiskANN 모두 근사(ANN) 인덱스라 recall을 질의 시점 파라미터로 조절한다"고 서술했지만, 그 서술은 공식 문서를 옮긴 것이었지 직접 잰 것이 아니었다(문서에 "미실측"으로 표시되어 있었다). 세 엔진의 튜닝 손잡이 이름도 다르고(`ef_search`/`probes`/`query_search_list_size`), 같은 방향으로 움직이는지도 확인되지 않았다. 세 엔진을 **같은 데이터, 같은 ground truth**로 나란히 재서 그 서술을 숫자로 확정하거나 반박하는 것이 이 실험의 목적이다.

## 가설

**H1.** HNSW·IVFFlat·DiskANN 모두, 질의 시점 파라미터(`ef_search`/`probes`/`query_search_list_size`)를 올리면 recall@10이 오르고 버퍼·시간 비용도 같이 오른다 - recall과 비용이 같은 방향으로 움직이는 트레이드오프를 보인다.

이 가설이 **거짓으로 밝혀지는 경우**(예: 파라미터를 올려도 recall이 변하지 않거나, 비용만 늘고 recall 이득이 없는 엔진이 있다면)는 그 자체로 "이 엔진은 이 규모에서 튜닝할 필요가 없다/소용없다"는 실무적 의미를 가지므로, 가설이 틀리는 것도 유의미한 결과로 본다.

## 방법

- 배경 벡터 50,000개(균등분포 난수, 128차원) + 질의 50개마다 "진짜 가까운 점" 20개를 질의 벡터 + 균등분포 노이즈(차원당 ±0.5)로 섞어 넣음(총 51,000행). 질의 50개는 배경과 별도 테이블.
- **ground truth**: 인덱스를 하나도 만들기 전에 `enable_indexscan=off`로 강제한 Seq Scan + 정렬로 질의마다 정확한 top-10을 계산.
- 인덱스는 **한 번에 하나만** 둔다(이전 회차 K절의 측정 원칙) - HNSW → 드롭 → IVFFlat → 드롭 → DiskANN 순서로 만들고, 만들 때마다 빌드 시간·인덱스 크기를 `\timing`/`pg_relation_size`로 직접 측정.
- 빌드 파라미터는 **기본값 그대로**(HNSW `m=16, ef_construction=64`, IVFFlat `lists=50`\*, DiskANN 기본). 질의 시점 파라미터만 스윕: HNSW `ef_search ∈ {10,40,100,200}`, IVFFlat `probes ∈ {1,10,50}`(=lists 전체), DiskANN `query_search_list_size ∈ {10,50,100,200}`.
- recall@10 = 50개 질의 각각의 ANN 결과 10개와 ground truth 10개의 교집합 크기 평균 / 10. 비용은 `EXPLAIN (ANALYZE, BUFFERS)`로 50개 질의를 한 번의 `LATERAL` 조인으로 묶어 측정(질의당 평균으로 환산), 시간은 3회 재실행한 중앙값.
- 전체를 **2회 반복 실행**해 재현성을 확인했다.

\* `lists = rows/1000`(pgvector 권장값, rows < 1M)

## 측정 중 겪은 함정 (고치는 데 대부분의 시간을 썼다)

1. **균등분포 난수만으로는 최근접 이웃이 정의되지 않는다.** 128차원 균등분포 벡터끼리는 "차원의 저주"로 모든 쌍의 L2 거리가 거의 완전히 같은 값(약 4.0)에 수렴한다(집중 현상, concentration of measure). 처음 이 데이터로 돌렸을 때 HNSW/DiskANN recall@10이 **모든 파라미터에서 정확히 0.0**, IVFFlat은 **정확히 1.0**이 나왔다 - 숫자가 하나같이 "깔끔하게" 나온 것 자체가 버그 신호였다. IVFFlat 1.0은 플래너가 IVFFlat 인덱스를 아예 안 쓰고 Seq Scan으로 떨어져 ground truth와 우연히 똑같았던 것뿐이었다(인덱스가 있어도 안 쓰일 수 있다는 것은 pg_trgm 때도 나온 패턴이다). 해결: 질의마다 "진짜로 가까운 점"을 직접 섞어 넣어 거리 분포에 실제 구조를 만들었다.
2. **스칼라 서브쿼리가 행마다 한 번씩 평가되지 않았다.** `(SELECT array_agg(random()) FROM generate_series(1,128))::vector`를 `INSERT ... SELECT`의 타깃 리스트에 썼더니, 플래너가 이 서브쿼리를 바깥 행과 상관없다고 보고 **InitPlan으로 딱 한 번만 평가**해 재사용했다 - 5만 행이 전부 똑같은 벡터가 돼버렸다(`SELECT count(DISTINCT embedding)` = 1). HNSW로 **자기 자신을 질의해도 거리 0인 지점을 못 찾는** 증상으로 발견했다. `generate_series`끼리 실제 cross join + `GROUP BY`로 바꿔 `random()`이 행마다 진짜로 재평가되게 고쳤다.
3. **명시적으로 `id`를 넣은 `INSERT`는 `bigserial` 시퀀스를 전진시키지 않는다.** 배경 데이터를 `id`를 지정해서 넣은 뒤, "근접점 주입" `INSERT`가 `id`를 생략하고 `DEFAULT`에 맡겼더니 시퀀스가 다시 1부터 내줘서 PK 충돌이 났다. `setval()`로 직접 당겨서 해결.

## 가설 검증

**H1 - 부분적으로 채택.** 엔진별로 결과가 갈렸다 - "모두 같은 트레이드오프를 보일 것"이라는 가설은 세 엔진 중 둘에서만 맞았다.

| 엔진 | H1(파라미터↑ → recall↑·비용↑) | 근거 |
| --- | --- | --- |
| HNSW | **채택** | `ef_search` 10→200: recall 0.63→0.93(+0.30), 버퍼 495→5,060(×10.2) - 둘 다 뚜렷하게 올랐다 |
| IVFFlat | **채택** | `probes` 1→50: recall 0.54→1.00(+0.46), 버퍼 81→3,438(×42.4) - 둘 다 가장 크게 올랐다 |
| DiskANN | **기각** | `query_search_list_size` 10→200: 버퍼는 3,203→10,132(×3.2)로 올랐지만 **recall은 10에서 이미 1.000으로 200까지 변화가 없었다** - "같이 오른다"는 가설의 전제(recall에 오를 여지가 있다)가 이 조건에서는 성립하지 않았다 |

DiskANN에서 가설이 기각된 이유는 엔진이 잘못됐다기보다 **천장 효과(ceiling effect)** 다 - 가장 싼 설정에서 이미 recall이 100%라 더 오를 수가 없었다. 이것이 "DiskANN이 이 정도 규모에서는 비정상적으로 좋다"는 뜻인지, 단지 "이 규모·데이터가 DiskANN에게는 너무 쉬웠다"는 뜻인지는 이 실험만으로는 구분할 수 없다 - [실험 06](../06-recall-at-scale/)이 행 수를 300,000으로 올려 이 질문에 다시 접근한다(결론: 착시가 아니었다. 격차가 더 벌어진다).

## 해석

- 같은 "가장 저렴한 설정"끼리 비교하면 HNSW `ef_search=10`은 recall 0.63~0.65에 그쳤는데 DiskANN(`query_search_list_size=10`)은 처음부터 만점이었다. 다만 DiskANN은 그 대신 **빌드가 압도적으로 느렸다**(51~52초, HNSW의 약 14배, IVFFlat의 약 235배) - Timescale 자사 벤치마크가 "인덱스 빌드가 현재 단일 스레드 구현이라 느리다"고 인정한 것과 방향이 같다([pgvectorscale.md](../../../pgvectorscale.md) 참고).
- 버퍼 수가 커질수록 ms/질의도 거의 선형으로 늘었다 - buffer hit(전부 캐시 적중, `read=0`)인데도 CPU 비교 비용이 지배적이라는 뜻이다. `shared_buffers=512MB`에 51,000×128차원 데이터가 통째로 들어가므로 디스크 I/O 효과는 이 실험에서 분리되지 않는다.

## 한계

- 합성 데이터(균등분포 배경 + 주입된 근접점)이고, 실제 임베딩의 클러스터 구조와는 다르다. 절대적인 recall 수치보다 **파라미터에 따른 상대적 경향**으로 읽어야 한다.
- 메모리 3.8GiB·CPU 3개짜리 환경이라 절대 시간은 참고용이다. 결정적 지표(recall, 버퍼)를 우선해서 읽는다.
- DiskANN 빌드 시간은 `diskann.min_vectors_for_parallel_build = 65536`(기본값) 미만이라 병렬 빌드가 적용되지 않은 상태의 수치다 - 더 큰 규모에서는 병렬 빌드가 켜져 상대적 격차가 달라질 수 있다(실험 02에서 확인).

재현: `python3 bench.py` (환경변수 `RESULTS_DIR`로 결과 위치 변경 가능). 원본 JSON은 [results/run1.json](results/run1.json)(1차), [results/run.json](results/run.json)(2차).
