# 실험 06 — DiskANN의 recall 우위는 300,000행에서도 보이는가

PostgreSQL 16.15 / pgvector 0.8.6 / pgvectorscale 0.9.1, Docker(공유 CPU 3개, RAM 3.8GiB). [bench.py](bench.py)

## 왜 이 실험이 필요했는가

실험 01(51,000행)은 "가장 싼 설정끼리 비교하면 HNSW(`ef_search=10`)는 recall 0.63에 그쳤는데 DiskANN(`query_search_list_size=10`)은 이미 1.0으로 포화해 있었다"는 결과를 냈지만, 그 문서는 스스로 한계를 적어뒀다 - "51,000행·128차원은 DiskANN의 설계 목적(수천만 행 규모)을 시험하는 규모가 아니다. 이 규모에서는 그냥 기본 빌드 자체가 이미 충분히 철저해서 바닥을 쳤을 뿐일 수 있다." 실험 02는 규모를 키웠지만(300,000행까지) 빌드 비용·크기만 쟀지 recall은 다시 재지 않았다. 이 실험이 그 공백을 메운다 - 같은 "가장 싼 설정" 비교를 300,000행에서 다시 해서, DiskANN의 포화가 규모와 무관한 현상인지 아니면 작은 규모에서만 보이는 착시인지를 가른다.

## 가설

**H1.** 300,000행에서는 51,000행 때와 달리 DiskANN도 가장 싼 설정(`query_search_list_size=10`)에서 recall@10 < 1.0으로 떨어질 것이다 - 탐색 공간이 6배로 커졌으니 같은 탐색 폭으로는 부족해질 것이라는 예상. **H2.** 그래도 HNSW·IVFFlat의 가장 싼 설정보다는 DiskANN의 가장 싼 설정이 recall이 더 높을 것이다 - "포화까지는 아니어도 여전히 유리하다"는 더 약한 버전의 주장.

## 방법

- 배경 300,000행 + 질의 50개당 근접점 20개(실험 01과 같은 생성 방식·시드, 128차원) - 실험 02와 같은 규모를 골랐다(이미 빌드 비용을 알고 있어 예산을 잡기 쉬웠다).
- 빌드 비용이 커서(DiskANN 300,000행은 실험 02에서 약 583초) 파라미터 스윕을 **"가장 싼 값"과 "중간값" 두 개**로 줄였다: HNSW `ef_search ∈ {10,100}`, IVFFlat `probes ∈ {1,30}`(lists=300), DiskANN `query_search_list_size ∈ {10,100}`.
- 나머지(ground truth 계산, 인덱스 하나씩만 두기, buffers 측정)는 실험 01과 동일.
- 빌드 비용 때문에 **1회만 실행**한다(2회 반복이면 DiskANN 빌드만 약 20분).

## 결과

| 설정 | recall@10 | 버퍼/질의 | ms/질의 | 빌드 |
| --- | ---: | ---: | ---: | ---: |
| HNSW `ef_search=10` | **0.216** | 590.2 | 0.396 | 33.8초, 238.9MB |
| HNSW `ef_search=100` | 0.496 | 3,321.1 | 1.574 | (위와 같음) |
| IVFFlat `probes=1` | **0.286** | 111.0 | 0.195 | 1.6초, 158.1MB |
| IVFFlat `probes=30` | 0.886 | 2,679.0 | 5.964 | (위와 같음) |
| DiskANN `query_search_list_size=10` | **1.000** | 3,572.6 | 1.707 | 597.4초, 138.3MB |
| DiskANN `query_search_list_size=100` | 1.000 | 7,593.0 | 3.621 | (위와 같음) |

빌드 시간·크기는 실험 02(같은 300,000행)와 거의 정확히 일치한다(DiskANN 597.4초 vs 583.2초, 138.3MB vs 137.9MB) - 서로 다른 실행인데도 결정적 지표가 재현된다는 교차 확인이 됐다.

## 가설 검증

**H1(DiskANN도 300,000행에서는 recall<1.0으로 떨어질 것) - 기각.** `query_search_list_size=10`에서도 recall@10 = 1.000이었다 - 51,000행 때와 완전히 같다. 6배 큰 검색 공간에서도 전혀 흔들리지 않았다.

**H2(그래도 DiskANN의 가장 싼 설정이 HNSW·IVFFlat의 가장 싼 설정보다 낫다) - 채택, 그리고 격차가 더 벌어졌다.** 51,000행에서는 DiskANN(1.000)과 HNSW `ef_search=10`(0.63~0.65)의 격차가 약 0.37이었는데, 300,000행에서는 DiskANN(1.000)과 HNSW `ef_search=10`(**0.216**)의 격차가 **0.784**로 두 배 넘게 벌어졌다. IVFFlat도 같은 방향이다(`probes=1`이 0.54→0.29로 떨어졌다).

## 해석

- **실험 01의 한계로 남겼던 질문에 답이 나왔다** - DiskANN의 포화는 "51,000행이라는 작은 규모의 착시"가 아니었다. 오히려 **규모가 커질수록 DiskANN의 우위가 더 뚜렷해진다**(HNSW·IVFFlat의 "싼 설정"이 규모에 더 취약하기 때문이다). 이것은 DiskANN의 설계 의도(대규모에서 유리하다)와 방향이 일치하는, 이번 week05 작업 전체에서 가장 설계 의도에 부합하는 결과다.
- 대가는 여전히 빌드 시간이다 - 597초(약 10분) 대 HNSW 34초, IVFFlat 1.6초. "recall은 압도적으로 낫지만 빌드가 압도적으로 느리다"는 트레이드오프가 규모가 커져도 그대로 유지된다.
- HNSW를 "쓸만하게" 만들려면 `ef_search`를 올려야 하는데, 100까지 올려도(0.496) 여전히 DiskANN의 가장 싼 설정(1.000)에 한참 못 미친다 - 이 규모에서는 HNSW 튜닝만으로 DiskANN을 따라잡기 어렵다는 뜻이다. `ef_search`를 DiskANN 수준(recall 1.0)까지 올리려면 얼마가 필요한지는 이번 실험에서 보지 않았다 - 자연스러운 다음 질문이다.
- IVFFlat `probes=1`의 버퍼(111.0)가 HNSW `ef_search=10`(590.2)보다 훨씬 적은데도 recall은 비슷한 수준(0.286 vs 0.216)이다 - 같은 "가장 싼 설정"이라도 엔진마다 저렴함의 의미가 다르다.

## 한계

- 1회 실행이다(실험 01처럼 2회 반복하지 못했다) - 빌드 비용이 너무 크다(DiskANN만 10분). recall·버퍼 같은 결정적 지표는 과거 실험들에서 반복해도 ±0.02~0.04 수준으로만 흔들렸으므로 큰 폭의 결론(0.784의 격차)이 뒤집힐 가능성은 낮다고 보지만, 확인된 사실은 아니다.
- 파라미터를 2단계로만 줄였다 - 실험 01의 4단계 곡선 전체를 300,000행에서 다시 그리지는 않았다.
- 합성 데이터(균등분포 배경 + 주입된 근접점)이고, 실제 임베딩과는 분포가 다르다.
