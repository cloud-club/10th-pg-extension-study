# 실험 05 — 메모리를 아끼는 두 가지 선택: `halfvec` vs DiskANN의 SBQ 압축

PostgreSQL 16.15 / pgvector 0.8.6 / pgvectorscale 0.9.1, Docker(공유 CPU 3개, RAM 3.8GiB). [bench.py](bench.py)

## 왜 이 실험이 필요했는가

`pgvectorscale.md`(17회차)는 "대안" 절에서 pgvector의 `halfvec`(16비트 절반 정밀도)을 pgvectorscale 없이도 메모리를 줄이는 선택지로 언급했지만, DiskANN의 SBQ 압축과 **직접 비교한 적이 없었다**. 둘은 서로 다른 계층에서 메모리를 아낀다 - `halfvec`은 타입 자체(저장되는 숫자의 정밀도)를 바꾸고, SBQ는 인덱스 내부의 양자화다. "같은 recall을 유지하면서 메모리를 아끼고 싶다면 무엇을 먼저 시도해야 하는가"라는 실무 질문에 답하려면 둘을 나란히 재야 한다. `halfvec`은 pgvectorscale 설치·빌드 없이 pgvector 하나로 끝난다는 운영상 이점도 있어, 효과가 비슷하다면 `halfvec`을 먼저 권할 근거가 된다.

## 가설

**H1.** DiskANN(SBQ)이 `halfvec`보다 인덱스를 더 작게 만들 것이다(SBQ가 이진 양자화라 halfvec의 16비트보다 더 공격적으로 압축하므로). **H2.** 그 대신 `halfvec`이 DiskANN보다 recall 손실이 적을 것이다(16비트는 원본 float4의 근사치를 유지하지만 이진 양자화는 정보 손실이 더 크다). **H3.** `halfvec`은 추가 확장 설치가 필요 없고 빌드도 원본 `vector` HNSW와 비슷하게 빠를 것이다(단순 캐스팅이므로).

## 방법

- 실험 01과 같은 데이터(배경 50,000 + 질의 50개당 근접점 20개, 128차원, 같은 시드) - 세 설정을 직접 비교할 수 있도록 **같은 실행 안에서** 만든다.
- 원본 `vector` 컬럼에서 `halfvec(128)` 컬럼을 추가로 캐스팅해 만든다.
- 세 설정을 **하나씩** 인덱스를 만들고 지운 뒤 다음 것을 만든다(측정 원칙): ① `vector` + HNSW(`vector_l2_ops`), ② `halfvec` + HNSW(`halfvec_l2_ops`), ③ `vector` + DiskANN(SBQ, 기본값).
- HNSW `ef_search`와 DiskANN `query_search_list_size`는 100으로 고정(튜닝 효과가 아니라 **표현/압축 방식 자체의 효과**만 분리하려고 스윕하지 않았다).
- **ground truth는 항상 원본 float4 정밀도의 정확한 거리**로 정의한다 - 정밀도를 낮춘 쪽이 "원본 기준으로 봤을 때" 얼마나 정확한 답을 내는지가 공정한 비교라고 판단했다.

## 결과

(참고: `table_mb`는 `halfvec` 컬럼을 추가한 뒤에 측정해 실험 01·02의 "순수 vector 컬럼만 있는 테이블" 크기와 직접 비교할 수 없다 - 이 실험은 세 **인덱스끼리의** 크기·비용을 비교하는 것이 목적이라 영향 없다.)

| 설정 | 빌드 시간 | 인덱스 크기 | recall@10 | 버퍼/질의 | ms/질의 |
| --- | ---: | ---: | ---: | ---: | ---: |
| `vector`(float4) + HNSW | 3.61초 | 40.49 MB | 0.880 | 2,780.0 | 0.761 |
| `halfvec`(float2) + HNSW | 6.64초 | 27.77 MB | 0.940 | 2,740.5 | 0.816 |
| `vector`(SBQ) + DiskANN | 50.60초 | 23.45 MB | 1.000 | 6,674.6 | 2.117 |

## 가설 검증

**H1(크기: DiskANN < halfvec) - 채택.** DiskANN 23.45MB < halfvec 27.77MB < float4 40.49MB. 다만 격차는 크지 않다 - halfvec은 DiskANN 대비 18% 더 크고, float4 대비로는 이미 31% 작다. **halfvec 하나만으로도 압축 효과의 대부분(크기 감소량의 약 2/3)을 거저 얻는다.**

**H2(recall: halfvec 손실이 DiskANN보다 적을 것) - 기각, 그리고 설계 자체가 틀렸다.** 실제로는 DiskANN이 recall@10 = 1.000으로 가장 높았고 halfvec(0.940)·float4(0.880) 순이었다 - "압축이 없는 float4가 가장 정확해야 한다"는 가정부터 깨졌다. 원인은 둘 다 이 실험이 통제하지 못한 변수다: ① 실험 01에서 이미 확인했듯 DiskANN은 이 규모·데이터에서 기본 설정부터 recall이 천장(1.0)을 친다 - 압축 손실과 무관한 효과. ② HNSW는 그래프 빌드 자체가 비결정적이다(이 프로젝트가 GiST에서도 확인한 패턴) - float4와 halfvec을 **별도로 빌드**했으므로 그래프 구조가 서로 다르고, 0.88 vs 0.94라는 6%p 차이가 "정밀도 때문"인지 "그날 그 빌드의 운" 때문인지 이 설계로는 구분할 수 없다. **표현 정밀도가 recall에 미치는 영향은 이 실험으로 검증되지 않았다.**

**H3(halfvec 빌드가 float4만큼 빠를 것) - 기각.** halfvec HNSW 빌드가 오히려 **float4보다 84% 더 느렸다**(6.64초 vs 3.61초) - "단순 캐스팅이니 비슷할 것"이라는 예상이 틀렸다. 원인은 확인하지 못했다(halfvec 비교 연산자의 구현 차이일 수도, 두 빌드 사이의 일반적인 변동일 수도 있다 - 반복 측정을 하지 않아 구분 못 한다).

## 해석

- **실무 질문("메모리를 아끼려면 뭘 먼저 시도하나")에는 그래도 답이 된다.** halfvec은 추가 확장 설치 없이, pgvector 하나로 크기를 31% 줄였다. DiskANN은 그보다 더 줄였지만(42%) 격차가 크지 않고(halfvec 대비 18%p), 대신 빌드가 7.6배 느리고 질의당 버퍼가 2.4배, 지연시간이 2.6배 더 든다. **"halfvec부터 시도하고, 그래도 부족하면 DiskANN을 검토한다"는 순서가 이 실험의 수치로는 합리적이다** - 다만 recall 비교가 깨져 있으므로(H2) "recall을 희생하지 않는다"는 보장까지는 못 한다.
- DiskANN의 버퍼·지연시간이 더 큰 것은 인덱스가 더 작다는 것과 모순처럼 보이지만, 크기와 질의 비용은 다른 축이다 - `query_search_list_size=100`(기본값)이 그 규모에서 더 많은 후보를 탐색하도록 만들어져 있고, 압축된 표현을 다시 풀어(rescore) 비교하는 추가 단계도 있다(`diskann.query_rescore` 기본값 50).

## 한계

- **recall 비교가 설계상 깨졌다**(H2에서 설명) - HNSW 빌드 비결정성과 DiskANN의 천장 효과가 뒤섞여, "압축이 recall에 주는 순수한 영향"을 이 실험에서는 분리하지 못했다. 같은 그래프 구조에서 표현만 바꿔 비교하거나(가능하다면), 여러 번 빌드해 분산을 보는 설계가 필요하다 - 다음 과제로 남긴다.
- 1회 실행이다. 빌드 시간·recall 모두 반복 측정으로 변동 폭을 확인하지 못했다.
- 50,000행·128차원 규모다. halfvec과 SBQ의 격차가 더 큰 규모에서 벌어지는지 좁혀지는지는 확인하지 않았다.

재현: `python3 bench.py`. 원본 JSON은 [results/run.json](results/run.json).
