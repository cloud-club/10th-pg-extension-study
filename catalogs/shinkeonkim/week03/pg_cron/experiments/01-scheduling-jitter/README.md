# 실험 01 - 초 단위 스케줄은 실제로 얼마나 정확한가

```bash
./bench.sh          # 약 3분 (75초 x 2 phase + 빌드/기동)
./bench.sh down     # 정리만
```

## 질문

pg_cron 1.5+ 는 `'1 seconds'`처럼 1~59초 간격 스케줄을 지원한다. 웹의 `#/pg-cron/about`에서 예약 문법을 설명한다. launcher가 매초 폴링하며 조건에 맞는 잡을 트리거하므로, "1초"라고 적어도 실제 실행 간격은 정확히 1.000초가 아닐 수 있다. **실제 지터(jitter)는 얼마나 되고, 동시에 여러 잡이 돌 때 더 나빠지는가?**

## 방법

- `'1 seconds'` 로 도는 잡 하나(`probe`)가 `heartbeat` 테이블에 `now()` 타임스탬프를 기록한다.
- **baseline**: `probe` 하나만 75초간 관찰.
- **load**: `probe` + 동시에 도는 다른 1초짜리 잡 10개(`SELECT pg_sleep(0.05)`)를 75초간 관찰 - launcher 가 매초 더 많은 일을 처리해야 하는 "잡이 많은" 상황을 흉내낸다.
- 기록된 타임스탬프에 `lag() OVER (ORDER BY tick)` 을 적용해 연속된 두 실행 사이의 실제 간격(초)을 계산하고, 평균/표준편차/최소/최대와 "1.0초에서 20% 이상 벗어난 횟수"를 집계한다.
- 환경: Docker Desktop, 컨테이너 안 `nproc` = **12**. 노트북/데스크톱 1대에서 다른 프로세스와 CPU 를 공유하는 환경이다 - 격리된 벤치마크 서버가 아니다. Docker 자체의 스케줄링도 지터의 원인이 될 수 있어 pg_cron 만의 오차라고 단정할 수 없다 ([측정 경계](#분석과-측정-경계) 참고).

## 결과

과거 pg_cron 1.6.7로 기록된 1회 측정값이다. 현재 실행 이미지는 1.6.8이며 소켓 접속을 명시한다. 당시 연결 설정 전체를 표만으로 복원할 수 없으므로 현재 재실행과 동일 조건으로 취급하지 않는다:

| phase | 샘플수 | 평균(초) | 표준편차(초) | 최소(초) | 최대(초) | 1.0초 대비 20% 이상 이탈 |
| --- | --- | --- | --- | --- | --- | --- |
| baseline (probe 단독) | 72 | 1.0051 | 0.0029 | 1.0023 | 1.0158 | 0 / 72 |
| load (probe + 노이즈 10개) | 72 | 1.0054 | 0.0030 | 1.0016 | 1.0120 | 0 / 72 |

## 분석과 측정 경계

- 이 표는 성공적으로 기록된 **인접 heartbeat의 트랜잭션 시작 시각 간격**이다. 예정 시각 대비 시작 지연, SQL 소요시간, 완료 시각 오차를 직접 측정한 값이 아니다.
- 과거 두 phase의 평균 간격은 약 1.005초, 표준편차는 약 3ms였다. 편차 원인을 launcher·연결·OS 중 하나로 분리하지 않았다.
- 이 한 번의 측정에서는 노이즈 잡 10개 추가에 따른 뚜렷한 차이가 보이지 않았다. 동시 한도 이내라면 정확도가 떨어지지 않는다거나 통계적으로 차이가 없다는 결론은 낼 수 없다.
- 샘플 수는 heartbeat 행 수가 아니라 인접 간격 수여서 행 수보다 1개 적다. 실행 실패·취소가 있으면 간격 분포에도 영향을 준다. 현재 스크립트는 최소 표본 수를 확인한다.
- 단일 Docker·공유 CPU·고정 phase 순서의 짧은 실험이다. 애플리케이션이 결과를 가져가는 지연은 포함하지 않는다. 정밀한 시각 보장이 필요한 용도의 적합성은 별도로 검증해야 한다.
- 동시 한도를 낮춘 조건은 [실험 03](../03-capacity-and-serialization/)에서 다룬다. 현재 실행 점검은 `DURATION=10 ./bench.sh`를 사용하며, 75초 과거 결과를 대체하는 성능 재측정이 아니다.
