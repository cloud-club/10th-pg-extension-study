# 실험 04 — SKIP LOCKED 소비자 두 개와 오류 롤백

2026-09-15, PostgreSQL 16.15 / pg_cron **1.6.8-1.pgdg13+1**, 기본 libpq·유닉스 소켓, 동시 한도 4. [setup.sql](setup.sql)에 전체 테이블·함수 정의가 있다.

## 검증할 것

같은 jobid의 직렬화는 서로 다른 잡이 같은 업무 행을 처리하는 문제를 해결하지 않는다. 항목을 `FOR UPDATE SKIP LOCKED`로 잡고, 처리 결과 INSERT와 완료 표시를 하나의 트랜잭션에서 수행하면 두 잡을 함께 돌릴 수 있는지 검증한다.

고정 40개 항목을 만들고, 1초 주기의 서로 다른 잡 두 개가 회차당 최대 5개를 소비한다. 항목당 `pg_sleep(0.05)`를 넣어 잠금이 겹칠 기회를 만든다. 결과 테이블은 업무 ID가 PRIMARY KEY이므로 중복 INSERT를 조용히 허용하지 않는다. 완료 표시·attempts 증가도 같은 트랜잭션에 있다.

이어서 다른 잡이 `INSERT INTO fault_effects VALUES(1)` 직후 의도적으로 예외를 발생시키도록 한다. 실패 이력이 두 번 쌓일 때까지 관찰하고, 결과 테이블에 행이 남았는지 확인한다. 매 회차 같은 강제 예외가 발생했는지도 검사해, 첫 INSERT가 남아 다음 회차에 PK 오류만 난 상황과 구분한다.

## 10회 실행한 결과

| 검증 항목 | 10회 결과 |
| --- | ---: |
| 완료 항목 / 입력 항목 | 매회 40 / 40 |
| 결과 행 수 | 매회 40 |
| 항목별 커밋된 attempts 최소 / 최대 | 매회 1 / 1 |
| consumer 1 / consumer 2 처리 항목 | 매회 20 / 20 |
| 강제 예외 실패 이력 | 매회 2 |
| 실패 직전 INSERT의 잔존 행 | 매회 0 |

재현하면 `results/`에 `1.json`부터 `10.json`까지 상세 결과가 생성된다. 이 디렉터리는 Git에서 제외하며, 저장소에는 위 집계와 웹의 반복별 요약만 남긴다. 각 로컬 파일에는 모든 입력 항목의 최종 상태, 결과별 worker ID, cron 실행 이력, 정확한 환경이 있다. 처리 분배 20/20은 이번 관찰값이며 공정한 분배를 보장하는 API가 아니다.

**같은 DB 안의 결과 기록과 완료 표시가 원자적으로 커밋되도록 구성한 예제는 성공했다.** 이 검증은 pg_cron의 exactly-once 보장이나 외부 작업 큐의 대체 가능성을 증명하지 않는다. attempts는 커밋된 변경만 세므로 실패했다가 롤백된 시도는 여기에 남지 않는다. 또한 실패 잡의 두 실행은 **다음 예약 시각의 새 실행**으로, 자동 재시도 정책이 구현된 것이 아니다.

## 한계와 다음 설계

- 메일·HTTP처럼 외부에 이미 발생한 효과는 DB 트랜잭션으로 롤백할 수 없다.
- 실패를 별도 저장하지 않으면 같은 영구 실패 항목을 계속 집을 수 있다. 시도 횟수·오류 상태·지연 재시도·격리 정책은 별도 구현 대상이다.
- 이번 실험은 서버 크래시·장애 전환·네트워크 단절을 주입하지 않았다.
- SKIP LOCKED는 잠긴 행을 건너뛰므로 일반 조회의 일관된 결과 대신 큐 분산 소비에 맞는 도구다. 처리 순서의 엄격한 보장은 별도 문제다.
- 짧은 대기가 들어간 정확성 실험이므로 worker별 처리 수를 실서비스 처리량으로 환산하지 않는다.

출처: [PostgreSQL 16 SELECT locking clause](https://www.postgresql.org/docs/16/sql-select.html#SQL-FOR-UPDATE-SHARE), [Explicit Locking](https://www.postgresql.org/docs/16/explicit-locking.html).
