# 실험 01 — GiST 의 `siglen` 은 실제로 얼마나 중요한가

## 질문

[`labs/02-gin-vs-gist`](../../labs/02-gin-vs-gist) 에서 **"기본 `siglen=12` 에서는 GiST 가 GIN 보다 인덱스 버퍼를 400배 더 읽는데, `siglen=64` 로 올리면 GIN 과 같아진다"** 는 것을 봤다.

그런데 그건 5만 행 한 점에서, `siglen` 두 값만 재본 것이었다. 그래서 남은 질문:

- `siglen` 을 12부터 256까지 훑으면 **단조롭게 좋아지나, 아니면 최적점이 있나?**
- **문서 길이**에 따라 달라지나? (시그니처는 "문서 하나에서 나오는 조각 수"에 따라 포화되므로)
- 크기·빌드 시간의 대가는 얼마나 되나?

## 방법

```bash
./bench.sh          # 빌드 -> 측정 -> 정리
./bench.sh keep     # 컨테이너를 남긴다
```

- [NSMC](https://github.com/e9t/nsmc)(CC0) 말뭉치로 **길이가 다른 두 테이블**을 만든다.

  | 테이블 | 행 수 | 평균 글자 수 | 만드는 법 |
  | --- | ---: | ---: | --- |
  | `docs_short` | 200,001 | **42.7** | 말뭉치 문장 1개 |
  | `docs_long` | 200,001 | **224.0** | 말뭉치 문장 6개를 이어붙임 |

- 각 테이블에 **정답이 정확히 1행인 문자열**(`희귀한 클라우드클럽 문서 하나`)을 심는다. `LIKE '%클라우드클럽%'` 의 정답이 1행이므로, "인덱스가 후보를 1행까지 좁혔는가"를 판정할 수 있다.
- `gin_trgm_ops` 를 기준선으로 두고, `gist_trgm_ops` 를 `siglen` 12(기본)/24/48/64/128/256 으로 훑는다.
- 지표는 **인덱스 스캔이 읽은 버퍼 수**다. 시간보다 안정적이고, "시그니처가 얼마나 잘 걸렀는가"를 직접 보여준다.

### ⚠️ GIN 은 결정적이고, GiST 는 그렇지 않다

**두 번 돌려보고 알게 된 것이다.**

| | 두 실행 차이 |
| --- | --- |
| `gin_trgm_ops` 크기·버퍼 | **완전히 동일** (39.35 MB / 13 버퍼, 161.87 MB / 13 버퍼) |
| `gist` 버퍼 | **0.1 ~ 5% 흔들린다** (4,480↔4,375, 412↔432, 2,834↔2,753) |
| `gist` 크기 | 대체로 안정적이나 한 칸이 크게 튀었다 — 긴 문서 siglen=24 에서 **176.66 ↔ 195.23 MB (10%)** |

데이터 삽입 순서는 `generate_series` 값으로 고정했는데도 그렇다. **GiST 인덱스 빌드 자체가 완전히 결정적이지 않다**(페이지 분할·`picksplit` 결과가 실행마다 조금씩 달라지는 것으로 보인다). 그래서 **아래 분석은 자릿수 차이에만 기대고, 몇 % 차이는 해석하지 않는다.**

## 분석

### 1. `siglen` 을 키우면 인덱스가 **작아진다** — 직관과 반대다

| | siglen 12 → 256 |
| --- | --- |
| 짧은 문서 | 41.05 → **32.92 MB** (20% 감소) |
| 긴 문서 | 248.80 → **143.80 MB** (42% 감소) |

시그니처 하나가 12바이트에서 256바이트로 **21배 커졌는데 인덱스는 오히려 작아진다.** 두 실행 모두에서 같은 방향이고 감소폭도 자릿수가 같으므로, 이건 노이즈가 아니다.

설명은 `trgm.h` 의 `ALLISTRUE` 에 있다. GiST 리프 엔트리는 조각 배열(`ARRKEY`)을 그대로 담다가, 크면 시그니처(`SIGNKEY`)로 전환한다. 시그니처가 96비트뿐이면 **문서 하나의 조각들만으로도 비트가 거의 다 차고**, 내부 노드로 올라가며 합쳐질수록 완전히 포화되어 `ALLISTRUE` 가 된다. 그러면 그 서브트리는 필터 역할을 못 하고, 검색이 트리를 더 넓게 뒤지게 되며, **트리 구조 자체가 나빠져 페이지가 늘어난다.**

**긴 문서에서 감소폭이 두 배(20% vs 42%)인 것이 이 설명을 뒷받침한다** — 문서가 길수록 96비트가 더 빨리 포화되기 때문이다.

### 2. 버퍼는 감소하지만, 마지막 구간에서 급락한다

```
짧은 문서:  4,480 → 4,003 → 3,031 → 3,012 → 2,191 → 412      (1회차)
            4,375 → 3,973 → 3,029 → 3,003 → 2,153 → 432      (2회차)
                                                     ^^^ 128→256 에서 5배 급락
긴 문서:   31,762 → 20,956 → 16,401 → 14,611 → 11,708 → 2,834  (1회차)
           31,739 → 21,291 → 16,448 → 14,666 → 11,725 → 2,753  (2회차)
                                                        ^^^^^ 4배 급락
```

- **12 → 128 구간은 완만하다** (짧은 문서 4,480 → 2,191, 약 2배).
- **128 → 256 에서 급락한다** (2,191 → 412, 5배). 이 구간에서 비로소 시그니처가 포화를 벗어나는 것으로 보인다. **두 실행 모두 같은 자리에서 급락했다.**

> **정정**: 초기 1회 측정에서 `siglen` 48 → 64 사이에 버퍼가 3,041 → 3,118 로 **미세하게 반등**하는 것을 관찰하고 "단조 감소가 아니다"라고 적었었다. **두 번 더 돌려보니 재현되지 않았다** — 두 실행 모두 감소했다(3,031 → 3,012, 3,029 → 3,003). 그 반등은 위에서 말한 GiST 빌드 비결정성(±5%) 범위 안의 노이즈였다. **1회 측정으로 몇 % 차이를 해석하면 안 된다는 사례다.**

**"조금 올려보고 효과가 없으면 포기"하면 안 된다.** 이 데이터에서는 128까지 올려도 GIN 과 여전히 170배 차이였고, 256에서 비로소 32배까지 좁혀졌다.

### 2-b. 그런데 256 위로는 **무너진다** — 재현되는 이상값이다

`siglen` 을 512·1024 까지 늘려봤다(허용 범위는 1~2,024). **더 좋아질 것이라 예상했는데 정반대였다.**

| 짧은 문서 (42.7자) | 크기 | 인덱스 버퍼 | 빌드 |
| --- | ---: | ---: | ---: |
| siglen=256 | **32.9 MB** | **412** | 2.8s |
| **siglen=512** | 143.8 MB (4.4배) | **11,080** (27배) | 23.2s |
| siglen=1024 | 49.6 MB | 573 | 10.7s |

| 긴 문서 (224자) | 크기 | 인덱스 버퍼 | 빌드 |
| --- | ---: | ---: | ---: |
| siglen=256 | **143.9 MB** | **2,855** | 6.7s |
| **siglen=512** | **1,876 MB** (13배) | **200,071** (70배) | 92.5s |
| **siglen=1024** | **1,480 MB** (10배) | **67,213** (24배) | 99.0s |

**`siglen=512` 는 3회 실행에서 거의 그대로 재현됐다** — 긴 문서 인덱스 1,840.91 / 1,857.22 / 1,876.02 MB, 버퍼 197,274 / 197,200 / 200,071. **노이즈가 아니다.**

**문서 길이에 따라 양상이 다르다는 것이 중요하다.**

- **짧은 문서**: 512 만 무너지고 1024 는 회복된다(49.6 MB / 573 버퍼).
- **긴 문서**: **512·1024 둘 다 재앙이다**(1,876 MB / 1,480 MB). 회복이 없다.

> 처음에 짧은 문서만 보고 "512 만 이상하고 1024 는 괜찮다"고 읽을 뻔했다.
> **긴 문서를 같이 재보니 그 해석이 틀렸다** — 두 테이블을 나란히 두지 않았으면 놓쳤을 결론이다.

<sub>`siglen=1024` 의 짧은 문서 값은 47.48 / 84.48 / 49.64 MB 로 실행마다 크게 흔들린다 — GiST 빌드 비결정성(위 ⚠️ 절)이 이 구간에서 특히 심하다. **512 는 안정적으로 나쁘고, 1024 는 불안정하다.**</sub>

#### 소스에서 확인한 것

먼저, `siglen` 이 무엇에 영향을 주는지부터 정확히 해야 한다. `gtrgm_compress()` 를 보면
**리프 엔트리는 시그니처가 아니라 트라이그램 배열(`ARRKEY`) 그대로** 저장된다.

```c
/* contrib/pg_trgm/trgm_gist.c — gtrgm_compress() */
if (entry->leafkey)
{                           /* trgm */
    res = generate_trgm(VARDATA_ANY(val), VARSIZE_ANY_EXHDR(val));
    ...                     /* 시그니처로 바꾸지 않는다 */
}
```

`makesign()` 은 `gtrgm_union()`/`gtrgm_picksplit()` 에서만 불린다. 즉 **`siglen` 은 내부 노드 키의 크기만 바꾼다.**
내부 노드 키 하나는 `siglen + 5`바이트쯤이고, 8KB 페이지에 256 이면 약 30개, 512 면 약 15개가 들어간다.

#### 가설 (확인하지 못했다)

`siglen=512` 근처에 PostgreSQL 의 인덱스 튜플 압축 임계값이 있다.

```c
/* src/include/access/heaptoast.h */
/*
 * If an index value is larger than TOAST_INDEX_TARGET, we will try to
 * compress it (we can't move it out-of-line, however).
 */
#define TOAST_INDEX_TARGET		(MaxHeapTupleSize / 16)   /* ≈ 510 바이트 */
```

`siglen=512` 짜리 키(≈517바이트)는 이 임계를 **막 넘는다.** 그래서 압축이 시도되는데,
그 크기의 시그니처는 비트가 촘촘해 **pglz 로 잘 안 줄어든다.**

짧은 문서에서 `siglen=1024` 가 회복되는 것은 이 가설과 맞는다 — 같은 개수의 비트가 두 배 넓은 공간에 흩어져
0 바이트가 많아 잘 압축된다. **하지만 긴 문서에서는 1024 도 무너지므로, 이 가설만으로는 다 설명되지 않는다.**
긴 문서는 트라이그램이 많아 시그니처가 어느 크기에서도 촘촘해지기 때문으로 보이나 확인하지 않았다.

**이 설명은 임계값의 존재까지만 확인했고, 압축이 실제로 어떻게 동작했는지는 확인하지 못했다.**

**"`ALLISTRUE` 포화를 직접 관측했다" 절에서 `pageinspect` 로 직접 세어 보니, 이 구간의 크기 증가는 전부 내부 노드 폭발이었다** — 긴 문서에서 내부 노드가 18,336 → 232,992(12.7배)로 늘고 인덱스 크기도 정확히 12.7배가 된다. `ALLISTRUE` 포화는 0.1% 뿐이라 **포화 때문이 아니다.**
확인하려면 `pageinspect` 로 내부 노드 튜플의 실제 길이(`itemlen`)를 siglen 별로 비교해야 한다.

> **실무 결론은 확실하다 — `siglen` 은 클수록 좋은 값이 아니다.**
> 두 테이블 모두 **256 이 최적**이었고, 그 위로는 인덱스가 4~13배로 부풀며 검색이 24~70배 느려졌다.
> **"더 올리면 더 좋아지겠지"로 512 나 1024 를 골랐다면 재앙이었을 것이다.** 반드시 자기 데이터로 스윕해 볼 것.

### 2-c. `ALLISTRUE` 포화를 **직접 관측했다** — 흔한 설명이 생각보다 좁다

지금까지 이 실험은 "시그니처가 포화(`ALLISTRUE`)돼서 GiST 가 느리다"고 **추론만** 하고 있었다. `pageinspect` 로 인덱스 페이지를 열어 **키의 flag 바이트를 직접 세어** 확인했다.

```c
/* trgm.h — GiST 키의 실제 모양 */
typedef struct { int32 vl_len_; uint8 flag; char data[FLEXIBLE_ARRAY_MEMBER]; } TRGM;
#define ARRKEY     0x01   /* 리프 — 트라이그램 배열 그대로 */
#define SIGNKEY    0x02   /* 내부 노드 — 시그니처 */
#define ALLISTRUE  0x04   /* 시그니처가 꽉 차 비트맵을 버린 상태 */
```

**짧은 문서 (평균 42.7자)** — 리프는 모든 siglen 에서 정확히 200,001개(= 행 수)

| ---: | ---: | ---: | ---: | ---: |

| 24 | 36.61 MB | 4,631 | 0 | 0.0% |
| 48 | 33.04 MB | 4,153 | 0 | 0.0% |
| 64 | 32.39 MB | 4,054 | 0 | 0.0% |

| 256 | 32.91 MB | 4,198 | 0 | 0.0% |

| 1024 | 48.52 MB | 6,204 | 9 | 0.1% |

**긴 문서 (평균 224자)**

#### 알게 된 것 세 가지

**(1) 포화는 실재하지만 "긴 문서 + 기본 `siglen=12`" 조합에서만 일어난다.**
긴 문서에서 내부 노드의 **94.7%** 가 `ALLISTRUE` 다 — 사실상 트리 전체가 "이 아래는 전부 가능성 있음"이라 필터로서 죽어 있다. 그런데 **`siglen` 을 24 로 한 단계만 올려도 0.0% 로 사라진다.**

> 이것이 `siglen=12 → 24` 에서 버퍼가 31,763 → 21,250 으로 가장 크게 떨어지는 이유다.
> **기본값을 벗어나는 것만으로 포화 문제는 끝난다.**

**(2) 짧은 문서는 어느 `siglen` 에서도 포화하지 않는다 — 그러니 "GiST 가 느린 건 ALLISTRUE 때문"은 여기서 틀렸다.**
42.7자 문서에서는 `siglen=12` 에서도 포화율이 **0%** 인데, 그런데도 GiST 는 GIN 보다 버퍼를 **345배**(4,480 vs 13) 읽는다. **원인은 포화가 아니라 시그니처 충돌(거짓 양성)** 이다 — 96비트에 수백 개 트라이그램을 해싱하면 꽉 차지 않아도 서로 다른 문서가 비슷한 비트 패턴을 갖게 된다.

> **"ALLISTRUE 때문에 GiST 가 느리다"는 설명은 절반만 맞다.**
> 긴 문서 + 기본 siglen 에서는 맞고, 짧은 문서에서는 **한 번도 일어나지 않는다.**

**(3) `siglen=512` 의 폭증도 포화가 아니다 — 내부 노드 폭발이다.**
512 에서 포화율은 0.1~0.2% 뿐이다. 대신 **내부 노드 수가 폭발**하고, **인덱스 크기가 정확히 그 배수만큼 커진다.**

| | 내부 노드 | 배수 | 인덱스 크기 | 배수 |
| --- | ---: | ---: | ---: | ---: |
| 짧은 문서 256 → 512 | 4,198 → 18,394 | **4.38×** | 32.91 → 143.74 MB | **4.37×** |
| 긴 문서 256 → 512 | 18,336 → 232,992 | **12.71×** | 143.74 → 1,820.28 MB | **12.66×** |

**두 자리까지 일치한다.** 리프는 200,001개로 고정이므로(ARRKEY 라 `siglen` 과 무관 — 소스에서 확인한 것), 크기 증가분은 **전부 내부 노드**다.

키 하나가 커져 페이지당 개수가 주는 것(256→512 면 약 2배)만으로는 12.7배가 설명되지 않는다. **페이지 분할이 병리적으로 일어나 트리가 훨씬 깊어지는 것으로 보이나, 그 이상은 확인하지 못했다.**

### 2-d. GiST 빌드는 **실제로** 비결정적이다 — 측정 노이즈가 아니다

"삽입 순서를 고정해도 GiST 버퍼가 ±5% 흔들린다"는 것까지는 알고 있었지만, **인덱스 구조가 달라지는 것인지 측정만 흔들리는 것인지**는 몰랐다. 같은 데이터로 세 번 빌드해 구조를 직접 셌다(`docs_long`, `siglen=256`).

| 회차 | 페이지 수 | 엔트리 수 | 리프 페이지 |
| ---: | ---: | ---: | ---: |
| 1 | 18,416 | 218,353 | 17,489 |
| 2 | 18,427 | 218,364 | 17,497 |
| 3 | 18,392 | 218,330 | 17,470 |

**세 값이 전부 다르다.** 데이터도, 삽입 순서도, 설정도 같은데 **만들어진 트리 자체가 매번 다르다.** 변동폭은 약 0.2%(18,392~18,427).

> **"측정이 흔들린 것"이 아니라 "빌드 결과가 달라진 것"이다.**
> 그래서 GiST 수치는 **범위로만 적어야 하고, 몇 % 차이를 해석하면 안 된다.**
> 다만 **왜** 달라지는지는 여전히 모른다 — `gtrgm_picksplit()` 의 분할 선택이 무엇에 의존하는지 더 파봐야 한다.

### 3. 그래도 GIN 이 압도적이다

| | 인덱스 버퍼 (짧은 문서) |
| --- | ---: |
| `gin_trgm_ops` | **13 / 13** |
| `gist` siglen=256 (최선) | 412 / 432 |

**`siglen` 을 최대한 튜닝해도 GIN 의 32배다**(412~432 vs 13). 긴 문서에서는 **212~218배**(2,753~2,834 vs 13). 게다가 GIN 은 크기도 비슷하거나 작다(짧은 문서 39.35 vs 32.9 MB 로 GiST 가 근소하게 작고, 긴 문서에서는 161.87 vs 143.8 로 GiST 가 조금 작다).

> **이 결과는 [`labs/02`](../../labs/02-gin-vs-gist) 의 결론을 수정한다.** 거기서는 `siglen=64` 로 GIN 과 버퍼가 같아졌는데(3 vs 3), 그 lab 은 **문장 8개를 5만 번 반복한 데이터**였다. 어휘가 그만큼 좁으면 64바이트 시그니처로도 포화를 피할 수 있지만, 실제 말뭉치에서는 같은 `siglen=64` 가 GIN 의 **약 231배**(3,003~3,012 vs 13)다. **"64면 충분하다"는 일반화는 성립하지 않는다** — 필요한 `siglen` 은 데이터의 어휘 다양성과 문서 길이가 정한다.

> **부분 문자열 검색만 필요하다면 GiST 를 고를 이유가 없다.** `siglen` 튜닝은 **KNN(`ORDER BY <->`) 때문에 GiST 를 이미 쓰고 있는데 `LIKE` 검색도 같이 해야 하는 상황**에서 의미가 있다.

### 4. 빌드 시간: GiST 가 GIN 보다 빠르고, 긴 문서에서 격차가 커진다

| | GIN | GiST (siglen 12) |
| --- | ---: | ---: |
| 짧은 문서 | 2.45s / 2.40s | **1.70s / 1.70s** (1.4배 빠름) |
| 긴 문서 | 14.65s / 14.44s | **7.07s / 6.94s** (2.1배 빠름) |

`siglen` 을 키워도 빌드 시간은 크게 안 늘어난다(짧은 문서 1.70 → 2.76s, 긴 문서 7.07 → 6.39s 로 오히려 줄기도 했다). **빌드 비용은 `siglen` 을 올리지 않을 이유가 되지 못한다.**

## 실무 처방

```sql
-- GiST 를 쓸 거라면 (= KNN 이 필요하다면), 기본값을 그대로 두지 말 것
CREATE INDEX ... USING gist (col gist_trgm_ops(siglen=256));
```

| 상황 | 권장 |
| --- | --- |
| 부분 문자열·정규식 검색만 필요 | **GIN** (`gin_trgm_ops`). GiST 는 고려할 필요 없다 |
| `ORDER BY col <-> '...' LIMIT n` 이 필요 | GiST — **`siglen` 을 키울 것**. 짧은 텍스트는 128 이상, 긴 텍스트는 256 |
| 둘 다 필요 | 인덱스를 두 개 만드는 것을 먼저 검토 (쓰기 비용은 [`bigm-vs-trgm/experiments/02`](../../../bigm-vs-trgm/experiments/02-index-build-size-and-write) 참고) |
| PostgreSQL 13 미만 | `siglen` 을 못 바꾼다 (pg_trgm 1.5 에서 추가). 업그레이드가 곧 성능 개선이다 |

## 한계

- ~~**`siglen` 최대값까지 가보지 않았다.**~~ **512·1024 까지 재봤다** — 더 좋아질 것이라는 예상과 정반대로 **256 위로는 무너진다**("256 위로는 무너진다" 절). 2,024(최대값)는 여전히 재지 않았다.
- 검색어를 하나(`클라우드클럽`, 6글자)만 썼다. 짧은 검색어나 정규식에서는 양상이 다를 수 있다.
- **각 조건을 2회 측정했다.** GIN 은 두 실행이 완전히 같지만 **GiST 버퍼는 0.1~5%, 크기는 한 칸에서 10% 흔들린다** — 삽입 순서를 고정해도 그렇다. **"GiST 빌드는 실제로 비결정적이다" 절에서 그 원인이 '측정 노이즈'가 아니라 '빌드 결과 자체가 다름'이라는 것을 확인했다.** 몇 % 차이를 해석하지 말 것.
- **256 위 구간에서 내부 노드가 왜 폭발하는지 모른다.** 폭증 자체와 인덱스 크기가 정확히 비례한다는 것까지는 쟀지만("`ALLISTRUE` 포화를 직접 관측했다" 절), 키 크기 증가만으로는 배수가 설명되지 않는다. `TOAST_INDEX_TARGET`(≈510바이트) 압축 임계가 후보이나 확인하지 못했다.
- **GiST 빌드가 왜 비결정적인지 모른다.** 트리 구조가 실제로 매번 달라진다는 것까지는 확인했지만("GiST 빌드는 실제로 비결정적이다" 절), `gtrgm_picksplit()` 의 분할 선택이 무엇에 의존하는지는 파보지 않았다.
- **`ALLISTRUE` 포화율은 `siglen` 별 1회 측정이다.** GiST 빌드가 비결정적이므로("GiST 빌드는 실제로 비결정적이다" 절) 작은 값(0.1~3.8%)은 실행마다 흔들릴 수 있다. **94.7% 와 0.0% 처럼 자릿수가 다른 차이만 해석했다.**
- Docker 3 CPU / 4 GB 환경이다.
