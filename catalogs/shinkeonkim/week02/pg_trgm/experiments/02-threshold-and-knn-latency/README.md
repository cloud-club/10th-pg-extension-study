# 실험 02 — 유사도 임계값과 KNN 의 비용

## 질문

[`labs/03-similarity-and-knn`](../../labs/03-similarity-and-knn) 은 열 몇 행짜리 장난감 테이블에서 "이런 게 된다"를 보여줬다. 실제 규모에서 던져야 할 질문은 다르다.

1. **`pg_trgm.similarity_threshold` 를 낮추면 후보가 얼마나 폭증하나?** 어느 지점부터 인덱스가 의미를 잃나?
2. **`similarity()` 는 본문이 길어지면 무너진다**고 했는데, 실제 규모에서 `word_similarity()` 와 **재현율**이 얼마나 차이나나?
3. **KNN(`ORDER BY <->`)은 `LIMIT` 을 키울수록 얼마나 비싸지나?** 인덱스 없이 전체 정렬하는 것과 비교하면?

## 방법

```bash
./bench.sh          # 빌드 -> 측정 -> 정리
./bench.sh keep     # 컨테이너를 남긴다
```

- [NSMC](https://github.com/e9t/nsmc)(CC0) 말뭉치 200,000행 + **정답으로 삼을 변형 6건**을 심는다. 검색어는 `클라우드클럽 스터디`.

  | 심은 문서 | 글자 수 | 성격 |
  | --- | ---: | --- |
  | `클라우드클럽 스터디` | 10 | 정확히 일치 |
  | `클라으드클럽 스터디` | 10 | 오타 |
  | `클라우드 클럽 스터디` | 11 | 띄어쓰기 |
  | `클라우드클럽 스터디 모임` | 13 | 짧은 확장 |
  | `클라우드클럽 스터디 10기 참여 안내 공지입니다` | 26 | 중간 확장 |
  | `오늘 클라우드클럽 스터디 에서 인덱스 튜닝을 …` | 45 | 긴 확장 |

  **정답 6건을 `id` 로 특정한다.** 처음엔 `WHERE doc LIKE '%클라%'` 로 골라냈는데 말뭉치의 `클라스`·`클라라`·`클라이맥스` 가 수십 건 걸려들어 재현율 계산이 무의미해졌다.

- **데이터 삽입을 결정적으로 만들었다.** 처음엔 `id serial` + 순서를 지정하지 않은 `INSERT ... SELECT` 를 썼는데, 힙의 물리적 행 순서가 실행마다 달라져 **GiST KNN 버퍼가 재현되지 않았다**(`LIMIT 1` 에서 230 → 156 → 117). 지금은 `id` 를 `generate_series` 값으로 직접 주고 `ORDER BY g` 로 순서를 고정한다. 그래도 `LIMIT 1` 은 완전히 안정되지 않는다 — 아래 참고.

## 결과 1 — 임계값 스윕 (200,006행)

| `similarity_threshold` | 매치 행 수 | **인덱스 스캔이 돌려준 행** | 인덱스 버퍼 | 실행 |
| ---: | ---: | ---: | ---: | ---: |
| 0.6 | 3 | 6 | 38 | 0.31 ms |
| 0.5 | 4 | 6 | 38 | 0.37 ms |
| 0.4 | 5 | 7 | 38 | 0.35 ms |
| **0.3 (기본)** | **5** | **9** | 38 | 0.43 ms |
| 0.2 | 6 | 29 | 38 | 0.97 ms |
| 0.1 | 7 | **253** | 38 | 4.91 ms |
| **0.05** | **51** | **12,130** | 37 | **162.06 ms** |

### 분석

**(a) 0.3 → 0.05 로 낮추면 후보가 1,348배로 늘어난다** (9행 → 12,130행). 실행 시간은 **377배**(0.43 → 162 ms).

**(b) 그런데 인덱스 버퍼는 38에서 거의 변하지 않는다.** 이게 중요하다 — **비용이 늘어나는 곳은 인덱스가 아니라 힙 재확인**이다. 임계값이 낮아지면 `consistent` 가 더 많은 후보를 통과시키고, 그 후보들의 원문을 힙에서 하나씩 읽어 실제 유사도를 계산해야 한다.

> **"인덱스 버퍼는 그대로인데 실행 시간만 폭증한다"** 는 것은 튜닝 지점이 인덱스가 아니라 **임계값 자체**라는 신호다.

**(c) 0.2 아래로는 급격히 나빠진다.** 0.3 → 0.2 는 2.3배(0.43 → 0.97 ms)지만, 0.2 → 0.1 은 5배, 0.1 → 0.05 는 33배다. **"결과가 안 나오면 임계값을 낮춰보자"는 대응이 위험한 이유다** — 0.05 에서는 매치가 51건으로 늘었지만 그중 정답은 여전히 6건뿐이고, 나머지 45건은 노이즈다.

**실무 처방: 임계값을 사용자 입력으로 그대로 받지 말고 서버에서 하한(예: 0.2)을 강제할 것.** [`labs/05-fastapi-search-api`](../../labs/05-fastapi-search-api) 가 그렇게 구현되어 있다.

## 결과 2 — `similarity` vs `word_similarity` 재현율

심어둔 정답 6건의 점수:

| 문서 | 글자 수 | `similarity` | `word_similarity` | `strict_word_similarity` |
| --- | ---: | ---: | ---: | ---: |
| 클라우드클럽 스터디 | 10 | 1.0000 | 1.0000 | 1.0000 |
| 클라으드클럽 스터디 (오타) | 10 | 0.5714 | 0.5714 | 0.5714 |
| 클라우드 클럽 스터디 | 11 | 0.6923 | 0.6923 | 0.6923 |
| 클라우드클럽 스터디 모임 | 13 | 0.7857 | **1.0000** | **1.0000** |
| 클라우드클럽 스터디 10기 참여 안내 공지입니다 | 26 | **0.4074** | **1.0000** | **1.0000** |
| 오늘 클라우드클럽 스터디 에서 인덱스 튜닝을 … | 45 | **0.2500** | **1.0000** | **1.0000** |

**`similarity()` 는 문서가 길어질수록 단조 감소한다** (1.0 → 0.79 → 0.41 → 0.25). 검색어가 문서 안에 **온전히 그대로 들어있는데도** 그렇다 — 자카드 유사도의 분모에 문서 전체 길이가 들어가기 때문이다.

`word_similarity` 계열은 검색어에 가장 잘 맞는 부분 구간만 보므로 **길이와 무관하게 1.0** 이다.

### 기본 임계값에서의 재현율 (정답 6건 중)

| 연산자 | 기본 임계값 | 잡은 건수 |
| --- | ---: | ---: |
| `%` (`similarity`) | 0.3 | **5 / 6** |
| `%>` (`word_similarity`) | 0.6 | **5 / 6** |
| `%>>` (`strict_word_similarity`) | 0.5 | **6 / 6** |

- **`%` 가 놓친 1건은 가장 긴 문서**(45글자, 0.2500 < 0.3)다. **검색어가 그대로 들어있는 문서를 길다는 이유만으로 놓쳤다.**
- **`%>` 도 5건인데, 놓친 것은 다른 문서다** — 오타가 있는 `클라으드클럽 스터디`(0.5714 < 0.6). `word_similarity` 의 기본 임계값 0.6 이 `similarity` 의 0.3 보다 훨씬 엄격하기 때문이다.
- **`%>>`(strict) 가 6/6 으로 유일하게 전부 잡았다.** 임계값이 0.5 로 중간이라 두 실패 모드를 모두 피했다.

> **"길어서 놓치는 것"과 "틀려서 놓치는 것"은 다른 문제이고, 세 연산자의 기본 임계값이 각각 다르기 때문에 어느 것을 쓰느냐에 따라 놓치는 대상이 달라진다.** 긴 본문에서 짧은 검색어를 찾는다면 `%` 를 쓰면 안 된다.

<sub>피연산자 순서 주의: 인덱스를 타려면 인덱스 컬럼이 왼쪽이어야 한다 — `doc %> '검색어'`(= `'검색어' <% doc`). `doc <% '검색어'` 는 의미도 다르고 `Seq Scan` 이 된다 ([`bigm-vs-trgm/experiments/03`](../../../bigm-vs-trgm/experiments/03-operator-coverage-and-correctness)).</sub>

## 결과 3 — KNN 비용 (GiST `siglen=256`)

**네 번 측정했다** (`LIMIT 1` 이 심하게 흔들려서 반복을 늘렸다).

| 방식 | LIMIT | 버퍼 (4회 관측) | 실행 시간 |
| --- | ---: | --- | ---: |
| GiST 인덱스 정렬 | 1 | **65 / 117 / 144 / 156** ← 3.5배 범위 | 1.7 ms 수준 |
| GiST 인덱스 정렬 | 5 | 3,853 / 3,869 / 3,878 / 3,883 | 58 ms 수준 |
| GiST 인덱스 정렬 | 10 | 4,223 / 4,229 / 4,235 / 4,235 | 60 ms 수준 |
| GiST 인덱스 정렬 | 50 | 4,263 / 4,269 / 4,275 / 4,275 | 61 ms 수준 |
| GiST 인덱스 정렬 | 100 | 4,313 / 4,319 / 4,325 / 4,325 | 66 ms 수준 |
| 인덱스 없이 (전체 정렬) | 1 / 10 / 100 | 3,299 (전부 동일) | 600~620 ms |

### ⚠️ `LIMIT 1` 은 재현되지 않는다

**두 번씩 돌려보고 알게 된 것이다.** `LIMIT 5` 이상은 실행 간 편차가 0.3~0.8% 인데, **`LIMIT 1` 만 65~156 으로 3.5배 흔들린다**(처음 발행했던 230까지 넣으면 3.5배).

삽입 순서를 `generate_series` 값으로 고정해도 그렇다. **GiST 인덱스 빌드 자체가 완전히 결정적이지 않고**([`../01-gin-vs-gist-build-and-probe/`](../01-gin-vs-gist-build-and-probe) 에서도 버퍼가 ±5% 흔들렸다), 절대 페이지 수가 작을 때 그 흔들림이 상대적으로 크게 보이는 것으로 해석된다.

### 분석

**(a) `LIMIT 1` 과 `LIMIT 5` 사이에 절벽이 있다** — 버퍼 65~156 → 3,853~3,883. **배수는 25~60배로 실행마다 다르지만, 절벽이 있다는 것 자체는 네 번 모두 재현됐다.** 1건만 필요하면 시그니처가 가장 가까운 가지 위주로 따라가면 되지만, 5건을 채우려면 여러 가지를 탐색해야 하기 때문으로 보인다(이 설명은 버퍼 거동에서 추론한 것이고 직접 확인하지 않았다).

**(b) 5 이후로는 거의 평평하다** (3,853 → 4,325, 12% 증가). **`LIMIT 10` 이든 `LIMIT 100` 이든 비용이 사실상 같다** — 자동완성에서 "10건만 주자"고 아껴봐야 얻는 게 없다는 뜻이다. 이 구간은 실행 간 편차가 0.3% 라 신뢰할 수 있다.

**(c) 그래도 전체 정렬보다는 10배 빠르다** (60 vs 610 ms). 그리고 **전체 정렬은 `LIMIT` 과 무관하게 버퍼가 정확히 3,299 로 일정하다** — 20만 행 전부의 거리를 계산한 뒤 정렬해서 자르기 때문이다. 네 실행 모두 3,299 였다.

**(d) 다만 절대 성능은 좋지 않다.** `LIMIT 10` 에 60 ms 는 대화형 자동완성으로 쓰기엔 느리다. 실무에서는 후보를 먼저 좁히고(예: 카테고리·`LIKE` 접두어) 그 안에서 KNN 을 돌리는 구성이 필요하다.

## 정리

| 발견 | 실무 처방 |
| --- | --- |
| 임계값을 0.3 → 0.05 로 낮추면 실행 시간 377배 | **임계값 하한을 서버에서 강제할 것** (0.2 권장) |
| 비용은 인덱스가 아니라 힙 재확인에서 늘어난다 | 인덱스 버퍼가 그대로인데 느려지면 임계값을 의심할 것 |
| `similarity()` 는 긴 문서를 놓친다 (45글자에서 0.25) | 긴 본문 검색에는 `%>` / `%>>` 를 쓸 것 |
| 세 연산자의 기본 임계값이 다르다 (0.3 / 0.6 / 0.5) | 연산자를 바꾸면 임계값도 다시 잡을 것 |
| KNN 은 `LIMIT 1` 과 `LIMIT 5+` 사이에 절벽이 있고(25~60배), 그 뒤로는 평평하다 | `LIMIT` 을 아껴도 얻는 게 없다. 대신 **후보를 먼저 좁힐 것** |

## 한계

- 검색어 하나(`클라우드클럽 스터디`)로만 쟀다. 검색어 길이·희귀도에 따라 임계값 곡선이 달라질 수 있다.
- 정답을 6건만 심었다. 재현율(5/6, 6/6)이 표본이 작아 일반화하기 어렵다 — **읽어야 할 것은 비율이 아니라 "왜 놓쳤는가"** 다.
- **임계값 스윕과 재현율은 4회 실행 전부 완전히 동일했다**(0.3 → 매치 5건 / 인덱스 9행, 0.05 → 51건 / 12,130행; 재현율 5·5·6). GIN 경로는 결정적이다.
- **KNN 버퍼는 `LIMIT 1` 만 재현되지 않는다**(65~156). GiST 빌드 비결정성 때문이며, `LIMIT 5` 이상은 0.3~0.8% 편차로 안정적이다.
- KNN 의 `LIMIT 1` → `5` 절벽에 대한 설명("가지 하나만 따라가면 되기 때문")은 **버퍼 거동에서 추론한 것이고 직접 확인하지 않았다.**
- 시간은 머신 부하에 크게 좌우된다 — 같은 조건에서 다른 컨테이너를 동시에 돌리면 2배까지 느려지는 것을 확인했다. 자릿수 차이(0.43 ms vs 162 ms)만 해석할 것.
- GiST `siglen=256` 으로만 쟀다. 기본 `siglen=12` 였다면 KNN 도 훨씬 느렸을 것이다 ([`../01-gin-vs-gist-build-and-probe/`](../01-gin-vs-gist-build-and-probe)).
- Docker 3 CPU / 4 GB 환경이다.
