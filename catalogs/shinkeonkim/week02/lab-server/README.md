# lab-server — 브라우저에서 직접 돌려보는 실험 서버

카탈로그의 `bench.sh` 들은 **미리 정해둔 조건**을 재고 그 결과를 README 에 적어 둡니다.
여기는 반대로, **조건을 브라우저에서 바꿔가며 그 자리에서 재는** 서버입니다.

```bash
./run.sh          # 빌드 + 기동 → http://localhost:8000
./run.sh logs     # API 로그
./run.sh down     # 정리 (데이터 볼륨까지)
```

**최초 1회는 5~10분** 걸립니다 — PostgreSQL 세 버전에 `pg_bigm` 을 소스로 빌드하기 때문입니다.

## 무엇을 바꿔볼 수 있나

| 변인 | 고를 수 있는 값 |
| --- | --- |
| **검색어** | 아무 문자열 (2글자로 바꿔보는 게 이 카탈로그의 핵심입니다) |
| **패턴 모양** | `%검색어%` / `검색어%` / `%검색어` |
| **행 수** | 1만 / 10만 / 50만 / 100만 |
| **주입 비율(선택도)** | 0.01% / 0.1% / 1% / 10% |
| **PostgreSQL 버전** | 16 · 17 · 18 |
| **엔진** | 인덱스 없음 · `pg_bigm` · `pg_trgm` |

고른 값의 **모든 조합**을 잽니다(버전 × 엔진 × 패턴).

## 처음 해볼 것 — 2글자 함정

1. 기본값(`클둥이`, 10만 행, PG16, 세 엔진, 세 패턴)으로 한 번 돌립니다 → 전부 초록.
2. 검색어만 **`클둥`**(2글자)으로 바꿔 다시 돌립니다.
3. **`pg_trgm` 의 `%검색어%` 줄만 빨갛게** 바뀝니다 — 인덱스가 **테이블 전체**를 후보로 올리고,
   Recheck 이 그 99.9% 를 힙에서 버립니다. **인덱스가 없느니만 못한 상태**입니다.
4. 같은 2글자로 패턴만 **`검색어%`** 로 바꾸면 다시 초록이 됩니다.

<sub>왜 그런지 → [`web/#/start/first`](../../web/README.md) · 미리 돌려둔 전체 결과 → [`web/`](../../web/README.md)</sub>

## 구성

```
docker-compose.yml    pg16 · pg17 · pg18 · api
Dockerfile.pg         PGVER 을 받아 pg_bigm 을 소스 빌드 (PGXS)
api/
  main.py             FastAPI — 작업 등록 / 조회 / 취소 + 워커
  store.py            작업 큐 (SQLite 한 파일, 볼륨에 저장)
  bench.py            실제 측정 — 카탈로그의 bench.sh 와 같은 설계·같은 지표
  corpus.py           NSMC 말뭉치 준비 (없으면 합성으로 폴백)
  static/             UI (HTML + CSS + JS, Chart.js 는 CDN)
```

### 왜 비동기인가

100만 행에 인덱스를 새로 만들면 30초쯤 걸립니다. HTTP 요청 안에서 끝내려 하면 타임아웃이 나고,
브라우저를 닫으면 결과도 잃습니다. 그래서

- `POST /api/runs` 는 **작업을 큐에 넣고 id 만 즉시** 돌려줍니다.
- **워커 하나**가 뒤에서 순서대로 돌립니다. (둘 이상 돌리면 같은 PostgreSQL 에서
  인덱스를 동시에 만들다 CPU 경합으로 시간 지표가 오염됩니다 — 이 카탈로그가 여러 번 당한 함정입니다.)
- 끝나면 상태가 `done` 으로 바뀌고 결과가 저장됩니다. 창을 닫았다 와도 남아 있습니다.

큐는 **SQLite 한 파일**(`/data/lab.db`, 도커 볼륨)입니다. API 가 재시작되면
`running` 이던 작업은 결과가 없으므로 **다시 `pending` 으로 되돌려 재실행**합니다.

### 측정 방식은 카탈로그와 동일합니다

- **주입 행 = `<검색어> 말뭉치문장 <검색어>`** — 세 패턴이 **모두 같은 행**에 걸립니다.
  그래야 보이는 차이를 "패턴 모양 때문"이라고 말할 수 있습니다.
  나머지 행은 뒤에 ` #<id>` 가 붙어 접미어 패턴에 절대 안 걸립니다(오염 차단).
- **난수를 쓰지 않습니다.** `generate_series` 의 나머지 연산으로 주입하므로 실행마다 같습니다.
- **주 지표는 시간이 아닙니다** — 인덱스가 돌려준 후보 행 · `Rows Removed by Index Recheck` · 버퍼.
  시간은 보조로만 보여줍니다.
- 인덱스 경로를 강제합니다(`enable_seqscan=off`). "플래너가 무엇을 고르나"는 다른 질문이고,
  그건 [`pg_bigm/experiments/00`](../pg_bigm/experiments/00-explain-before-after) 에서 따로 봅니다.

### 캐시

같은 **(버전, 행 수, 검색어)** 조합은 테이블을 다시 만들지 않고,
같은 **(…, 엔진)** 은 인덱스도 다시 만들지 않습니다. 두 번째 실험부터는 훨씬 빠릅니다.
전부 지우려면 `./run.sh down`.

## API

| | |
| --- | --- |
| `GET /api/meta` | 고를 수 있는 값들 (버전·엔진·패턴·행 수) |
| `POST /api/runs` | 작업 등록 → `{"id": 1, "status": "pending"}` |
| `GET /api/runs` | 최근 작업 목록 |
| `GET /api/runs/{id}` | 상태 · 진행 · 결과 |
| `POST /api/runs/{id}/cancel` | **아직 시작 안 한 것만** 취소 (돌던 것은 안 끊습니다 — 인덱스 생성 중에 끊으면 DB 에 찌꺼기가 남습니다) |

```bash
curl -s localhost:8000/api/runs -X POST -H 'content-type: application/json' \
  -d '{"keyword":"클둥","rows":100000,"versions":["16"],"engines":["none","bigm","trgm"],"patterns":["infix"]}'
```

## 만들면서 걸린 함정 셋

이 서버를 만들며 실제로 겪은 것들입니다. 카탈로그의 다른 문서와 같은 이유로 남겨 둡니다 —
**같은 걸 만들 사람이 또 밟을 자리**라서요.

### 1. 인덱스 두 개가 공존하면 플래너가 하나를 골라버린다

캐시를 살리려고 `_bigm` 과 `_trgm` 인덱스를 둘 다 두고 엔진만 바꿔가며 쟀습니다.
그랬더니 **`pg_trgm` 의 2글자 `%검색어%` 가 정상으로 나왔습니다** — 무너져야 맞는 칸인데요.
플래너가 `bigm` 인덱스를 골라 쓰고 있었습니다.

카탈로그의 `bench.sh` 들이 *"인덱스는 한 번에 하나만 존재하게 한다"* 고 적어둔 이유가 이것인데,
캐시를 넣으면서 그 원칙을 깨뜨린 겁니다.

**고친 방법**: 트랜잭션 안에서 **상대 인덱스를 `DROP` 하고 재고 `ROLLBACK`** 합니다.
롤백하면 인덱스가 되살아나므로 캐시는 그대로 남습니다.
그리고 플랜에서 `Index Scan on ...` 을 읽어 **의도한 인덱스를 정말 썼는지 확인**하고,
아니면 결과 표에 ⚠ 로 표시합니다 — **가정하지 않고 검증합니다.**

### 2. 재시작하면 끊긴 백엔드의 `CREATE INDEX` 가 서버에서 계속 돈다

API 를 재시작해도 큐가 남는지 확인하려고 실험 도중에 재시작했더니,
재큐된 작업이 `UniqueViolation: ... docs_1000000_..._bigm already exists` 로 죽었습니다.

클라이언트가 끊겨도 **PostgreSQL 은 그 `CREATE INDEX` 를 끝까지 돌립니다.**
새 작업이 `to_regclass` 로 확인할 때는 아직 커밋 전이라 "없음"이 나오고,
그래서 또 만들다 먼저 끝난 쪽과 부딪힌 겁니다.

**고친 방법**: 이름으로 `pg_advisory_lock` 을 걸어 줄을 세우고, `CREATE INDEX IF NOT EXISTS` 로 만듭니다.
덤으로 **`indisvalid` 를 확인**해서 중간에 끊겨 생긴 무효 인덱스면 지우고 다시 만듭니다
(무효 인덱스는 플래너가 안 쓰는데 `to_regclass` 에는 잡힙니다).

### 3. psycopg3 는 "여러 문장 + 파라미터" 를 한 번에 못 보낸다

`SET enable_seqscan=off; EXPLAIN ... LIKE %s` 를 한 번에 보냈다가 전부 실패했습니다.
문장을 나눠 보내야 합니다.

## 한계

- **PostgreSQL 19beta1 은 뺐습니다.** `pg_bigm` 1.2 가 빌드되지 않습니다 —
  PG19 에서 전역 `database_ctype_is_c` 가 `pg_locale_t` 의 필드로 옮겨지고 `char2wchar()` 가
  헤더에서 빠졌습니다. 근거: [`experiments/07`](../bigm-vs-trgm/experiments/07-postgres-version-matrix).
- **시간은 랩톱 부하에 좌우됩니다.** 자릿수 차이만 해석하세요. 결정적 지표(후보 행·Recheck·버퍼)는 재현됩니다.
- 워커가 하나라 **작업이 밀리면 줄을 섭니다.** 의도한 것입니다(동시 실행은 시간 지표를 망칩니다).
- 컨테이너 세 개가 항상 떠 있으므로 **메모리를 3~4GB 씁니다.** 다 쓰면 `./run.sh down`.
- **작업 취소는 아직 시작 안 한 것만 됩니다.** 돌고 있는 것을 끊으면 위 함정 2번이 그대로 재현되므로
  일부러 막아 뒀습니다. 급하면 `./run.sh down` 으로 전부 지우세요.
- 처음 띄우면 지난 실험 기록이 남아 있을 수 있습니다(개발 중 돌린 것들). `./run.sh down` 이면 사라집니다.
