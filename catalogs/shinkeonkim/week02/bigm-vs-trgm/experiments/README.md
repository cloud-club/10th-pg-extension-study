# bigm vs trgm — 정량 비교 실험

`pg_bigm`과 `pg_trgm`의 검색 성능, 인덱스 크기, 연산자 지원을 비교한 실험입니다.

> **처음이라면** — 두 확장이 뭔지부터 알아야 이 표가 읽힙니다.
> [`web/#/start/first`](../../../web/README.md) 를 먼저 보세요(3분, 용어 사전 포함).
> 아주 짧게: **글자를 두 개씩 잘라 색인하면 `pg_bigm`, 세 개씩 자르면 `pg_trgm`** 입니다.

각 실험은 독립된 Docker 컨테이너에서 **`./bench.sh` 하나로 재현**되고, README 에는 **실제로 그 스크립트를 돌려 나온 값만** 적혀 있습니다.

## 주요 결과

- **단어 경계가 없는 두 글자 부분 문자열 패턴은 pg_trgm에서 후보를 충분히 줄이지 못할 수 있습니다.** 다른 길이와 패턴의 결과는 아래 실험에서 비교합니다.
- **실험 05의 3글자 이상 검색 조건에서는 실행시간 차이가 뚜렷하지 않았습니다.** 20회 중앙값으로 비교한 결과입니다.
- **한국어는 2글자 검색어가 흔합니다**(`서울`·`배송`·`결제`). 그래서 `pg_bigm` 이야기가 나오는 겁니다.

## 실험 목록

| 실험 | 질문 | 핵심 발견 |
| --- | --- | --- |
| [01-keyword-length-and-selectivity](01-keyword-length-and-selectivity) | "한국어면 pg_bigm 이 낫다"는 말은 **어느 칸에서** 참인가 | **2글자 검색어에서 trgm 은 인덱스가 테이블 전체(200,000행)를 후보로 올린다** — bigm 은 정답 200행. 인덱스 버퍼 4 vs 5,097. 그런데 **3글자 이상에서는 trgm 이 오히려 버퍼를 덜 읽는다** |
| [02-index-build-size-and-write](02-index-build-size-and-write) | 그 인덱스를 유지하는 비용은 | **"2-gram 이라 조각이 많아서 인덱스가 크다"는 설명은 틀렸다** — 생 조각 수는 857k vs 793k 로 오히려 비슷하고, 인덱스는 bigm 이 25% 작다. **유니크 조각 수(50,398 vs 121,558)에서 차이가 난다**. `FASTUPDATE` 를 끄면 쓰기가 3~4배 느려진다 |
| [03-operator-coverage-and-correctness](03-operator-coverage-and-correctness) | 애초에 **되는가**, 그리고 결과가 같은가 | pg_bigm 은 `LIKE`/`=%` 만 된다(`ILIKE`·정규식·`=` 는 Seq Scan). 같은 오탈자에 bigm 이 **1.1~3.5배 높은 점수**를 준다 — `클둥이`↔`클동이` 는 trgm 기본 임계값에 아예 못 미친다 |
| [04-storage-overhead-at-scale](04-storage-overhead-at-scale) | 인덱스가 **저장 용량을 얼마나 늘리나** (10만~500만 행) | **배수가 규모에 따라 떨어진다** — trgm 이 10만 행에서 테이블의 2.48배인데 500만 행에서는 1.01배. 유니크 엔트리(엔트리 트리)가 고정비이고 포스팅 리스트는 압축되기 때문. `btree` 는 0.98배로 일정해 이 구조를 뒷받침한다 |
| [05-pattern-and-length](05-pattern-and-length) | 순수 `LIKE` vs bigm vs trgm, **길이·패턴별로** | 인덱스는 **50~110배** 빠르고 **검색어 길이(3~20글자)는 거의 무관**하다. 그런데 **trgm 의 2글자에서만 `%X%` 와 `X%` 가 535~580배 차이**난다(797 ms vs 1.49 ms). 인덱스 없이도 `X%` 가 `%X%` 보다 3~4배 빠르다. **후속 확인에서 “bigm 이 3글자 이상에서 1.5~2배 빠르다”는 주장을 철회했다** — 20회 중앙값으로 재니 노이즈였다 |
| [06-fulltext-vs-ngram](06-fulltext-vs-ngram) | 코어 내장 전문검색(`tsvector`/`tsquery`)으로 대신할 수 있나 | **`tsvector` 는 익스텐션이 아니라 코어다** — 층위가 다르다. 사전 없는 `simple` 설정에서 한국어 재현율이 **평균 20.4%**(`:*` 접두어로 84.6%). `영화가` 안의 `화가` 는 원리상 못 찾는다(25,366 vs 445). 대신 **구절 검색·`ts_rank` 는 전문검색만 된다**.<br>**⚠️ 속도 표는 인덱스 세 개를 동시에 둔 채 재서 한 번 틀렸다** — 다시 재고 "쓴 인덱스" 열을 넣었다 |
| [07-postgres-version-matrix](07-postgres-version-matrix) | 이 결론이 **PostgreSQL 16 한정인가** | **아니다.** 16·17·18 에서 인덱스 스캔 행·recheck·버퍼·인덱스 크기가 **한 자리도 다르지 않다** — `GIN_SEARCH_MODE_ALL` 은 버전으로 해결되는 문제가 아니다. 유일한 차이는 **인덱스 빌드 시간**(PG18 에서 약 2배 빠름, 원인 미확인). 그리고 **pg_bigm 1.2 는 PG19beta1 에서 빌드되지 않는다**. **다섯 축(질의·길이×패턴 45칸·길이×선택도·인덱스 5종 크기·전문검색 재현율)을 버전마다 다시 재서**, 시각화 차트 **11개**에 버전 선택기를 붙였다 |
| [08-space-and-punctuation](08-space-and-punctuation) | **공백이 든 문장은 조각이 어떻게 만들어지나** | **공백은 조각 안에 들어간다 — 낱말 경계 표시 자리로만.** `ab cd` 에 `"b "` 는 있지만 `b c` 는 없고, 공백을 빼면 `bc` 가 생긴다. **갈리는 지점은 공백이 아니라 구두점이다** — `pg_bigm` 은 `192.168.0.1` 을 한 낱말로 보고 점을 조각에 남기고, `pg_trgm` 은 네 낱말로 쪼개고 버린다(공식 문서의 `foo|bar` 예시와 글자까지 일치). **공백이 든 패턴은 양쪽 다 인덱스를 탄다**(`%드 클%`), 다만 trgm 은 후보가 4배 넓다. `% X %` 우회는 동작하지만 **정답이 250 → 203행으로 바뀐다** |
| [09-ilike-and-case-insensitive](09-ilike-and-case-insensitive) | **`ILIKE` 는 실제로 빨라지나** (플래너를 강제하지 않고) | **pg_trgm 의 `ILIKE` 는 38배 빠르고 recheck 이 0 이다** — `IGNORECASE` 로 조각이 이미 소문자라 인덱스에게 자연스러운 연산이 `ILIKE` 쪽이다. **거꾸로 대소문자를 구분하는 `LIKE` 에서는 후보 600행 중 400을 버린다.** **pg_bigm 은 한글 검색어에서도 `ILIKE` 한 글자에 51배를 잃는다**(1.05 → 54.00 ms) — 대소문자 개념이 없는 문자인데도 연산자 클래스에 `~~*` 가 없어 인덱스가 통째로 무시된다. 대안은 **`lower()` 함수 인덱스**(trgm 네이티브 `ILIKE` 와 동등하고 인덱스는 35 MB 로 더 작다). **코어 전문검색(tsvector + GIN)과도 견줬다** — 정답이 같아지도록 만든 구간에서는 tsvector 가 2~3배 빠르지만, 낱말 *가운데* 를 찾으면(`%우드클럽%`) **가장 빠르면서 0행을 돌려준다** |
| [10-one-char-and-partial-match](10-one-char-and-partial-match) | **1글자 검색은 왜 pg_bigm 에서만 되나** | 카탈로그가 계속 써온 "엔트리가 정렬돼 있어서" 라는 설명을 **처음으로 재봤다.** `pg_opclass` 를 직접 읽으니 `gin_bigm_ops` 는 엔트리 타입이 **`text`**(opckeytype=0)이고 **`gin_bigm_compare_partial` 이 등록돼 있는데**, `gin_trgm_ops` 는 **`int4`**(CRC32)라 **comparePartial 이 아예 없다** — 해시는 정렬 순서가 원문과 무관해 연속 구간이 존재하지 않으니 등록할 수가 없다. 실측: 1글자 `%ퟛ%` 에서 bigm 은 **버퍼 3,225 → 404, 27.1 → 1.42 ms**(후보 400 = 정답 400, recheck 0), trgm 은 Seq Scan. **3글자에서 두 확장이 만난다** |

각 실험 디렉터리에서 `./bench.sh` 로 재현할 수 있다 (`./bench.sh down` 으로 정리, `./bench.sh keep` 으로 컨테이너 유지).

## 측정 원칙

이 실험들은 [`../../pg_bigm/experiments/02`](../../pg_bigm/experiments/02-query-latency-at-scale) 가 **3회차에서 결과가 재현되지 않아 핵심 주장을 철회**했던 경험에서 나온 원칙을 따른다.

1. **벽시계 시간 대신 결정적 지표를 먼저 본다** — `EXPLAIN (ANALYZE, BUFFERS)` 의 `Bitmap Index Scan` 이 돌려준 `actual rows`, `Rows Removed by Index Recheck`, `Buffers: shared hit`. 같은 데이터·같은 쿼리면 실행마다 거의 변하지 않는다. 시간은 보조 지표로만 적는다.
2. **난수 대신 `id` 나머지로 주입한다** — 검색어를 정확히 정해진 비율에, 항상 같은 물리적 배치로 심는다.
3. **선택도를 통제 변수로 명시한다** — 실제 매치 비율을 먼저 재서 기록한다.
4. **정답 행 수를 미리 알고 설계한다** — "인덱스가 후보를 정답까지 좁혔는가"를 판정하려면 정답을 알아야 한다.
5. **인덱스는 한 번에 하나만 존재하게 한다.** 둘 다 있으면 **플래너가 하나를 골라버려** 비교가 안 된다.
   실제로 [`06`](06-fulltext-vs-ngram) 이 이걸 어겨 "bigm 으로 쟀다"는 줄이 trgm 을 타고 있었다.
   그래서 지금은 **플랜에서 `Index Scan on` 을 읽어 쓴 인덱스를 기록**한다 — 가정하지 않고 확인한다.
6. **설명되지 않는 값은 설명되지 않는다고 적는다** — [`../../pg_bigm/experiments/00`](../../pg_bigm/experiments/00-explain-before-after) 의 "미해결" 절이 그 예다.

## 데이터

- **말뭉치**: [NSMC](https://github.com/e9t/nsmc)(Naver Sentiment Movie Corpus, **CC0**) 199,993문장. [Korpora](https://github.com/ko-nlp/Korpora) 가 소개하는 한국어 말뭉치 중 라이선스·접근성 때문에 골랐다.
- 말뭉치 파일은 **커밋하지 않는다.** `bench.sh` 가 실행 시점에 `.corpus/` 로 내려받아 캐시하고, 네트워크가 없으면 합성 데이터로 폴백한다(그 경우 결과에 "합성 데이터"라고 표시된다).
- **검색어**: 스터디 공용 예시 문자열(`클라우드클럽` / `클둥이` · `김신건` / `클클` · `코아` · `신건` · `신컨`). 길이가 2·3·6글자로 고르게 분포하고, `신건`/`신컨` 과 `김신건`/`김신컨` 은 한 글자만 다른 오탈자 쌍이다. 자세한 배경은 [`web/#/meta/method`](../../../web/README.md).

## 한 장 결론

```
                   검색어 길이
              2글자          3글자 이상
           ┌──────────────┬─────────────────┐
   높음    │ bigm 압도적   │  동률            │
 (희귀)    │ 버퍼 1,274배  │ (trgm 근소 우위)  │
 선택도    ├──────────────┼─────────────────┤
   낮음    │ bigm 이 낫지만│  둘 다 힙 읽기가  │
 (흔함)    │ 둘 다 느리다  │  병목            │
           └──────────────┴─────────────────┘
```

**이 실험에서는 왼쪽 위의 짧은 검색어 조건에서 pg_bigm의 이점이 뚜렷했다.** 다만 한국어에서는 그 칸에 자주 들어가고(2글자 검색어가 흔하다), 거기서의 격차가 압도적이다. 반대로 **환경 제약**(수퍼유저 권한 없음, 매니지드 미지원)이 있으면 `pg_trgm` 에 패턴 우회를 얹는 선택도 실용적이다.
