# 실험 05 — 검색어 길이 × 패턴 모양 × 엔진 (100만 행)

## 질문

세 가지를 한 격자에서 답한다.

1. **순수 `LIKE`(인덱스 없음) 대비 `pg_trgm`·`pg_bigm` 이 얼마나 빠른가?**
2. **검색어가 길어지면**(3 → 5 → 10 → 20글자) 달라지나?
3. **`%문자열%` 와 `문자열%`, `%문자열` 은 차이가 없나?**

## 방법

```bash
./bench.sh                              # 100만 행 (약 45초)
ROWS=100000 INJECT_MOD=200 ./bench.sh   # 빠르게 훑기
```

### 선택도를 고정하고 길이·패턴만 변수로 남기는 설계

길이를 바꾸면 보통 매치되는 행 수도 바뀌어서, "길이 때문인지 선택도 때문인지" 구분이 안 된다. 그래서 **정답 행 수를 45개 칸 전부에서 같게** 만들었다.

20글자짜리 기준 문자열을 하나 정하고(`BASE20 = 클둥이클라우드클럽십기스터디참여클둥클럽`), 주입 행을 이렇게 만든다.

```
<BASE20> <말뭉치 문장> <BASE20>
```

그러면 길이 `L` 에 대해 세 패턴이 **모두 같은 행 집합**에 걸린다.

| 패턴 | 만드는 법 | 왜 걸리나 |
| --- | --- | --- |
| 부분 일치 | `'%' || left(BASE20, L) || '%'` | 앞쪽 `BASE20` 안에 있다 |
| 접두어 | `left(BASE20, L) || '%'` | 문서가 `BASE20` 으로 **시작**한다 |
| 접미어 | `'%' || right(BASE20, L)` | 문서가 `BASE20` 으로 **끝난다** |

나머지 행은 뒤에 ` #<id>` 가 붙으므로 접미어 패턴에 절대 안 걸린다(오염 차단). **실제로 45개 칸 전부 정답 500행으로 측정됐다** — 설계대로 동작했다는 확인이다.

- 데이터: [NSMC](https://github.com/e9t/nsmc)(CC0) 말뭉치 100만 행, 주입 500행(0.05%).
- 엔진 3종: **인덱스 없음**(`enable_indexscan/bitmapscan=off` 로 순수 시퀀셜 스캔 강제) / `gin_bigm_ops` / `gin_trgm_ops`.
- **2회 실행해 재현성을 확인했다** — 정답 행수·플랜·인덱스 스캔 행·recheck 은 45칸 전부 동일, 버퍼만 0.5% 미만 흔들렸다.

## 분석

### 1. 인덱스는 50~110배 빠르다 — 단, 한 칸만 빼고

3글자 이상 부분 문자열 검색 기준:

| | 시간 | 버퍼 | 인덱스 없음 대비 |
| --- | ---: | ---: | ---: |
| 인덱스 없음 | 57.7 ~ 69.7 ms | 16,187 | 1× |
| `gin_trgm_ops` | 1.06 ~ 1.32 ms | ~510 | **약 50배** |
| `gin_bigm_ops` | 0.54 ~ 0.80 ms | ~510 | **약 90~110배** |

**버퍼는 32배 줄고 시간은 50~110배 줄었다.** 버퍼 감소보다 시간 감소가 큰 것은, 시퀀셜 스캔이 100만 행 각각에 대해 문자열 매칭 CPU 를 쓰기 때문이다 — 인덱스는 그 일을 500행으로 줄인다.

### 2. **검색어 길이는 거의 영향이 없다** — 2글자만 빼고

이게 다소 의외였다. 3 → 20글자로 **7배** 길어져도:

- `bigm`: 0.54 → 0.80 ms (1.5배)
- `trgm`: 1.06 → 1.27 ms (1.2배)
- 인덱스 없음: 59.9 → 57.7 ms (변화 없음)

**긴 검색어가 더 느려지지 않는다.** 조각이 많아지면 GIN 이 AND 해야 할 포스팅 리스트가 늘지만, 각 리스트가 더 희귀해져 짧아지므로 상쇄된다. 버퍼가 504 → 560 으로 11% 만 느는 것이 그 증거다.

> **"검색어가 길면 느려지지 않을까" 는 걱정하지 않아도 된다. 걱정할 것은 짧을 때다.**

### 3. **패턴 모양이 결정적인 순간은 딱 하나 — trgm 의 2글자다**

| trgm, 2글자 | 인덱스 스캔 행 | recheck 제거 | 버퍼 | 시간 |
| --- | ---: | ---: | ---: | ---: |
| `%클둥%` | **1,000,000** | 999,500 | 50,328 | **797 ms** |
| `클둥%` | 500 | 0 | 511 | **1.49 ms** |
| `%클럽` | 590 | 90 | 594 | **1.37 ms** |

**같은 2글자인데 패턴 모양만 바꾸면 535~580배 빨라진다.**

이유는 패딩이다. `pg_trgm` 은 단어 앞에 공백 2개, 뒤에 1개를 붙여 3글자씩 자르는데, **`%` 로 감싸면 그 자리에 무슨 글자가 올지 모르므로 패딩을 못 붙인다** → 2글자로는 트라이그램을 하나도 못 만든다 → `GIN_SEARCH_MODE_ALL`(인덱스 전체 스캔).

반면 `클둥%` 는 앞쪽 경계가 문자열 시작이므로 `LPADDING 2` 가 붙어 `"  클둥"` 이 되고, `%클럽` 은 뒤쪽이 끝이므로 `RPADDING 1` 이 붙어 `"클럽 "` 이 된다. 둘 다 3글자를 채워 정상 동작한다.

```c
/* trgm_op.c - get_wildcard_part() 주석 */
 * If the found word is bounded by non-word characters or string boundaries
 * then this function will include corresponding padding spaces into buf.
```

**3글자부터는 패턴 모양이 무의미하다** — 이미 트라이그램을 만들 수 있으므로. 표를 보면 3~20글자에서 세 패턴이 전부 1.0~1.4 ms 로 같다.

**`pg_bigm` 은 어느 칸에서도 이 문제가 없다.** 2글자로도 온전한 bigram 을 만들 수 있어서다.

### 4. 인덱스 없이도 `X%` 가 3~4배 빠르다 — 인덱스와 무관한 효과

`none` 엔진에서 접두어가 눈에 띄게 빠르다(15.4~21.0 ms vs 57~79 ms). **인덱스를 전혀 안 쓰는데도 그렇다.**

버퍼는 16,187 로 세 패턴 모두 같다 — **I/O 는 동일하고 CPU 만 다르다.** `LIKE 'X%'` 는 각 행의 첫 글자만 비교하면 대부분 바로 탈락시킬 수 있지만, `LIKE '%X%'` 는 문자열의 **모든 시작 위치**에서 매칭을 시도해야 한다. 평균 35글자 문서면 최대 35배의 비교가 필요하다.

> **인덱스를 못 붙이는 상황(임시 쿼리, 매니지드 제약)에서도 검색을 접두어로 바꿀 수 있다면 그것만으로 3~4배를 얻는다.**

<sub>**정정** — 처음에는 접미어(`%X`)가 부분 일치보다 조금 느린 것을 두고 "끝에서부터 비교해야 해서"라고 추정했다. **재보니 틀렸다.** 아래 §6 참고.</sub>

### 5. ~~bigm 이 trgm 보다 1.5~2배 빠르다 (3글자 이상)~~ — **철회했다**

| 길이 | bigm | trgm | 비 |
| ---: | ---: | ---: | ---: |
| 3 | 0.54 ms | 1.06 ms | 2.0배 |
| 5 | 0.64 ms | 1.13 ms | 1.8배 |
| 10 | 0.63 ms | 1.32 ms | 2.1배 |
| 20 | 0.80 ms | 1.27 ms | 1.6배 |

> **⚠️ 이 절의 주장은 철회한다.** 위 표는 각 칸 **1회 측정**이다. 같은 질의를 20회씩 다시 돌려보니
> **두 인덱스의 범위가 완전히 겹쳤고, 3글자에서는 오히려 trgm 이 빨랐다.** 자세한 것은 아래 **§6-2**.
> 표는 "1회 측정으로 2배 차이를 해석하면 안 된다"는 사례로 남겨 둔다.

버퍼가 거의 같은데(약 510) 시간만 2배 차이나는 것이 애초에 이상한 신호였다 — **버퍼가 같으면 읽는 페이지가 같다는 뜻이므로, 시간 차이를 만들 구조적 이유가 없다.** 그때 의심했어야 했다.

<sub>[`01`](../01-keyword-length-and-selectivity) 에서는 3글자 이상일 때 trgm 이 버퍼를 **덜** 읽었다(4 vs 7). 버퍼 쪽은 재현되는 지표이므로 그 관찰은 그대로 유효하다.</sub>

## 6. 후속 확인 — 추정으로 남겨뒀던 두 가지를 재봤다

이 README 는 §4 와 §5 에서 "추정이며 확인하지 않았다"고 적어둔 것이 둘 있었다. 둘 다 재봤고, **둘 다 원래 설명이 틀렸다.**

### 6-1. 접미어가 느린 이유 — "접미어라서"가 아니라 "매치가 뒤에 있어서"다

원래 설명은 "끝에서부터 비교해야 하니까"였다. 그런데 더 단순한 설명이 있다 — **`LIKE` 매처는 첫 매치에서 멈춘다.**

```
주입 행 = <BASE20> <문장> <BASE20>
  '%X%'  →  맨 앞의 BASE20 에서 바로 걸린다   → 매처가 첫 위치에서 성공하고 끝난다
  '%X'   →  맨 뒤에서만 걸린다                → 매처가 문자열 끝까지 가야 한다
```

가르려면 **매치를 뒤에만 둔 부분 일치**를 만들어 비교하면 된다. 앞쪽 `BASE20` 을 뺀 테이블(`docs_tail`)을 따로 만들어 같은 `%X%` 를 재봤다.

| 테이블 | 패턴 | 매치 위치 | 시간 |
| --- | --- | --- | ---: |
| `docs` | `%클둥이클라%` (부분 일치) | **맨 앞** | **131.9 ms** |
| `docs` | `%여클둥클럽` (접미어) | 맨 뒤 | 142.0 ms |
| `docs_tail` | `%여클둥클럽%` (**부분 일치**) | **맨 뒤** | **152.5 ms** |
| `docs_tail` | `%여클둥클럽` (접미어) | 맨 뒤 | 139.8 ms |

**매치를 끝으로 옮기자 부분 일치가 접미어보다 오히려 느려졌다**(152.5 vs 139.8). 즉 순서가 뒤집힌다.

> **결론: "접미어가 느리다"는 패턴 모양의 성질이 아니라 이 실험 데이터의 성질이었다.**
> 주입 행이 `<BASE20> 문장 <BASE20>` 이라 부분 일치는 첫 글자에서 바로 끝나고 접미어는 끝까지 가야 했던 것뿐이다.
> **§4 의 "`X%` 가 `%X%` 보다 3~4배 빠르다"는 결론은 그대로 유효하다**(접두어는 각 행의 첫 글자만 보고 탈락시킬 수 있으므로, 매치 위치와 무관한 진짜 차이다).

### 6-2. "3글자 이상에서 bigm 이 1.5~2배 빠르다" — **철회한다. 노이즈였다.**

버퍼가 거의 같은데(약 510) 시간만 2배 차이나는 것이 이상해서, **같은 질의를 20회씩 돌려 중앙값과 범위**를 봤다.

| 길이 | bigm 중앙값 (min~max) | trgm 중앙값 (min~max) | 비 |
| ---: | --- | --- | ---: |
| 3 | 0.536 ms (0.512~4.552) | **0.486 ms** (0.468~1.935) | **0.91×** |
| 5 | **0.555 ms** (0.539~0.876) | 0.663 ms (0.612~3.579) | 1.19× |
| 20 | 0.898 ms (0.833~1.161) | 0.902 ms (0.831~2.494) | 1.00× |

- **min~max 범위가 서로 완전히 겹친다.**
- 3글자에서는 오히려 **trgm 이 빨랐다**(0.486 vs 0.536).
- 20글자에서는 사실상 동일(1.00×).

> **원래 표의 "1.6~2.1배"는 각 칸 1회 측정이었고, 그 차이는 재현되지 않는다.**
> 그래서 §5 의 "bigm 이 trgm 보다 빠르다"는 주장을 **철회한다** — 3글자 이상에서 두 인덱스는
> **시간으로 구분되지 않는다.** 버퍼가 같으니 당연한 결과이기도 하다.

**이것이 이 카탈로그의 측정 원칙 7번("결론을 적기 전에 두 번 돌린다")이 또 한 번 값을 한 자리다.**
1회 측정으로 2배 차이를 해석하면 안 된다 — 이 데이터에서는 같은 질의의 max/min 이 **9배**까지 벌어졌다.

## 정리 — 질문별 답

| 질문 | 답 |
| --- | --- |
| **순수 LIKE 대비 얼마나 빠른가?** | 3글자 이상 `%X%` 기준 **50~110배** (57~70 ms → 0.5~1.3 ms) |
| **검색어가 길어지면?** | **거의 영향 없다.** 3 → 20글자에서 1.2~1.5배만 느려진다 |
| **`%X%` vs `X%` vs `%X` 차이는?** | **trgm 의 2글자에서만 결정적**(535~580배). 3글자 이상은 무의미. **bigm 은 어느 칸에서도 무관** |
| **3글자 이상에서 bigm 이 더 빠른가?** | **아니다.** 20회 중앙값으로 다시 재니 두 인덱스가 구분되지 않는다(§6-2에서 철회) |
| **인덱스 없이도 패턴이 중요한가?** | 그렇다. `X%` 가 `%X%` 보다 **3~4배** 빠르다 (CPU 비교 횟수 차이) |

**실무 규칙 세 줄**

1. **3글자 이상이면 어느 쪽이든 쓰면 된다** — 인덱스만 있으면 50배 이상이고, 길이는 신경 쓸 필요 없다.
2. **2글자 이하가 흔하면 `pg_bigm`** — `pg_trgm` 은 같은 조건에서 인덱스가 없느니만 못하다(797 ms).
3. **`pg_trgm` 을 써야 한다면 패턴을 바꿔라** — `'키워드%'` 나 `'% 키워드 %'` 로 감싸면 2글자도 500배 이상 빨라진다.

## 한계

- **정답 500행(0.05%) 한 점에서만 쟀다.** 선택도가 낮으면(매치가 많으면) 인덱스 이득이 줄어드는데, 그 축은 [`01`](../01-keyword-length-and-selectivity) 에서 따로 본다.
- **검색어가 하나(`BASE20` 의 접두/접미)뿐이다.** 실제 서비스의 다양한 검색어 분포를 대표하지 않는다.
- 100만 행 한 규모다. 규모별 추세는 [`04`](../04-storage-overhead-at-scale)(용량)와 [`pg_bigm/experiments/00`](../../../pg_bigm/experiments/00-explain-before-after)(플랜 전환점) 참고.
- 시간은 각 칸 1회 측정이다. **결정적 지표(행 수·플랜·recheck)는 2회 실행에서 45칸 전부 동일**했고 버퍼는 0.5% 미만 흔들렸지만, 시간은 머신 부하에 좌우된다 — 자릿수 차이만 해석할 것.
