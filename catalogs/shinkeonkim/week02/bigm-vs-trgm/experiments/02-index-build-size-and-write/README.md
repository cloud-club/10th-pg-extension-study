# 실험 02 — 빌드 비용 · 인덱스 크기 · 쓰기 처리량, 그리고 조각 통계

## 질문

[`01`](../01-keyword-length-and-selectivity) 이 "검색이 얼마나 빠른가"를 쟀다면, 여기는 **그 인덱스를 유지하는 비용**을 잰다.

1. 같은 데이터에서 `gin_bigm_ops` / `gin_trgm_ops` / `gist_trgm_ops` / `tsvector` 인덱스는 각각 얼마나 크고 얼마나 오래 걸려 만들어지나?
2. **유니크 조각(GIN 엔트리) 수는 몇 개인가?** "2-gram 은 조각이 더 많아서 인덱스가 크다"는 흔한 설명이 실제로 맞나?
3. 인덱스가 있으면 `INSERT` 가 얼마나 느려지나? `FASTUPDATE` 는 얼마나 도움이 되나?
4. **영문 데이터에서는 결론이 뒤집히나?** (이 카탈로그의 결론이 한국어에 편향된 건 아닌가)

## 방법

```bash
./bench.sh          # 빌드 -> 측정 -> 정리
./bench.sh keep     # 컨테이너를 남긴다
```

- **한국어**: [NSMC](https://github.com/e9t/nsmc)(CC0) 말뭉치 200,000행.
- **영문 대조군**: [Project Gutenberg](https://www.gutenberg.org) 3권(*Pride and Prejudice* · *Moby Dick* · *Frankenstein*, 퍼블릭 도메인)을 문장 단위로 자른 12,848문장을 순환 참조해 200,000행. **이전 판은 어휘 12개 조합의 합성 데이터였는데, 유니크 조각 수를 6.6배나 적게(294 vs 1,937) 만들고 있었다** — 아래 §한계 참고.
- 빌드는 **2회 반복**해 재현성을 확인했다.
- `INSERT` 는 인덱스를 먼저 만든 뒤 10,000행을 넣는 방식으로 잰다(운영에서 벌어지는 순서 그대로).

## 결과 1 — 조각(GIN 엔트리) 통계

표본 20,000행. **`show_bigm()`/`show_trgm()` 은 문서별로 중복을 제거한 조각을 돌려주므로**(`generate_bigm`/`generate_trgm` 이 마지막에 `qsort` + unique 를 돌린다), 중복 제거 **전** 개수는 문자열 길이로 따로 계산해 함께 낸다.

| 데이터 | n-gram | 중복 제거 전 | 중복 제거 후 | 중복 손실률 | **유니크 조각 수** | 조각당 평균 출현 |
| --- | --- | ---: | ---: | ---: | ---: | ---: |
| 한국어 (NSMC) | 2-gram | 857,069 | 791,053 | 7.7% | **50,398** | 15.7 |
| 한국어 (NSMC) | 3-gram | 793,062 | 763,255 | 3.8% | **121,558** | 6.3 |
| 영문 (Gutenberg) | 2-gram | 2,040,850 | 1,493,519 | **26.8%** | **1,937** | 771.0 |
| 영문 (Gutenberg) | 3-gram | 1,954,587 | 1,623,740 | 16.9% | **5,909** | 274.8 |

### 분석

**(a) 조각 "생산량" 자체는 두 확장이 비슷하다 — 다만 이유가 흔한 설명과 다르다.**

길이 `k` 인 단어 하나에서 나오는 조각 수는 **패딩까지 세면 양쪽 다 `k+1`** 이다.

```
2-gram: (k + 앞패딩 1 + 뒤패딩 1) - 2 + 1 = k + 1
3-gram: (k + 앞패딩 2 + 뒤패딩 1) - 3 + 1 = k + 1
```

그래서 **"2-gram 이라 조각이 더 많아서 인덱스가 크다"는 설명은 틀렸다.** 다만 두 확장은 **"단어"를 나누는 기준이 다르다.**

```c
/* pg_bigm: bigm_op.c */   #define iswordchr(c)        (!t_isspace(c))              /* 공백만 구분자 */
/* pg_trgm: trgm.h    */   #define ISWORDCHR(c, len)   (t_isalnum_with_len(c, len)) /* 영숫자가 아니면 전부 구분자 */
```

`pg_trgm` 은 구두점에서도 단어를 끊으므로 단어 개수가 늘고, 대신 구두점 글자 자체는 버린다. 이 두 효과가 상쇄되어 **생 조각 수가 한국어 857,069 vs 793,062(8% 차이), 영문 2,040,850 vs 1,954,587(4.4% 차이)** 로 비슷하게 나온다.

**(b) 중복 제거가 영문 2-gram 을 크게 깎는다 — 이게 표를 읽을 때 가장 헷갈리는 지점이다.**

| | 중복 손실률 |
| --- | ---: |
| 영문 2-gram | **20.4%** |
| 영문 3-gram | 6.1% |
| 한국어 2-gram | 7.7% |
| 한국어 3-gram | 3.8% |

영문 한 문장 안에 `th`·`he`·`in`·`er` 같은 2-gram 이 여러 번 나오므로 문서별 중복 제거에서 대량으로 사라진다. 3-gram 은 훨씬 덜 반복된다.

**그래서 중복 제거 후 숫자만 보면 영문에서 3-gram 이 2-gram 보다 16% 많아 보이는데(1,378,858 vs 1,184,708), 이건 "3-gram 이 조각을 더 만든다"는 뜻이 아니라 "2-gram 이 중복으로 더 많이 지워졌다"는 뜻이다.** 생 조각 수는 오히려 2-gram 이 근소하게 많다.

**(c) 진짜 차이는 유니크 조각 수다.** 한국어에서 3-gram 이 2.4배 많고(121,558 vs 50,398), 그래서 조각 하나가 2.4배 더 희귀하다(평균 출현 6.3회 vs 15.7회). **포스팅 리스트가 짧다 = 검색할 때 읽을 페이지가 적다** — [`01`](../01-keyword-length-and-selectivity) 에서 3글자 이상 검색어일 때 trgm 이 버퍼를 덜 읽은 이유가 이것이다.

**(d) 영문에서는 격차가 극단적이다.** 실제 영문 산문에서도 2-gram 유니크 조각이 **1,937개** 뿐이고, 조각 하나가 평균 **771행**에 나타난다 — **필터로서 거의 쓸모가 없다.** 3-gram 은 5,909개(평균 274.8행)로 **3배 낫다.**

한국어와 나란히 놓으면 차이가 분명하다.

| | 유니크 조각 (2-gram) | 조각당 평균 출현 |
| --- | ---: | ---: |
| 한국어 (NSMC) | **50,398** | 15.7행 |
| 영문 (Gutenberg) | **1,937** | **771.0행** |

**같은 2-gram 인데 한국어 조각이 26배 다양하고, 49배 희귀하다.** 음절 문자 체계라 알파벳이 크기 때문이다(한글 음절 11,172자 vs 영문 26자). **"한국어면 2-gram 으로 충분하다"의 진짜 근거가 이것이다** — 자세한 것은 [`web/#/pg-bigm/korean`](../../../../web/README.md).

> **한글은 음절이 11,172자라 2-gram 만으로도 조합 공간이 충분히 크다.** 영문에서 2-gram 이 무너지는 이유가 한국어에는 적용되지 않는다 — 이게 `pg_bigm` 이 CJK 를 겨냥해 만들어진 근본 이유다. 개념 설명은 [`web/#/foundations/ngram`](../../../../web/README.md).

## 결과 2 — 빌드 시간과 인덱스 크기 (200,000행, 2회 반복)

PostgreSQL 16 / pg_bigm 1.2 / pg_trgm 1.6 · Docker (3 CPU / 4 GB)

| 데이터 | 인덱스 | 빌드 (1회 / 2회) | 크기 (1회 / 2회) |
| --- | --- | ---: | ---: |
| 한국어 | `gin_bigm_ops` | 2.56s / 2.64s | **29.17 / 29.17 MB** |
| 한국어 | `gin_trgm_ops` | 2.45s / 2.62s | 39.03 / 39.03 MB |
| 한국어 | `gist_trgm_ops` (siglen 12) | **1.74s / 1.87s** | 41.00 / 41.08 MB |
| 한국어 | `gist_trgm_ops(siglen=64)` | 1.80s / 1.86s | 32.45 / 32.49 MB |
| 한국어 | `gin (to_tsvector('simple', doc))` | 1.81s / 2.00s | 35.05 / 35.05 MB |
| 영문 | `gin_bigm_ops` | 1.39s / 1.41s | **16.24 / 16.24 MB** |
| 영문 | `gin_trgm_ops` | 1.44s / 1.46s | 19.88 / 19.88 MB |

<sub>**GIN 인덱스 크기는 두 실행이 완전히 같고, GiST 만 미세하게 흔들린다**(41.00 vs 41.08). GiST 는 삽입 순서에 따라 페이지 분할이 달라지기 때문이다. 빌드 시간은 Docker 3 CPU 공유 환경이라 절대값에 노이즈가 있다.</sub>

### 분석

**(a) `pg_bigm` 인덱스가 한국어에서 25%, 영문에서 18% 작다.** 유니크 엔트리가 적으니 엔트리 트리가 작고, 포스팅 리스트가 뭉쳐 있어 압축이 잘 된다. **크기 면에서는 bigm 이 유리하다.**

<sub>이 결과는 [`pg_bigm/experiments/01`](../../../pg_bigm/experiments/01-index-build-time-and-size-vs-pg_trgm) 이 "차이는 5~13% 수준"이라고 적은 것과 다르다. 그 실험은 어휘 15문장짜리 합성 데이터를 썼는데, 반복도가 극단적으로 높으면 두 인덱스 모두 유니크 조각이 적어져 격차가 줄어든다. **실제 말뭉치에서는 25% 로 벌어진다** — 합성 데이터가 결론을 바꿀 수 있다는 사례다.</sub>

**(b) 빌드 시간은 GIN 두 종류가 사실상 동률이다** (2.56 vs 2.45, 2.64 vs 2.62 — 회차 간 편차가 두 인덱스 간 차이와 비슷하다). "어느 쪽이 빠르다"고 말할 근거가 없다.

**(c) GiST 가 GIN 보다 빌드는 빠르다** (1.74s vs 2.45s). 시그니처를 비트맵에 OR 로 합치기만 하면 되기 때문이다. 다만 [`01`](../01-keyword-length-and-selectivity) 과 [`pg_trgm/experiments/01`](../../../pg_trgm/experiments/01-gin-vs-gist-build-and-probe) 에서 봤듯 **검색은 훨씬 느리다.**

**(d) `siglen=64` 가 기본(12)보다 인덱스를 작게 만든다** (32.45 vs 41.00 MB). 직관과 반대인데, 기본 96비트 시그니처가 이 데이터에서 포화되어 `ALLISTRUE` 로 접히고 트리 구조가 나빠지기 때문으로 보인다. **크기와 검색 성능이 동시에 좋아지므로, 긴 텍스트를 GiST 로 인덱싱한다면 `siglen` 을 올리는 게 거의 항상 이득이다** ([`pg_trgm/experiments/01`](../../../pg_trgm/experiments/01-gin-vs-gist-build-and-probe) 에서 12~256 을 스윕했다).

**(e) `tsvector` 가 GIN n-gram 보다 빠르게 빌드된다** (1.81s vs 2.45s). 문서 하나에서 나오는 어휘소가 n-gram 조각보다 훨씬 적기 때문이다. 크기(35.05 MB)는 중간인데, **한국어는 조사가 붙은 형태가 전부 별개 어휘소가 되어 유니크 어휘소가 많아지기 때문**이다. 재현율 문제는 [`web/#/fulltext/tsvector`](../../../../web/README.md) 참고.

## 결과 3 — INSERT 처리량 (10,000행)

| 인덱스 | 소요 | 행당 | 인덱스 없음 대비 |
| --- | ---: | ---: | ---: |
| 인덱스 없음 | 0.06s | 6.0 µs | 1.0× |
| `gist_trgm_ops` | 0.14s | 14.0 µs | 2.3× |
| `gin_bigm_ops` | 0.18s | 18.0 µs | 3.0× |
| `gin_trgm_ops` | 0.19s | 19.0 µs | 3.2× |
| `gin_trgm_ops` **FASTUPDATE=off** | 0.55s | 55.0 µs | **9.2×** |
| `gin_bigm_ops` **FASTUPDATE=off** | 0.64s | 64.0 µs | **10.7×** |

### 분석

**(a) 두 GIN 인덱스의 쓰기 비용은 사실상 같다** (18 vs 19 µs). 인덱스 선택이 쓰기 성능을 좌우하지 않는다.

**(b) `FASTUPDATE` 를 끄면 쓰기가 3배 느려진다.** 이게 이 실험에서 가장 실무적인 숫자다. `FASTUPDATE`(GIN 기본 on)는 새 항목을 pending list 에 몰아뒀다가 나중에 본 인덱스로 합치는데, 끄면 매 INSERT 마다 엔트리 트리를 직접 갱신해야 한다.

**트레이드오프는 이렇다.**

| | `FASTUPDATE=on` (기본) | `FASTUPDATE=off` |
| --- | --- | --- |
| 쓰기 | **3배 빠르다** | 느리다 |
| 읽기 | pending list 를 매번 훑어야 해서 느려질 수 있다 | 일정하다 |
| 관측 | `pg_gin_pending_stats()` 로 pending list 크기 확인 | 해당 없음 |

**쓰기가 많으면 기본값(on)을 유지하고, 읽기 위주 + 지연 시간이 일정해야 하면 off 를 고려한다.** `pg_gin_pending_stats()` 는 `pg_bigm` 이 제공하지만 **모든 GIN 인덱스에 쓸 수 있는 범용 함수**라, `pg_trgm` 인덱스를 볼 때도 그대로 쓸 수 있다.

**(c) GiST 가 쓰기는 가장 싸다** (14 µs). 시그니처에 비트만 세우면 되기 때문이다.

## 정리

| 비용 항목 | 승자 | 격차 |
| --- | --- | --- |
| 인덱스 크기 (한국어) | **bigm** | 25% 작다 |
| 인덱스 크기 (영문) | **bigm** | 18% 작다 |
| 빌드 시간 (GIN 끼리) | 동률 | 측정 노이즈 수준 |
| 빌드 시간 (전체) | GiST / tsvector | GIN 대비 1.3~1.4배 빠르다 |
| INSERT 처리량 | 동률 | 18 vs 19 µs |
| 조각 선택도 | **trgm** | 조각 하나가 2.4배 희귀 |

**유지 비용만 놓고 보면 `pg_bigm` 이 근소하게 유리하거나 동률이다.** 선택 기준은 여전히 [`01`](../01-keyword-length-and-selectivity) 의 검색어 길이 축이고, 이 실험은 "쓰기·저장 비용 때문에 망설일 이유는 없다"는 것을 확인해준다.

## 한계

- ~~**영문은 합성 데이터다.**~~ **고쳤다.** Project Gutenberg 3권의 실제 산문으로 바꿔 다시 쟀다. 이전 합성 데이터와 얼마나 달랐는지 기록해 둔다.

  | | 합성 (어휘 12개) | 실제 (Gutenberg) | 배수 |
  | --- | ---: | ---: | ---: |
  | 2-gram 유니크 조각 | 294 | **1,937** | **6.6배** |
  | 3-gram 유니크 조각 | 1,497 | **5,909** | **3.9배** |
  | 2-gram 조각당 출현 | 4,029.6행 | **771.0행** | 1/5.2 |

  **방향(영문 2-gram 은 선택도가 나쁘다)은 그대로였지만 배수가 크게 틀렸다.** 합성 데이터는 "얼마나 나쁜가"를 과장한다.
- Gutenberg 텍스트에는 라이선스 안내문 같은 정형 문장이 섞여 있다. 전체의 1% 미만이라 무시했지만, 완전히 걸러내지는 않았다.
- **재현성 확보를 위해 데이터 생성을 두 번 고쳤다.** 처음엔 `docs_ko` 의 id 를 `serial` 로, `docs_en` 을 `setseed()+random()` 으로 만들었는데, 둘 다 실행 계획에 따라 결과가 달라져 조각 통계가 재현되지 않았다(영문 1,184,708 → 1,202,729). 지금은 둘 다 `generate_series` 값의 나머지 연산으로 완전히 결정적이며, **두 번 연속 실행이 바이트 단위로 동일한 것을 확인했다.**
- 200,000행 한 규모만 봤다.
- 빌드 시간은 2회 반복이지만 Docker 3 CPU 공유 환경이라 절대값에 노이즈가 있다. 회차 간 편차(2.45 → 2.62)가 두 GIN 인덱스 간 차이와 비슷하다는 점이 그 증거다. **다른 컨테이너를 동시에 돌리면 2배까지 느려지는 것도 확인했다** — 절대 시간을 인용하지 말 것.
- `INSERT` 는 1회 측정이다. 다만 `FASTUPDATE` on/off 의 3~4배 차이는 노이즈로 설명되지 않는다.
- pending list 가 실제로 얼마나 쌓였는지(`pg_gin_pending_stats()`)는 재지 않았다. INSERT 직후 상태와 VACUUM 이후 상태를 비교하면 더 정확한 그림이 나올 것이다.
- `tsvector` 는 인덱스 크기만 쟀고, **`tsvector` 컬럼 자체의 저장 비용은 포함되지 않았다.**
