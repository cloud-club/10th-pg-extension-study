# 실험 01 — 키워드 길이 × 선택도: bigm 과 trgm 은 정확히 어디서 갈리는가

## 질문

**"한국어면 `pg_bigm` 이 낫다"는 말은 어느 칸에서 참인가?**

두 확장을 비교한 자료는 많지만 대부분 "2-gram 이라 짧은 키워드에 강하다"는 정성적 서술에서 멈춘다. 이 실험은 **검색어 길이**와 **선택도**를 두 축으로 놓고, 각 칸에서 두 인덱스가 실제로 무엇을 하는지 잰다.

## 방법

```bash
./bench.sh          # 빌드 -> 측정 -> 정리
./bench.sh keep     # 컨테이너를 남긴다
```

### 시간 대신 결정적 지표를 본다

이 카탈로그의 [`pg_bigm/experiments/02`](../../../pg_bigm/experiments/02-query-latency-at-scale) 는 실행 시간을 쟀다가 **3회차에서 결과가 재현되지 않아 핵심 주장을 철회**해야 했다. 컨테이너에서 CPU 를 공유하면 벽시계 시간은 쉽게 흔들린다.

그래서 이 실험의 주 지표는 `EXPLAIN (ANALYZE, BUFFERS)` 에서 나오는 **결정적인 값 세 개**다.

| 지표 | 의미 |
| --- | --- |
| **인덱스 스캔이 돌려준 행** | 인덱스가 후보를 얼마나 좁혔나. **전체 행 수와 같으면 `GIN_SEARCH_MODE_ALL`**(인덱스 전체 스캔) 상태다 |
| **Rows Removed by Index Recheck** | 힙에서 원문을 확인해 버린 행. 크면 인덱스가 제 역할을 못 한 것이다 |
| **인덱스 스캔 버퍼** | 인덱스를 읽느라 실제로 만진 페이지 수 |

실행 시간도 함께 적지만 **참고용**이다. 위 세 값은 같은 데이터·같은 쿼리면 실행마다 거의 변하지 않는다.

### 데이터

- **말뭉치**: [NSMC](https://github.com/e9t/nsmc)(Naver Sentiment Movie Corpus, **CC0**) 199,993문장. [Korpora](https://github.com/ko-nlp/Korpora) 가 소개하는 한국어 말뭉치 중 라이선스·접근성 때문에 골랐다. `bench.sh` 가 실행 시점에 내려받아 `.corpus/` 에 캐시한다(커밋하지 않는다).
- **규모**: 200,000행.
- **검색어**: 스터디 공용 예시 문자열을 **`id` 나머지로 정확한 비율에 주입**한다(`random()` 을 쓰지 않으므로 실행마다 같은 비율·같은 물리적 배치가 나온다).

  | 검색어 | 글자 수 | 주입 | 의도 |
  | --- | :-: | --- | --- |
  | `클라우드클럽` | 6 | 0.1% | 긴 검색어 — 둘 다 잘 되는 대조군 |
  | `클둥이` · `김신건` | 3 | 각 0.1% | **3-gram 이 조각을 만들 수 있는 최소 길이** |
  | `클클` · `신컨` | 2 | 각 0.1% | **3-gram 이 조각을 못 만드는 길이 — 이 실험의 초점** |
  | `코아` | 2 | 30% | 2글자 + **낮은 선택도** |
  | `클둥일`·`클둥오`·`클둥삼`·`클둥사` | 3 | 1% / 5% / 10% / 30% | **선택도 축** — 길이를 3글자로 고정하고 선택도만 변수로 둔다 |

  <sub>선택도 축의 검색어는 **서로의 부분 문자열이 되면 안 된다.** 처음에 4글자 `클둥이오` 를 썼다가 `클둥이` 의 정답 행수가 200 → 10,200 으로 오염됐다. 전부 3글자 `클둥+X` 로 통일해 고쳤다.</sub>

- 인덱스는 **한 번에 하나만** 존재하게 한다(둘 다 있으면 플래너가 하나만 골라 비교가 안 된다). 인덱스 생성 후 `VACUUM ANALYZE` 를 돌려 죽은 튜플이 후보 수를 부풀리지 않게 한다.
- 인덱스 경로를 보기 위해 `enable_seqscan = off` 를 건다. **"플래너가 무엇을 고르나"는 다른 질문**이고, 그건 [`pg_bigm/experiments/00`](../../../pg_bigm/experiments/00-explain-before-after) 에서 따로 잰다.

## 분석

### 1. 3글자 이상에서는 두 확장이 사실상 동률이다 — 오히려 trgm 이 버퍼를 덜 읽는다

`클라우드클럽`(6글자), `클둥이`·`김신건`(3글자) 세 칸 모두 **양쪽 다 정답 200행을 정확히 집어낸다.** 그리고 **인덱스 버퍼는 trgm 쪽이 더 적다**(4 vs 7, 13 vs 16).

이유는 선택도다. 3-gram 은 조각 하나가 더 희귀해서 포스팅 리스트가 짧고, 그만큼 읽을 페이지가 적다. **"pg_bigm 이 무조건 낫다"는 말은 틀렸다** — 검색어가 충분히 길면 trgm 이 근소하게 유리하다.

<sub>`김신건` 의 trgm 이 208행을 돌려주고 8행을 Recheck 로 버린 것은, 해싱된 트라이그램이 겹치거나(3바이트로 눌러 담기 때문) 말뭉치에 우연히 부분 겹침이 있어서다. 실무상 무시할 수준이다.</sub>

### 2. 2글자에서 완전히 뒤집힌다 — 그것도 "조금"이 아니다

`클클`, `신컨` 두 칸이 이 실험의 결론이다.

| | bigm | trgm | 배수 |
| --- | ---: | ---: | ---: |
| 인덱스 스캔이 돌려준 행 | **200** (= 정답) | **200,000** (= 테이블 전체) | 1,000배 |
| Recheck 로 버린 행 | 0 | **199,800** | — |
| 인덱스 버퍼 | **4** | **5,097** | 1,274배 |
| 실행 시간 | 0.52 ms | 231.57 ms | **약 445배** |

**trgm 쪽 `인덱스 스캔이 돌려준 행 = 200,000` 이 테이블 전체 행 수와 정확히 같다.** 이게 `GIN_SEARCH_MODE_ALL` 의 지문이다 — 조각을 하나도 못 뽑아서 인덱스 엔트리를 전부 읽고, 모든 행을 후보로 올린 뒤, 힙에서 199,800행을 하나씩 걸러냈다.

**"인덱스를 안 탄다"가 아니라 "인덱스를 통째로 읽고 나서 시퀀셜 스캔까지 한다"** 는 뜻이다. 인덱스가 없느니만 못하다.

원인은 소스 한 줄이다.

```c
/* pg_trgm: trgm_op.c - make_trigrams() */
    if (charlen < 3)
        return tptr;              /* 포기 → GIN_SEARCH_MODE_ALL */

/* pg_bigm: bigm_op.c - make_bigrams() */
    if (charlen < 2) {
        compact_bigram(bptr, ptr, pg_mblen(str));
        bptr->pmatch = true;      /* 부분 일치로 전환 */
        ...
    }
```

### 3. 선택도가 낮으면 bigm 도 느려진다 — 다만 성격이 다르다

`코아`(2글자, 30% 매치) 칸을 보면:

- **bigm**: 인덱스가 정확히 60,006행(= 정답)을 돌려준다. Recheck 0. **인덱스는 완벽히 작동했다.** 그런데도 13.78 ms 가 걸렸다 — 6만 행의 힙을 실제로 읽어야 하기 때문이다.
- **trgm**: 여전히 전체 인덱스 스캔(200,000행)이고 257.81 ms.

**bigm 이 느려진 것은 "인덱스가 실패해서"가 아니라 "정답이 원래 많아서"다.** 이 구분이 중요하다 — 전자는 인덱스나 검색어를 바꿔 고칠 수 있지만, 후자는 인덱스로 고칠 수 없다(6만 행을 돌려줘야 하는 쿼리는 어떤 인덱스로도 빨라지지 않는다).

### 3-b. 선택도를 300배 흔들어도 순위가 바뀌지 않는다

길이 축만 보면 "3글자 이상이면 동률"까지밖에 말할 수 없다. 그래서 **길이를 3글자로 고정하고 선택도만 0.1% → 30% 로 300배** 흔들어 봤다.

```
인덱스 버퍼      선택도  0.1%    1%     5%    10%    30%
  pg_bigm                 31     24     33     31     32      ← 거의 일정
  pg_trgm                  4      4      7      8     14      ← 선택도에 비례해 는다
                          ^^^ 모든 칸에서 trgm 이 적다
```

**세 가지가 보인다.**

1. **모든 선택도에서 trgm 이 버퍼를 덜 읽는다.** 3글자 조각이 2.4배 희귀해 포스팅 리스트가 짧기 때문이다 — 선택도를 바꿔도 이 성질은 안 바뀐다.
2. **bigm 의 버퍼는 선택도와 거의 무관하다**(24~33). 2-gram 조각이 원래 흔해서, 정답이 200행이든 6만 행이든 읽는 포스팅 양이 비슷하다.
3. **그런데 실행 시간의 순위는 칸마다 뒤집힌다** — 5%에서는 trgm 이 2배 빠르고, 10%·30%에서는 bigm 이 근소하게 빠르다. **선택도가 높아지면 병목이 인덱스가 아니라 힙 읽기로 옮겨가기 때문이다.** 두 인덱스가 같은 힙을 같은 만큼 읽으므로 시간이 수렴하고, 남는 차이는 노이즈 수준이다.

> **결론: "bigm 이 유리한 칸"을 정하는 것은 선택도가 아니라 길이다.**
> 선택도는 "인덱스가 이득인가"를 정할 뿐(30%면 무엇을 써도 힙 읽기가 병목),
> "어느 인덱스가 나은가"는 바꾸지 않는다.

<sub>표에서 `클둥이` 의 bigm 후보가 200 → 257(recheck 57)로 늘어난 것도 이 실험에서 새로 생긴 현상이다. 선택도 축 검색어(`클둥일`·`클둥오`…)를 추가하면서 `␣클`·`클둥` 조각을 가진 행이 늘었고, **조각은 다 있지만 `클둥이` 라는 연속 문자열은 없는 행**이 57개 생겼다. **Recheck 이 정확히 그 57행을 걸러냈다** — 손실 인덱스의 교과서적인 예다([`web/#/foundations/recheck`](../../../../web/README.md)).</sub>

### 4. 격자로 정리하면

```
                   검색어 길이
              2글자          3글자 이상
           ┌──────────────┬──────────────┐
   높음    │ bigm 압도적   │  동률        │
 (희귀)    │ (버퍼 1,274배)│ (trgm 근소 우위)│
 선택도    ├──────────────┼──────────────┤
   낮음    │ bigm 이 낫지만│  둘 다 힙 읽기가│
 (흔함)    │ 둘 다 느리다  │  병목         │
           └──────────────┴──────────────┘
```

**`pg_bigm` 을 쓸 진짜 이유는 왼쪽 위 칸 하나다.** 그리고 한국어에서는 그 칸에 자주 들어간다 — `클클`, `코아`, `신건` 같은 2글자 검색어가 흔하기 때문이다.

### 5. trgm 을 쓸 수밖에 없다면

`pg_trgm` 은 contrib 이고 `trusted` 라 수퍼유저가 아니어도 설치되는 반면, `pg_bigm` 은 소스 빌드 + 수퍼유저가 필요하다. 그래서 **환경 때문에 trgm 을 써야 하는 경우**가 실제로 있다. 그때는 패턴을 바꿔 패딩을 얻어내는 우회가 있다.

| 패턴 | trgm 인덱스가 돌려주는 행 |
| --- | ---: |
| `LIKE '%클클%'` | 200,000 (전체) |
| `LIKE '클클%'` (앞 고정) | 소수 |
| `LIKE '% 클클 %'` (공백으로 감쌈) | 소수 |

의미가 "부분 일치 → 접두어/단어 일치"로 바뀌는 것을 받아들일 수 있는지가 판단 기준이다. 실측은 [`../../../pg_trgm/labs/04-regex-and-tuning/`](../../../pg_trgm/labs/04-regex-and-tuning) 에 있다.

## 한계

- **한국어 말뭉치 하나(NSMC, 영화 리뷰)로만 쟀다.** 리뷰 텍스트는 구어체가 많아 어휘 분포가 특수하다. 영문 데이터에서는 결론이 달라지는데, 그건 [`../02-index-build-size-and-write/`](../02-index-build-size-and-write) 에서 영문 대조군으로 확인한다.
- **200,000행 한 규모만 봤다.** 규모에 따른 추세는 [`pg_bigm/experiments/00`](../../../pg_bigm/experiments/00-explain-before-after) 참고.
- ~~선택도는 0.1% 와 30% 두 점만 봤다.~~ **고쳤다** — 0.1 / 1 / 5 / 10 / 30% 다섯 점을 3글자 고정으로 잰다("선택도를 300배 흔들어도 순위가 바뀌지 않는다"). 다만 **2글자에서는 선택도 축을 재지 않았다**(2글자 구간은 trgm 이 이미 무너져 있어 비교가 의미 없다).
- 실행 시간은 1회 측정이라 참고용이다. 다만 231 ms vs 0.52 ms 처럼 자릿수가 다른 차이는 노이즈로 설명되지 않는다. **"선택도를 300배 흔들어도 순위가 바뀌지 않는다" 에서 순위가 뒤집히는 칸들은 전부 노이즈 범위**이므로 시간으로 우열을 말하지 않았다.
- Docker 3 CPU / 4 GB 환경이다. 버퍼 수와 인덱스 스캔 행 수는 환경과 무관하지만 절대 시간은 환경에 의존한다.
