# 실험 03 — 연산자 지원 행렬과 유사도 점수 대조

## 질문

[`01`](../01-keyword-length-and-selectivity) 과 [`02`](../02-index-build-size-and-write) 가 "얼마나 빠른가 / 얼마나 비싼가"를 쟀다면, 여기는 **"애초에 되는가"** 를 잰다.

성능 비교는 두 확장이 같은 일을 할 수 있을 때만 의미가 있다. 그런데 실제로는 **할 수 있는 일 자체가 다르다.** 그리고 "지원한다"고 문서에 적힌 연산자도 실제로 인덱스를 타는지는 별개 문제다.

1. 연산자별로 각 인덱스가 **실제로** 쓰이는가?
2. 같은 오탈자에 두 확장이 매기는 유사도 점수가 얼마나 다른가?
3. 임계값을 같은 0.3 으로 두면 결과 집합이 어떻게 달라지는가?
4. 대소문자·구두점 처리 차이가 검색 결과에 어떻게 나타나는가?

## 방법

```bash
./bench.sh          # 빌드 -> 측정 -> 정리
./bench.sh keep     # 컨테이너를 남긴다
```

- [NSMC](https://github.com/e9t/nsmc)(CC0) 말뭉치 100,000행 + **정답을 알 수 있도록 심어둔 변형 문자열 14개**(`클라우드클럽`, `클라우드 클럽`, `클라으드클럽`, `김신건`/`김신컨`, `CloudClub`/`cloudclub`, `서버 192.168.0.1 접속` 등).
- 인덱스는 한 번에 하나만 두고, `bigm` / `trgm`(GIN) / `gist` 세 가지로 각각 잰다.
- 연산자를 아예 지원하지 않으면 쿼리가 에러 나는데, **그것도 결과로 기록한다.**

## 결과 1 — 연산자 지원 행렬 (100,014행, 정답 행 수를 함께 표기)

| 조건 | `gin_bigm_ops` | `gin_trgm_ops` | `gist_trgm_ops` |
| --- | --- | --- | --- |
| `LIKE '%클라우드클럽%'` (6글자) | 인덱스 (후보 **2**) | 인덱스 (후보 **2**) | 인덱스 (후보 **2**) |
| `LIKE '%클클%'` (2글자) | 인덱스 (후보 **1**) | 인덱스 (후보 **100,014**) | 인덱스 (후보 **100,014**) |
| `ILIKE '%CLOUDCLUB%'` | **Seq Scan** | 인덱스 (후보 2) | 인덱스 (후보 2) |
| `~ 'cloudclub'` (ASCII 정규식) | **Seq Scan** | 인덱스 (후보 2) | 인덱스 (후보 2) |
| `~ '클라우드클럽'` (한글 정규식) | **Seq Scan** | 인덱스 (후보 **100,014**) | 인덱스 (후보 **100,014**) |
| `= '클둥이'` (동등 비교) | **Seq Scan** | 인덱스 (후보 1) | 인덱스 (후보 1) |
| `=% '클라우드클럽'` (bigm 유사도) | 인덱스 (후보 8) | — 연산자 없음 | — |
| `% '클라우드클럽'` (trgm 유사도) | — 연산자 없음 | 인덱스 (후보 6) | 인덱스 (후보 4) |
| `ORDER BY <-> LIMIT 3` (KNN) | — 연산자 없음 | 정렬 불가 | **Index Scan ... Order By** |

### 분석

**(a) `pg_bigm` 은 `LIKE` 와 `=%` 두 가지만 한다.** `ILIKE`, 정규식, `=` 모두 `Seq Scan` 이다. 지원 범위가 좁다는 것이 숫자로 확인된다.

<sub>**공식 문서도 같은 말을 한다.** [pg_bigm 공식 문서](https://github.com/pgbigm/pg_bigm/blob/REL1_2_STABLE/docs/pg_bigm_en.md)의 비교표는 이용 가능한 텍스트 검색 연산자를 pg_bigm 은 *"LIKE only"*, pg_trgm 은 *"LIKE (~~), ILIKE (~~*), ~, ~*"* 로 적는다. 실측(`gin_bigm_ops` 연산자 클래스에 `~~*` 가 등록되어 있지 않다)과 문서가 일치한다 — 반대로 [pg_trgm 공식 문서](https://www.postgresql.org/docs/16/pgtrgm.html)는 *"additionally support trigram-based index searches for `LIKE`, `ILIKE`, `~`, `~*` and `=` queries"* 라고 적고, `pg_amop` 을 읽어 확인한 8개 전략과 맞는다.</sub>

**(b) `pg_trgm` 은 전부 되지만, 두 칸에서 "된다"가 함정이다.** `LIKE '%클클%'` 와 `~ '클라우드클럽'` 이 `Index Cond` 를 달고 있으면서 **후보로 테이블 전체(100,014행)를 올린다.** `GIN_SEARCH_MODE_ALL` 상태다.

> **표에서 "인덱스 사용"만 보면 안 되는 이유가 이것이다.** 반드시 후보 행 수를 함께 봐야 한다.

**(c) `= '클둥이'` 를 `pg_trgm` 만 인덱스로 처리한다.** pg_trgm 1.6(PostgreSQL 14)에서 연산자 패밀리에 `OPERATOR 11 =` 이 추가됐기 때문이다. 실용성은 낮다(B-tree 가 훨씬 낫다) — 다만 이미 trgm 인덱스가 있는 컬럼에 동등 비교가 섞여 들어올 때 별도 인덱스 없이 처리된다는 의미는 있다.

**(d) KNN 은 GiST 만 가능하다.** `pg_bigm` 에는 `<->` 에 대응하는 연산자가 없어서 쿼리 자체를 쓸 수 없다.

### 함정: `word_similarity` 는 피연산자 순서가 인덱스 사용 여부를 바꾼다

처음에 `doc <% '클라우드클럽'` 로 재봤더니 `Seq Scan` 이 나왔다. 연산자를 지원하지 않는 줄 알았는데, **쓰는 방향이 틀렸던 것**이다.

| 쿼리 | 결과 |
| --- | --- |
| `doc <% '검색어'` | **Seq Scan** (Filter 로만 평가) |
| `doc %> '검색어'` | **Index Cond** ✓ |
| `'검색어' <% doc` | **Index Cond** ✓ (플래너가 `doc %> '검색어'` 로 교환한다) |

이유는 두 가지가 겹쳐 있다.

1. **의미**: `word_similarity(a, b)` 는 "a 가 b 의 **어떤 부분**과 얼마나 닮았나"다. 문서에서 검색어를 찾으려면 `'검색어' <% doc` 가 의미상 맞다.
2. **인덱스**: `pg_trgm` 1.2 는 연산자 패밀리에 **`%>` 만** 등록했다(`ALTER OPERATOR FAMILY gin_trgm_ops ADD OPERATOR 7 %>`). 인덱스를 타려면 인덱스 컬럼이 왼쪽에 와야 하므로 `doc %> '검색어'` 형태여야 하고, `'검색어' <% doc` 는 플래너가 교환해 그 형태로 만들어준다.

**`doc <% '검색어'` 는 의미도 다르고 인덱스도 안 탄다** — 두 가지가 동시에 틀리는데 에러는 안 나므로 발견하기 어렵다.

### `strict_word_similarity`(`<<%`) 도 같은 함정이 있다 — 그리고 뜻이 또 다르다

`strict_word_similarity` 는 PostgreSQL 11 에서 추가된 셋째 유사도다. 방향 규칙은 `word_similarity` 와 같다.

| 쿼리 | GIN | GiST |
| --- | --- | --- |
| `doc <<% '검색어'` | **Seq Scan** | — |
| `doc %>> '검색어'` | **Index Cond** ✓ (후보 5행) | — |
| `'검색어' <<% doc` | **Index Cond** ✓ (후보 5행) | **Index Cond** ✓ (후보 5행) |

**세 유사도가 서로 무엇이 다른지**를 같은 검색어(`'클럽'`)로 나란히 재봤다.

| 문서 | `similarity` | `word_similarity` | `strict_word_similarity` |
| --- | ---: | ---: | ---: |
| `클럽` | 1.0000 | 1.0000 | 1.0000 |
| `클럽 하우스` | 0.4286 | **1.0000** | **1.0000** |
| `클라우드클럽` | 0.2500 | **0.3333** | 0.2500 |
| `클라우드클럽 십기 스터디 참여 안내문` | **0.0909** | **0.3333** | **0.2500** |

읽는 법이 셋 다 다르다.

- **`similarity`** 는 **문서 전체**와 비교한다. 그래서 문서가 길어질수록 점수가 떨어진다(0.25 → 0.09). **검색 랭킹으로 쓰면 안 되는 이유가 이것이다** — 긴 문서에 벌점을 준다.
- **`word_similarity`** 는 문서 안 **아무 부분 문자열**과 비교한다. 그래서 문서 길이에 영향받지 않는다(0.3333 유지). `클라우드클럽` 안의 `클럽` 처럼 **단어 중간에서 시작하는 부분**도 인정한다.
- **`strict_word_similarity`** 는 **단어 경계에 맞춘 부분**하고만 비교한다. `클럽 하우스` 의 `클럽`(공백으로 끊긴 온전한 단어)은 1.0 이지만, `클라우드클럽` 안의 `클럽` 은 단어 중간이라 0.25 에 그친다.

> **한국어에서는 이 차이가 특히 크다.** 띄어쓰기가 불규칙하고 복합어가 흔해서, `strict` 판은 `클라우드클럽` 같은 붙여쓴 복합어 안의 부분을 계속 놓친다. **한국어 부분 문자열 검색에는 `word_similarity`(strict 아님) 쪽이 맞다.**

**`pg_bigm` 에는 `word_similarity` 계열이 아예 없다** — `bigm_similarity()` 하나뿐이고, 그것은 위 표의 `similarity` 열과 같은 성질(문서 전체와 비교)이다.

## 결과 2 — 같은 오탈자, 다른 점수

| 원본 | 변형 | `bigm_similarity()` | `similarity()` | 배수 |
| --- | --- | ---: | ---: | ---: |
| 신건 | 신컨 | **0.3333** | 0.2000 | 1.67× |
| 김신건 | 김신컨 | **0.5000** | 0.3333 | 1.50× |
| 클둥이 | 클동이 | **0.5000** | 0.1429 | **3.50×** |
| 클라우드클럽 | 클라으드클럽 | **0.7143** | 0.4000 | 1.79× |
| 클라우드클럽 | 클라우드 클럽 | **0.8571** | 0.5556 | 1.54× |
| 클라우드클럽 | 클라우드클럽스터디 | **0.6000** | 0.5455 | 1.10× |
| 클라우드클럽 | 클클 | 0.1429 | 0.1111 | 1.29× |
| CloudClub | cloudclub | 0.6667 | **1.0000** | **0.67×** |

### 분석

**(a) 한글 오탈자에서는 `pg_bigm` 이 항상 높은 점수를 준다** (1.1× ~ 3.5×). 이유가 둘 겹쳐 있다.

1. **조각이 덜 깨진다** — 한 글자 틀리면 3-gram 은 조각 3개가, 2-gram 은 2개가 깨진다.
2. **분모가 다르다** — `pg_bigm` 은 `공통 / max(len1, len2)`, `pg_trgm` 은 자카드 `공통 / (len1 + len2 - 공통)`. 분모가 자카드 쪽이 항상 크거나 같다.

두 확장 모두 소스에 `DIVUNION` 이라는 **같은 이름의 매크로**로 공식을 분기하는데, `pg_trgm` 만 그 매크로를 `#define` 해뒀다. `pg_bigm` 은 정의하지 않아 반대쪽 가지가 컴파일된다.

**(b) `클둥이` → `클동이` 에서 3.5배로 가장 크게 벌어진다.** 3글자 단어에서 가운데 한 글자가 틀리면 3-gram 은 사실상 전멸한다(0.1429 = 임계값 0.3 미달 → **검색에 안 걸린다**). 짧은 한국어 이름·별명의 오탈자 검색에서는 `pg_bigm` 이 아니면 안 된다는 뜻이다.

**(c) 대소문자에서는 정반대다.** `CloudClub` vs `cloudclub` 에서 `pg_trgm` 은 1.0(완전 동일), `pg_bigm` 은 0.6667. `pg_trgm` 만 `IGNORECASE` 로 소문자화하기 때문이다. **대소문자가 의미를 갖는 식별자·코드 검색이면 `pg_bigm`, 자연어 검색이면 `pg_trgm` 이 편하다.**

## 결과 3 — 임계값을 같은 0.3 으로 두면

```sql
SET pg_bigm.similarity_limit     = 0.3;
SET pg_trgm.similarity_threshold = 0.3;
```

| 순위 | `pg_bigm` `=%` | sim | `pg_trgm` `%` | sim |
| :-: | --- | ---: | --- | ---: |
| 1 | 클라우드클럽 | 1.0000 | 클라우드클럽 | 1.0000 |
| 2 | 클라우드 클럽 | 0.8571 | 클라우드 클럽 | 0.5556 |
| 3 | **클라으드클럽** | 0.7143 | **클라우드클럽스터디** | 0.5455 |
| 4 | 클라우드클럽스터디 | 0.6000 | **클라으드클럽** | 0.4000 |

**결과 집합은 같지만 순위가 다르다.** `pg_bigm` 은 오탈자(`클라으드클럽`)를 3위로, `pg_trgm` 은 접미 확장(`클라우드클럽스터디`)을 3위로 올린다.

- **`pg_bigm`**: 오탈자에 관대하다 → "사용자가 틀리게 쳤을 것"이라는 가정에 맞는다
- **`pg_trgm`**: 자카드라 길이 차이에 민감하다 → 긴 문서일수록 점수가 깎인다

**같은 0.3 이라도 재는 자가 다르므로 `pg_bigm` 쪽이 훨씬 관대하다.** 한쪽에서 다른 쪽으로 옮길 때 임계값을 그대로 가져오면 결과 개수가 크게 달라진다.

## 결과 4 — 구두점

```sql
SELECT show_bigm('192.168.0.1');
--  {" 1",.0,.1,0.,"1 ",16,19,2.,68,8.,92}          ← 점도 조각의 일부

SELECT show_trgm('192.168.0.1');
--  {"  0","  1"," 0 "," 1 "," 16"," 19",168,192,"68 ","92 "}   ← 점에서 단어가 끊긴다
```

`pg_trgm` 은 `KEEPONLYALNUM` 때문에 점을 단어 구분자로 취급해 `192`/`168`/`0`/`1` 네 조각으로 쪼갠다. **`168.0` 이라는 연결 정보가 인덱스에서 사라진다** — IP, 시맨틱 버전, 파일 경로, 코드 식별자 검색에서 실제로 걸린다. `pg_bigm` 에는 이 문제가 없다.

## 정리 — 기능으로 고르는 표

| 필요한 것 | 답 |
| --- | --- |
| 2글자 한글 부분 문자열 | **pg_bigm** (trgm 은 전체 인덱스 스캔) |
| 짧은 한글 이름의 오탈자 검색 | **pg_bigm** (trgm 은 임계값 0.3 에 못 미친다) |
| 구두점이 의미를 갖는 검색 (IP·버전·경로) | **pg_bigm** |
| 대소문자를 구분해야 하는 검색 | **pg_bigm** |
| `ILIKE` | **pg_trgm** (bigm 은 Seq Scan) |
| 정규식 (ASCII/유럽어) | **pg_trgm** — 대안 없음 |
| 정규식 (한글) | **둘 다 안 된다** (trgm 은 전체 인덱스 스캔, bigm 은 Seq Scan) |
| "가장 비슷한 것 N건" 정렬 | **pg_trgm + GiST** — 대안 없음 |
| 단어 단위 유사도 | **pg_trgm** (단, `'검색어' <% doc` 방향으로) |
| 대소문자 무시 유사도 | **pg_trgm** |

## 한계

- 100,000행 한 규모, 한국어 말뭉치 하나로만 쟀다.
- 유사도 점수 비교는 짧은 문자열 8쌍만 봤다. 긴 문서에서는 두 공식의 차이가 더 벌어질 수 있다(자카드는 길이 차이에 더 민감하다).
- `strict_word_similarity` 는 점수와 인덱스 사용 여부만 봤고, **성능(버퍼·시간)은 재지 않았다.**
- 세 유사도 비교는 검색어 하나(`클럽`)와 문서 4개로만 봤다. 어휘가 다양한 실제 말뭉치에서 다시 재면 더 정확할 것이다.
- 후보 행 수만 보고 실행 시간은 재지 않았다 — 시간 비교는 [`01`](../01-keyword-length-and-selectivity) 에 있다.
- `ILIKE` 가 `pg_bigm` 에서 인덱스를 안 탄다는 것은 이 환경(PostgreSQL 16 / pg_bigm `v1.2-20250903`)에서의 관측이다.
