# 실험 04 — n-gram 인덱스는 저장 용량을 얼마나 늘리나 (10만 ~ 500만 행)

## 질문

`"인덱스가 29 MB 다"` 는 그 자체로 판단 근거가 안 된다. 용량 산정에 필요한 건 세 가지다.

1. **원본 테이블 대비 몇 배인가?** ← 실제로 쓰는 단위
2. **규모가 커져도 그 비율이 유지되나?** 아니면 좋아지거나 나빠지나
3. 인덱스 종류별로 얼마나 다른가 (bigm / trgm / GiST / tsvector), 그리고 **평범한 B-tree 와 비교하면?**

[`02`](../02-index-build-size-and-write) 는 20만 행 한 점에서만 쟀다. 여기서는 **50배 규모까지** 늘려본다.

## 방법

```bash
./bench.sh                          # 100k / 500k / 1M / 5M  (약 10분)
SCALES="100000 500000" ./bench.sh   # 빠르게 훑기
```

- [NSMC](https://github.com/e9t/nsmc)(CC0) 한국어 말뭉치 199,993문장을 순환 참조해 각 규모를 채운다.
- 인덱스는 **한 번에 하나만** 만들고 크기를 잰 뒤 지운다.
- `maintenance_work_mem=256MB` 로 올렸다(기본 64MB 로는 500만 행에서 과도하게 스필한다).
- **B-tree(`btree (doc)`)를 대조군으로 넣었다** — "인덱스는 원래 테이블만큼 크다"는 감각의 기준선이다.
- 유니크 엔트리 수는 표본 2만 행 기준 추정치다(전수는 500만 행에서 너무 느리다).

## 분석

### 1. 배수가 규모에 따라 **떨어진다** — 이게 이 실험의 핵심 발견이다

| 행 수 | `gin_bigm_ops` | `gin_trgm_ops` | `gist(siglen=256)` | `btree` |
| ---: | ---: | ---: | ---: | ---: |
| 100,000 | 1.42× | 2.48× | 1.29× | 0.98× |
| 500,000 | 1.04× | 1.57× | 1.31× | 0.98× |
| 1,000,000 | 0.89× | 1.17× | 1.32× | 0.98× |
| 5,000,000 | **0.79×** | **1.01×** | **1.34×** | 0.98× |

**10만 행에서 trgm 은 테이블의 2.5배였는데, 500만 행에서는 1.0배가 된다.** 50배 규모에서 배수가 2.5배 줄었다.

이유는 GIN 의 구조에 있다. GIN 인덱스는 두 부분으로 나뉜다.

```
엔트리 트리   : 서로 다른 조각의 목록          -> 유니크 조각 수에 비례
포스팅 리스트 : 각 조각이 어느 행에 있는지     -> 총 조각 수에 비례 (압축됨)
```

**유니크 엔트리 수가 규모와 무관하게 고정(50,398 / 121,558)이다.** 그래서 엔트리 트리는 안 커지고, 행이 늘어나면 포스팅 리스트만 늘어나는데 그건 TID 를 **델타 인코딩으로 압축**해 저장하므로 행당 비용이 매우 싸다. 결과적으로 고정비(엔트리 트리)가 전체에서 차지하는 비중이 줄어들면서 배수가 떨어진다.

### 2. ⚠️ 그런데 이 감소폭은 이 데이터가 과장한 것이다

**유니크 엔트리가 정확히 고정된 이유는 말뭉치가 199,993문장뿐이기 때문이다.** 1M 행은 같은 문장을 5번, 5M 행은 25번 반복한다. 그래서 행이 늘어도 새 조각이 하나도 안 생긴다.

**실제 서비스에서는 문서가 늘면 새 어휘·새 조각이 계속 나온다.** 유니크 엔트리가 함께 증가하므로 배수 감소가 이만큼 크지 않다. 이 표에서 읽어야 할 것은 **정확한 배수가 아니라 구조**다.

> **n-gram 인덱스 용량은 "행 수 × 상수"가 아니다.**
> `유니크 조각 수`(엔트리 트리, 고정비) + `총 조각 수`(포스팅 리스트, 변동비) 로 결정되고,
> **어휘 반복도가 높을수록 배수가 낮아진다.**

거꾸로 말하면 **어휘가 다양한 데이터(로그, 코드, 사용자 생성 콘텐츠)일수록 배수가 높게 유지된다.**

### 2-b. 그래서 **어휘가 계속 늘어나는 데이터**로도 재봤다

앞 절("이 감소폭은 이 데이터가 과장한 것이다")의 한계를 지적만 하고 두면 "그래서 실제로는 얼마나 다른가"에 답할 수 없다. 그래서 같은 규모를 두 데이터로 나란히 잰다.

| 데이터 | 만드는 법 | 성질 |
| --- | --- | --- |
| `fixed` | 말뭉치를 순환 참조 | 행이 늘어도 **어휘가 안 는다** — 유니크 조각이 금방 포화 |
| `grow` | 각 행에 **그 행에만 있는 한글 낱말**을 하나 붙인다 | 행이 늘수록 **어휘도 는다** |

`grow` 의 낱말은 44개 음절 풀에서 `id` 를 44진법으로 펼쳐 만든다(난수를 안 쓰므로 실행마다 동일). 100만 행이면 100만 개의 서로 다른 낱말이 생긴다.

**표본 20,000행 기준 유니크 엔트리**

| | `fixed` | `grow` | 증가 |
| --- | ---: | ---: | ---: |
| `gin_bigm_ops` | 50,398 | 51,448 | **+2%** |
| `gin_trgm_ops` | 121,558 | 142,546 | **+17%** |
| `gin tsvector` | 82,633 | 102,631 | **+24%** |

**테이블 대비 배수 (100만 행)**

| | `fixed` | `grow` | |
| --- | ---: | ---: | --- |
| `gin_bigm_ops` | 0.89× | **0.89×** | 변화 없음 |
| `gin_trgm_ops` | 1.17× | 1.15× | 변화 없음 |
| `gist_trgm_ops(256)` | 1.32× | 1.32× | 변화 없음 |
| **`gin tsvector`** | **0.93×** | **1.15×** | **+24%** ← 여기만 움직인다 |
| `btree` | 0.98× | 1.00× | — |

**예상과 다른 결과가 나왔다.** "어휘가 늘면 n-gram 인덱스 배수가 덜 떨어질 것"이라고 예상했는데, **움직인 것은 `tsvector` 뿐이었다.**

이유는 **조각의 공간 크기**다.

- **낱말 하나가 통째로 새 어휘소**가 되는 `tsvector` 는 행이 늘면 엔트리가 그만큼 는다 — 무한히 자란다.
- **n-gram 은 낱말을 44개 음절 풀에서 만든 조각으로 쪼갠다.** 2-gram 이 만들 수 있는 조각은 최대 44² = **1,936가지**뿐이라, 이미 있던 50,398개에 파묻힌다. 3-gram 은 44³ = 85,184가지라 조금 더 늘었다(+17%).

> **n-gram 인덱스의 고정비는 "문서 수"가 아니라 "문자 조합 공간"이 정한다.**
> 새 낱말이 아무리 늘어도, 그것이 이미 본 문자들의 조합이면 새 조각은 거의 안 생긴다.
> **이것이 어휘 단위 색인과의 근본적인 차이다** — 그리고 `n` 이 작을수록 이 포화가 더 빨리 온다.

<sub>**설계 한계.** 음절 풀을 44개로 잡았기 때문에 2-gram 쪽 상한이 1,936 으로 낮다. 풀을 한글 전체(11,172자)로 키우면 2-gram 도 계속 자랄 것이다 — 다만 그건 "실제 한국어 텍스트"가 아니라 무작위 음절열이므로, 실서비스의 상한은 이 둘 사이 어딘가다. **이 실험은 두 극단을 보여줄 뿐 실서비스 값을 예측하지 않는다.**</sub>

### 3. `btree` 대조군이 0.98× 로 일정한 것이 이 구조를 뒷받침한다

B-tree 는 **모든 행의 값을 그대로** 저장하므로 테이블 크기에 정확히 비례한다 — 네 규모 모두 0.98×. 고정비가 없다.

**n-gram 인덱스만 규모에 따라 배수가 변한다.** 이 대비가 "배수가 규모에 따라 떨어진다" 의 설명이 맞다는 증거다.

### 4. GiST 는 규모와 무관하게 1.3× 로 일정하다

`gist_trgm_ops(siglen=256)` 은 1.29 → 1.31 → 1.32 → 1.34× 로 거의 변하지 않는다. **시그니처가 행당 고정 크기(256바이트)** 라서 B-tree 처럼 선형으로 커지기 때문이다.

**결과적으로 큰 규모에서는 GiST 가 GIN 보다 커진다** — 500만 행에서 850 MB vs bigm 502 MB(1.7배). 작은 규모에서는 반대였다(10만 행에서 16.2 vs 17.9 MB). 검색 성능은 [`pg_trgm/experiments/01`](../../../pg_trgm/experiments/01-gin-vs-gist-build-and-probe) 에서 봤듯 GIN 이 압도적이므로, **규모가 커질수록 GiST 를 고를 이유가 더 없어진다.**

### 5. bigm 이 trgm 보다 항상 작다 — 격차는 규모에 따라 줄어든다

| 행 수 | trgm / bigm |
| ---: | ---: |
| 100,000 | 1.75배 |
| 500,000 | 1.51배 |
| 1,000,000 | 1.30배 |
| 5,000,000 | 1.28배 |

유니크 엔트리가 2.4배 차이나므로(50,398 vs 121,558) 고정비 차이가 크고, 규모가 커져 변동비 비중이 늘면 격차가 줄어든다.

### 6. 실무 용량 산정

| 상황 | 잡아둘 배수 (테이블 대비) |
| --- | --- |
| 수십만 행 이하, 어휘 다양 | **2 ~ 2.5×** (trgm) / **1.5×** (bigm) |
| 수백만 행, 어휘 반복 많음 | **1 ~ 1.5×** |
| GiST 를 쓴다면 | 규모와 무관하게 **1.3×** |
| 안전하게 | **테이블의 2배**를 잡고 실제 데이터로 재측정 |

**빌드 시간은 500만 행에서도 66~97초** 로, 용량보다 문제가 안 된다. 오히려 `btree` 가 90.6초로 GIN 보다 느렸다(정렬 비용).

## 한계

- **말뭉치가 199,993문장뿐이라 1M·5M 행은 같은 문장의 반복이다.** "이 감소폭은 이 데이터가 과장한 것이다" 에 적었듯 이것이 배수 감소를 과장한다. **이 실험의 가장 큰 한계이고, 표의 절대 배수를 그대로 인용하면 안 된다.** → "어휘가 계속 늘어나는 데이터로도 재봤다" 에서 **어휘가 늘어나는 대조군(`grow`)** 을 함께 재서 이 한계를 정량화했다.
- **`grow` 의 음절 풀이 44개뿐이다.** 그래서 2-gram 이 만들 수 있는 조각 상한이 1,936 가지로 낮다("어휘가 계속 늘어나는 데이터로도 재봤다" 의 각주). 한글 전체 풀로 키우면 결과가 달라질 것이나 그건 실제 한국어가 아니다.
- **`grow` 는 100만 행까지만 쟀다**(5M 은 시간이 과하다). `fixed` 만 500만 행까지 있다.
- **유니크 엔트리는 표본 20,000행 기준이다.** 규모별 총 유니크 수가 아니라 **"2만 행당 어휘 밀도"**를 재는 값이다 — 전수 집계는 5M 행에서 너무 느리다.
- 한국어 한 종류로만 쟀다. 영문은 유니크 조각이 훨씬 적으므로([`02`](../02-index-build-size-and-write): 2-gram 1,937개) 배수가 더 빨리 떨어질 것이다.
- 각 조건을 1회씩 측정했다. GIN 크기는 결정적이지만([`02`](../02-index-build-size-and-write) 에서 2회 확인) GiST 는 몇 % 흔들린다.
- `pg_relation_size()` 만 봤다 — TOAST·FSM·VM 은 제외했다. 실제 디스크 사용량은 조금 더 크다.
- 인덱스를 만든 직후의 크기다. 운영 중 갱신이 쌓이면 블로트로 더 커진다.
