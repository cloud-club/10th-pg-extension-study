# 실험 07 — PostgreSQL 버전별 벤치 (16 / 17 / 18 / 19beta1)

## 질문

이 카탈로그의 결론이 **PostgreSQL 16 에만 해당하는 이야기인가?**

1. "trgm 은 2글자 `%X%` 에서 `GIN_SEARCH_MODE_ALL` 로 무너진다" 가 버전이 올라가도 여전한가?
2. 인덱스 크기·빌드 시간이 버전에 따라 달라지나?
3. 조각 통계가 같게 나오나 (= 확장 자체의 동작이 안 바뀌었나)?

## 방법

```bash
./bench.sh                     # 16 17 18 19, 50만 행 (길이×패턴 격자 45칸 포함)
VERSIONS="16 18" ./bench.sh    # 일부만
ROWS=200000 ./bench.sh         # 행 수 축소
./bench.sh down                # 정리만
```

- 각 버전마다 **pg_bigm 을 그 버전의 서버 헤더로 다시 빌드한다.** PGXS 빌드라 `.so` 가 버전별로 따로 필요하다.
- 컨테이너는 **한 번에 하나만** 띄운다. 동시에 띄우면 CPU 경합으로 시간이 오염된다.
- 데이터·주입은 다른 실험과 동일한 결정적 방식(`generate_series` + `id` 나머지).
- 50만 행, 정답 500행(0.1%) 고정. 검색어는 2·3·6글자 각 하나.

### 도커 태그 주의

PostgreSQL 19 는 아직 GA 가 아니라 태그가 `19beta1-trixie` 이다. 그래서 `PGVER`(경로에 쓰는 메이저 번호)과 `PGTAG`(도커 태그)를 따로 받는다.

## 결과 1 — pg_bigm 1.2 는 PostgreSQL 19beta1 에서 **빌드되지 않는다**

가장 먼저 나온 결과가 이것이다.

```
bigm_op.c:177:26: error: ‘database_ctype_is_c’ undeclared (first use in this function)
bigm_op.c:180:9: warning: implicit declaration of function ‘char2wchar’;
                          did you mean ‘wchar2char’?
make: *** [<builtin>: bigm_op.o] Error 1
```

원인을 헤더에서 직접 확인했다.

| | `utils/pg_locale.h` |
| --- | --- |
| **PG 18** | `extern PGDLLIMPORT bool database_ctype_is_c;` — **전역 변수로 export** 된다. `char2wchar()` 도 선언돼 있다 |
| **PG 19beta1** | 전역 변수가 **사라졌다.** 대신 `pg_locale_t` 구조체 안으로 들어갔다 — `bool ctype_is_c;`. `char2wchar()` 는 **아예 없다** |

즉 PG19 에서 로케일 처리가 "전역 상태"에서 "로케일 객체의 필드"로 리팩터링되면서, 그 전역을 쓰던 확장이 전부 깨진다.

> **이 카탈로그의 Dockerfile 주석은 "1.2 계열, PostgreSQL 16~19 지원" 이라고 적고 있었다. 그 서술은 (적어도 19beta1 시점에는) 사실이 아니다.**
> pg_bigm 쪽 공식 지원 표기와 실제 빌드 가능 여부가 다르다 — **직접 빌드해 보기 전에는 알 수 없다**는 사례다.
> `pg_trgm` 은 contrib 이라 코어와 함께 이관되므로 19beta1 에서도 정상이다.

**그래서 아래 수치는 16 / 17 / 18 세 버전이다.**

## 결과 2 — 결정적 지표는 세 버전에서 **완전히 동일하다**

| PG | server_version | 테이블 | 유니크 조각 (bigm) | 유니크 조각 (trgm) |
| --- | --- | ---: | ---: | ---: |
| 16 | 16.15 | 63 MB | 50,196 | 120,834 |
| 17 | 17.11 | 63 MB | 50,196 | 120,834 |
| 18 | 18.6 | 63 MB | 50,196 | 120,834 |

| PG | bigm 인덱스 | trgm 인덱스 |
| --- | ---: | ---: |
| 16 | 65.8 MB | 99.1 MB |
| 17 | 65.8 MB | 99.1 MB |
| 18 | 65.8 MB | 99.1 MB |

**MB 단위로 완전히 같다.** 확장의 조각 생성 로직도, GIN 의 저장 형식도 이 구간에서 바뀌지 않았다.

### 질의 — 2글자 함정도 그대로다

| PG | 검색어 | 엔진 | 인덱스 스캔 행 | Recheck 제거 | 버퍼 | 시간 |
| --- | --- | --- | ---: | ---: | ---: | ---: |
| 16 | 클클(2) | bigm | 500 | 0 | 4 | 0.74 ms |
| 17 | 클클(2) | bigm | 500 | 0 | 4 | 0.80 ms |
| 18 | 클클(2) | bigm | 500 | 0 | 4 | 0.92 ms |
| **16** | **클클(2)** | **trgm** | **500,000** | **499,500** | **12,642** | **440.7 ms** |
| **17** | **클클(2)** | **trgm** | **500,000** | **499,500** | **12,642** | **429.4 ms** |
| **18** | **클클(2)** | **trgm** | **500,000** | **499,500** | **12,642** | **414.2 ms** |
| 16 | 클둥이(3) | trgm | 500 | 0 | 4 | 0.74 ms |
| 17 | 클둥이(3) | trgm | 500 | 0 | 4 | 0.79 ms |

**인덱스 스캔 행 · Recheck · 버퍼가 세 버전에서 한 자리도 다르지 않다.**

> **`GIN_SEARCH_MODE_ALL` 은 버전을 올려서 해결되는 문제가 아니다.** 이건 플래너나 실행기의 최적화 여지가 아니라 `extractQuery()` 가 조건을 하나도 못 만든 결과이기 때문이다. PostgreSQL 이 할 수 있는 일이 없다.

## 결과 2-b — 길이 × 패턴 격자도 세 버전에서 같다

시각화의 **버전 선택기**가 실험 05 차트에도 붙으려면 그 격자를 버전별로 재야 한다. 그래서 [`05`](../05-pattern-and-length) 와 같은 설계(`<BASE20> 문장 <BASE20>` 주입)로 45칸을 버전마다 다시 잰다. **세 버전 모두 45칸 전부 정답 500행**으로 나왔다 — 설계대로 동작했다는 확인이다.

**2글자 `%X%` (문제의 칸)**

| PG | 인덱스 없음 | `pg_bigm` | `pg_trgm` |
| --- | ---: | ---: | ---: |
| 16 | 29.8 ms | **0.92 ms** | **480.2 ms** ⚠️ |
| 17 | 32.3 ms | **1.03 ms** | **447.0 ms** ⚠️ |
| 18 | 29.7 ms | **1.05 ms** | **466.5 ms** ⚠️ |

**3글자 이상 `%X%` (평균)**

| PG | 인덱스 없음 | `pg_bigm` | `pg_trgm` |
| --- | ---: | ---: | ---: |
| 16 | 30.1 ms | 1.11 ms | 1.06 ms |
| 17 | 30.1 ms | 1.10 ms | 1.13 ms |
| 18 | 29.6 ms | 1.39 ms | 1.20 ms |

**패턴 효과 — 각 엔진의 `%X%` 를 1.0 으로 놓은 상대값(3글자 이상)**

| PG | | `%X%` | `X%` 접두어 | `%X` 접미어 |
| --- | --- | ---: | ---: | ---: |
| 16 | 인덱스 없음 | 1.00 | **0.30** | 1.21 |
| 16 | pg_bigm | 1.00 | 1.07 | 1.09 |
| 16 | pg_trgm | 1.00 | 0.94 | 1.16 |
| 18 | 인덱스 없음 | 1.00 | **0.31** | 1.18 |
| 18 | pg_bigm | 1.00 | 0.91 | 0.95 |
| 18 | pg_trgm | 1.00 | 1.07 | 1.31 |

**여기서도 버전 차이는 없다.**

- **2글자 `%X%` 에서 trgm 이 무너지는 것**은 세 버전 모두 447~480 ms 로 같다.
- **인덱스가 없을 때만 접두어가 0.30 으로 빨라지는 것**도 16·18 에서 똑같이 재현된다(0.303 / 0.305). 인덱스가 붙으면 세 패턴이 0.9~1.3 으로 평평해진다 — **패턴 효과는 CPU 비교 횟수의 문제라 인덱스가 그걸 없애 준다.**

> **버전을 바꿔도 "무엇이 문제인가"는 바뀌지 않는다.**
> 이 격자가 시각화의 실험 05 차트 다섯 개에 버전 선택기를 붙여 준다.

## 결과 2-c — 나머지 세 축도 버전에서 안 갈린다

시각화의 버전 선택기를 **실험 01·04·06 차트에도** 붙이려면 그 축들도 버전별 값이 있어야 한다. 그래서 셋을 더 잰다.

### 길이 × 선택도 (실험 01 축)

| 검색어 | 정답 | 엔진 | PG16 후보/버퍼 | PG17 후보/버퍼 | PG18 후보/버퍼 |
| --- | ---: | --- | ---: | ---: | ---: |
| 클라우드클럽 (6) | 500 | bigm | 500 / 17 | 500 / 17 | 500 / 17 |
| 클둥이 (3) | 500 | bigm | 621 / 65 | 621 / 65 | 621 / 65 |
| **클클 (2)** | 500 | **bigm** | **500 / 4** | **500 / 4** | **500 / 4** |
| **클클 (2)** | 500 | **trgm** | **500,000 / 13,209** | **500,000 / 13,209** | **500,000 / 13,209** |
| 클둥사 (3, 30%) | 150,000 | bigm | 150,000 / 61 | 150,000 / 61 | 150,000 / 61 |
| 클둥사 (3, 30%) | 150,000 | trgm | 150,030 / 25 | 150,030 / 25 | 150,030 / 25 |

**후보 행·Recheck·버퍼가 세 버전에서 한 자리도 다르지 않다.** 선택도를 0.1% → 30% 로 300배 흔들어도 마찬가지다.

<sub>`클둥이` 에서 bigm 이 621행(recheck 121)을 올리는 것은 선택도 축 검색어(`클둥일`·`클둥오`…)가 같은 조각을 공유하기 때문이다 — **손실 인덱스의 교과서적인 예**이고, 이것도 세 버전에서 똑같다.</sub>

### 인덱스 5종 크기 (실험 04 축) — 테이블 63 MB 기준

| 인덱스 | PG16 | PG17 | PG18 |
| --- | ---: | ---: | ---: |
| `gin_bigm_ops` | 65.8 MB (1.04×) | 65.8 MB | 65.8 MB |
| `gin_trgm_ops` | 99.1 MB (1.57×) | 99.1 MB | 99.1 MB |
| `gist_trgm_ops(siglen=256)` | 82.9~83.0 MB (1.31×) | 82.9 MB | 82.9 MB |
| `gin (tsvector)` | 72.8 MB (1.15×) | 72.8 MB | 72.8 MB |
| `btree` (대조군) | 61.8~61.9 MB (0.98×) | 61.9 MB | 61.9 MB |

**MB 단위로 같다.** GiST 만 0.1 MB 흔들리는데, 그건 [GiST 빌드가 비결정적](../../../pg_trgm/experiments/01-gin-vs-gist-build-and-probe) 이기 때문이다.

### 전문검색 재현율 (실험 06 축)

| 키워드 | LIKE(정답) | tsquery 재현율 | 세 버전 |
| --- | ---: | ---: | --- |
| 영화 | 156,809 | **37.8%** | 16·17·18 모두 동일 |
| 배우 | 16,316 | **8.9%** | 동일 |
| 재미 | 37,382 | **7.3%** | 동일 |

**소수점까지 같다.** 순수 집계이므로 당연하지만, **"버전이 바꿀 수 있는 것이 아니다"를 확인해 둔 것**이다.

<sub>50만 행 기준이라 [`06`](../06-fulltext-vs-ngram)(100만 행)과 절대 행수는 다르지만 **재현율은 37.8% / 8.9% 로 소수점까지 일치한다** — 규모에도 안 흔들린다는 뜻이다.</sub>

> **여기까지가 이 실험의 답이다.** 네 축(질의·길이×패턴·길이×선택도·용량·재현율) 전부에서
> **PostgreSQL 버전은 결과를 바꾸지 않는다.** 바뀌는 것은 인덱스 빌드 시간 하나뿐이다 — 아래 "결과 3" 절.

## 결과 3 — 그런데 **인덱스 빌드는 PG18 에서 약 2배 빨라졌다**

이번 실험에서 유일하게 버전 차이가 난 지표다.

| PG | bigm 빌드 | trgm 빌드 |
| --- | ---: | ---: |
| 16 | 8.0 s | 7.1 s |
| 17 | 7.8 s | 7.0 s |
| 18 | **3.5 s** | **3.7 s** |

**2회 실행 모두 같은 방향이었다**(1회차 7.4/6.7 → 4.0/4.9, 2회차 8.0/7.1 → 3.5/3.7). 16→17 은 차이가 없고, **17→18 에서 갈린다.**

원인은 **확인하지 못했다.** PostgreSQL 18 이 도입한 비동기 I/O(`io_method`)나 인덱스 빌드 경로의 변경이 후보이지만, 이 실험은 그걸 분리해 재지 않았다. **관측만 기록한다.**

> 실무적으로는 이렇게 읽으면 된다 — **검색 성능은 버전으로 개선되지 않지만, 대량 적재 후 인덱스를 다시 만드는 운영 작업은 18 에서 눈에 띄게 빨라진다.**

<sub>시간 지표라 머신 부하에 민감하다. 2배는 자릿수 차이가 아니므로 **한 대의 머신에서 두 번 관측한 것** 이상으로 일반화하면 안 된다.</sub>

## 이번에 걸린 함정 — PostgreSQL 18 이 `EXPLAIN` 출력 형식을 바꿨다

첫 실행에서 **PG18 만 인덱스 스캔 행과 버퍼가 전부 `-`** 로 나왔다. 파서 문제였다.

```
PG 16/17 :  (actual time=0.03..0.14 rows=500 loops=1)
PG 18+   :  (actual time=0.03..0.14 rows=500.00 loops=1)
                                          ^^^^^^ 소수로 바뀌었다
```

PostgreSQL 18 부터 `EXPLAIN ANALYZE` 의 `actual rows` 가 소수로 표시된다(루프당 평균을 반올림 없이 보여주기 위해). `rows=[0-9]+` 로만 잡던 정규식이 전부 빗나갔다.

> **버전 매트릭스 실험에서 가장 위험한 실패 모드는 "측정이 틀리는 것"이 아니라 "파싱이 조용히 실패해서 그 버전만 빈칸이 되는 것"이다.** 값이 `-` 로 나왔을 때 "그 버전은 인덱스를 안 탔나 보다"로 읽었다면 완전히 틀린 결론이 됐을 것이다.

두 번째 함정도 있었다. 조각 통계를 이렇게 셌더니 세 버전 모두 정확히 `20000` 이 나왔다.

```sql
-- 틀린 것: LIMIT 이 DISTINCT 결과에 걸린다
SELECT count(*) FROM (SELECT DISTINCT unnest(show_bigm(doc)) FROM docs LIMIT 20000) s;

-- 고친 것: LIMIT 은 표본 문서 수에 걸어야 한다
SELECT count(DISTINCT g)
FROM (SELECT doc FROM docs ORDER BY id LIMIT 20000) t, unnest(show_bigm(t.doc)) g;
```

**세 버전이 똑같이 20000 이라 "버전 간 동일"로 읽힐 뻔했다.** 값이 일치한다고 해서 측정이 맞은 것은 아니다.

## 정리

| 질문 | 답 |
| --- | --- |
| 결론이 PG16 한정인가? | **아니다.** 16·17·18 에서 결정적 지표가 완전히 동일하다 |
| 2글자 함정이 버전으로 해결되나? | **안 된다.** 세 버전 모두 500,000행 / 499,500 recheck / 12,642 버퍼로 똑같다 |
| 인덱스 크기가 달라지나? | **안 달라진다.** MB 단위로 동일 |
| 달라지는 것은? | **인덱스 빌드 시간.** PG18 에서 약 2배 빠르다 (원인 미확인) |
| PG19 는? | **pg_bigm 1.2 가 빌드되지 않는다** (`database_ctype_is_c` 제거) |

## 한계

- **50만 행 한 규모, 선택도 한 점(0.1%)** 에서만 쟀다. 격자의 절대 시간은 [`05`](../05-pattern-and-length)(100만 행)와 다르다 — **버전 간 비교에만 쓸 것.** 다른 축은 [`01`](../01-keyword-length-and-selectivity)·[`05`](../05-pattern-and-length) 참고.
- **19 는 빌드 실패라 `pg_trgm` 단독으로도 재지 않았다.** contrib 이므로 동작은 할 것이나 확인하지 않았다.
- **빌드 시간 차이의 원인을 분리하지 않았다.** PG18 의 비동기 I/O 가 후보이지만 확인하지 않았다.
- 각 칸 1회 측정이다. 다만 실험 전체를 **2회 돌려** 결정적 지표가 동일한 것과 빌드 시간 방향이 같은 것을 확인했다.
- 기본 설정 + `maintenance_work_mem=256MB` 만 준 상태다. 버전마다 기본값이 다른 GUC 가 있으면 그 영향이 섞여 있을 수 있다.
