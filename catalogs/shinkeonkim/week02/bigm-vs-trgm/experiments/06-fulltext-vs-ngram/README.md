# 실험 06 — 내장 전문검색(tsvector/tsquery) vs n-gram 인덱스 (100만 행)

## 먼저 짚을 것

**`tsvector`/`tsquery` 는 익스텐션이 아니다.** PostgreSQL 코어에 내장된 타입·연산자이고 `CREATE EXTENSION` 이 필요 없다. 스크립트는 이것부터 확인하고 시작한다.

```
  설치된 익스텐션 목록:        타입 목록:
 pg_bigm                      tsvector | tsvector | b
 pg_trgm                      tsvector | tsquery  | b
 plpgsql
```

`pg_bigm`/`pg_trgm` 과는 **층위가 다르다** — 그래서 "무엇이 더 빠른가"보다 **"무엇을 못 하는가"** 가 중요한 비교다.

## 질문

1. "부분 문자열이 들어 있는 문서를 찾는다"는 요구에 대해, 전문검색은 **몇 %를 찾나?**
2. 접두어 검색(`:*`)을 쓰면 **얼마나 회복되나?**
3. 인덱스 크기와 속도는?
4. **각자만 할 수 있는 것**은 무엇인가?

## 방법

```bash
./bench.sh                  # 100만 행
ROWS=200000 ./bench.sh      # 작은 머신
./bench.sh down             # 정리만
```

- 데이터: [NSMC](https://github.com/e9t/nsmc)(CC0) 영화 리뷰 말뭉치 199,993문장을 순환 복제해 100만 행.
- 키워드: 말뭉치에 실제로 흔한 `영화 연기 배우 스토리 감동 재미`. 조사가 붙는 정도가 서로 다르도록 골랐다.
- `tsvector` 컬럼: `GENERATED ALWAYS AS (to_tsvector('simple', doc)) STORED`.
- **재현율의 정답은 `LIKE '%키워드%'`** 로 정의한다. "이 문자열이 들어 있는 문서 전부"가 우리가 답하려는 질문이기 때문이다.

### `'simple'` 설정을 쓴 이유와 그 한계

PostgreSQL 코어에는 **한국어 형태소 사전이 없다.** `'simple'` 은 공백으로 자르고 소문자화만 한다. 그래서 `영화`·`영화는`·`영화지만`·`이영화` 가 **전부 다른 어휘소**가 된다.

> 아래 재현율 숫자는 **"코어만 써서 한국어 전문검색을 하면 이렇게 된다"** 는 뜻이지, "전문검색이 원래 나쁘다"는 뜻이 아니다. 은전한닢/mecab 같은 형태소 분석기를 붙이면 달라진다 — 그건 이 실험의 범위 밖이다.

## 결과 (실측, 1,000,000행)

### (1) 재현율 — `LIKE` 를 정답으로

| 키워드 | LIKE (정답) | `tsquery` | 재현율 | `tsquery '키워드:*'` | 재현율 | 정확 일치 어휘소 변형 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 영화 | 313,428 | 118,437 | **37.8%** | 239,651 | 76.5% | 1,280 |
| 연기 | 51,121 | 11,252 | **22.0%** | 43,019 | 84.2% | 1,034 |
| 배우 | 32,520 | 2,900 | **8.9%** | 24,100 | 74.1% | 552 |
| 스토리 | 34,651 | 10,490 | **30.3%** | 31,316 | 90.4% | 555 |
| 감동 | 30,996 | 4,980 | **16.1%** | 28,381 | 91.6% | 772 |
| 재미 | 74,494 | 5,516 | **7.4%** | 67,524 | 90.6% | 1,738 |

**평균 20.4% → 접두어로 84.6%.**

### (2) 놓치는 것의 정체

`'영화'` 를 포함하지만 `to_tsquery('simple','영화')` 가 못 찾는 문서를 뽑으면 셋 중 하나다.

| 유형 | 예 | 어휘소 |
| --- | --- | --- |
| 조사가 붙음 | "오래 전에 본 **영화지만** 그 긴장감은…" | `'영화지만'` |
| 복합어 안 | "입장에선 **이영화** 안찍었으면" | `'이영화'` |
| 공백이 없음 | "마음이따듯해지는영화." | `'마음이따듯해지는영화'` |

키워드 하나가 실제 말뭉치에서 **552~1,738가지 어휘소**로 흩어진다.

`:*` 는 **앞쪽이 일치하는** 변형(`영화는`, `영화지만`)을 회수한다. 하지만 **키워드 앞에 뭔가 붙은 경우(`이영화`, `공포영화`)는 원리상 못 잡는다** — 남은 8~26%가 그것이다.

> **`:*` 는 반쪽짜리 해법이다.** 그리고 접두어 매칭은 엔트리 트리를 구간 스캔하므로 정확 일치보다 비싸다.

### (3) 인덱스 크기와 빌드 시간

| 대상 | 크기 | 테이블 대비 | 빌드 |
| --- | ---: | ---: | ---: |
| 테이블 (`doc` + `tsv` 컬럼 포함) | 291 MB | — | — |
| `gin(tsv)` | **121 MB** | 0.41× | **5.6s** |
| `gin_bigm_ops` | 123 MB | 0.42× | 13.6s |
| `gin_trgm_ops` | 158 MB | 0.54× | 12.8s |

**주의 — 이 표는 tsvector 에 유리하게 기울어 있다.** 분모인 291 MB 에 `tsv` **생성 컬럼 자체가 이미 포함**되어 있다. n-gram 쪽은 그 컬럼이 필요 없으므로, 실제 총 소유 비용은 tsvector 쪽이 표에 보이는 것보다 불리하다. 인덱스만 놓고 보면 tsvector 와 bigm 은 사실상 같고(121 vs 123 MB), trgm 만 30% 크다 — 3-gram 의 유니크 조각이 더 많기 때문이다([`02`](../02-index-build-size-and-write) 에서 5만 vs 12만으로 측정).

빌드가 tsvector 만 2배 이상 빠른 것은 **만들어야 할 엔트리 자체가 적어서**다. 어휘소는 문자 조각보다 훨씬 성기다.

### (4) 속도 — 이 비교의 주인공이 아니다

> **⚠️ 이 절은 한 번 잘못 쟀다. 아래는 다시 잰 값이다.** 경위는 §속도 표를 왜 다시 쟀나 참고.

| 키워드 | 방식 | **쓴 인덱스** | 매치 행수 | 버퍼 | 시간 |
| --- | --- | --- | ---: | ---: | ---: |
| 영화 | `tsquery @@` | `docs_tsv` | 118,437 | 36,009 | 198.4 ms |
| 영화 | `LIKE` (bigm) | `docs_bigm` | **313,428** | 37,252 | 115.0 ms |
| 영화 | `LIKE` (trgm) | `docs_trgm` | **313,428** | **72,032** | **1,972.2 ms** |
| 스토리 | `tsquery @@` | `docs_tsv` | 10,490 | 9,228 | 45.6 ms |
| 스토리 | `LIKE` (bigm) | `docs_bigm` | **34,651** | 22,873 | 178.0 ms |
| 스토리 | `LIKE` (trgm) | `docs_trgm` | **34,651** | 22,854 | 134.6 ms |

**매치 행수가 다르다 — 같은 일을 하고 있지 않다.** `영화` 에서 tsquery 가 찾은 행은 `LIKE` 의 **1/3**이다. 속도만 떼어 비교하면 "전문검색이 비슷하네"라고 잘못 읽게 된다.

<sub>**절대 시간은 이 표 안에서만 비교할 것.** 이 실행은 머신 부하가 높아 이전 실행보다 시간이 전반적으로 크다(tsquery 영화가 77.7 → 198.4 ms). **버퍼는 두 실행에서 거의 같다**(36,009 그대로) — 그래서 이 카탈로그가 시간 대신 버퍼를 주 지표로 쓴다.</sub>

**덤으로 알게 된 것 — `영화`(2글자)를 trgm 으로 풀면 버퍼가 2배(37,252 → 72,032), 시간이 17배다.** 2글자라 조각을 못 만들어 `GIN_SEARCH_MODE_ALL` 로 떨어지기 때문이다. `스토리`(3글자)에서는 둘이 비슷하다. **이 카탈로그의 2글자 함정이 전문검색 비교 안에서도 그대로 나타난다.**

### 속도 표를 왜 다시 쟀나 — 인덱스 세 개를 동시에 둔 채로 쟀다

1차 판은 `docs_tsv` · `docs_bigm` · `docs_trgm` **세 인덱스를 다 만들어 둔 채로** `doc LIKE '%키워드%'` 를 재고 그 줄에 **"LIKE (bigm 인덱스)"** 라고 적었다. 그런데 **`LIKE` 는 bigm 으로도 trgm 으로도 풀 수 있다** — 플래너가 둘 중 무엇을 골랐는지 확인한 적이 없었다.

**버퍼 수가 지문이 됐다.**

| 키워드 | 1차 판에 적힌 버퍼 | 다시 잰 bigm | 다시 잰 trgm | 실제로 쓴 것 |
| --- | ---: | ---: | ---: | --- |
| 영화 | 37,248 | **37,252** | 72,032 | **bigm** — 라벨이 맞았다 |
| 스토리 | **22,854** | 22,873 | **22,854** | **trgm** — 라벨이 틀렸다 |

**같은 표 안에서 한 줄은 bigm 을, 한 줄은 trgm 을 탔는데 둘 다 "bigm"이라고 적혀 있었다.** 버퍼가 결정적 지표(같은 데이터·같은 쿼리면 실행마다 거의 안 변한다)라서 이 대조가 증거로 성립한다.

<sub>이 카탈로그의 다른 실험 11개는 전부 **"인덱스는 한 번에 하나만 존재하게 한다"** 는 원칙을 지키고 있었다([`01`](../01-keyword-length-and-selectivity) 의 `make_index` 주석에 그 이유가 적혀 있다). **이 실험만 세 개를 동시에 만드는 바람에 빠져나갔다.**</sub>

**고친 방법 세 가지**

1. n-gram 쪽을 잴 때는 **상대 인덱스를 지우고** 잰다.
2. 플랜에서 `Index Scan on <이름>` 을 읽어 **"쓴 인덱스" 열에 기록**한다 — 가정하지 않고 확인한다.
3. 이왕 나눈 김에 **`LIKE` 를 trgm 으로 푸는 경우도 함께** 잰다(원래 없던 비교인데, 위의 2글자 발견이 여기서 나왔다).

**이 절 말고는 영향이 없다.** 재현율·인덱스 크기·`%화가%` 교차·구절 검색은 전부 순수 집계이거나 크기라서 인덱스 공존과 무관하다. `tsquery @@` 줄도 `docs_tsv` 로만 풀리므로 경합이 없다.

<sub>발견 경위: [`lab-server`](../../../lab-server/README.md) 를 만들며 캐시를 넣으려고 인덱스 두 개를 남겨뒀더니 **trgm 의 2글자가 정상으로 나왔다.** 그게 이상해서 파고들다 원래 실험까지 되짚었다.</sub>

### (5) 전문검색만 되는 것

**구절 검색** — 어휘소의 *위치*를 저장하기 때문에 가능하다.

| 질의 | 결과 |
| --- | ---: |
| `phraseto_tsquery('simple','영화 연기')` — 인접 | **45** |
| `to_tsquery('simple','영화 & 연기')` — 같은 문서 아무 데나 | 1,250 |

n-gram 인덱스는 조각의 위치를 저장하지 않으므로 **대응하는 기능이 없다.**

**관련도 랭킹** — `ts_rank(tsv, query)`. `pg_trgm` 의 `similarity()` 가 비슷해 보이지만 그것은 "질의와 문서가 **얼마나 닮았나**"이지 "질의에 대해 이 문서가 **얼마나 관련 있나**"가 아니다. 긴 문서일수록 유사도가 떨어지므로 **관련도 정렬로 쓰면 오히려 해롭다.**

### (6) n-gram 만 되는 것

**어휘 경계를 가로지르는 부분 문자열.**

| 질의 | 결과 |
| --- | ---: |
| `doc LIKE '%화가%'` | **25,366** |
| `tsv @@ to_tsquery('simple','화가')` | 445 (1.8%) |

`영화가` 안의 `화가` 는 어휘소 `'영화가'` 의 일부일 뿐이다. 전문검색은 어휘소 **전체**가 일치해야 하므로 **단어 중간은 원리상 접근할 수 없다.** `:*` 도 소용없다 — 접두어이지 부분 문자열이 아니기 때문이다.

## 정리

| | tsvector | n-gram (bigm/trgm) |
| --- | --- | --- |
| 설치 | 코어 — 불필요 | `CREATE EXTENSION` |
| 인덱싱 단위 | 어휘소 (파서+사전이 결정) | 고정 길이 문자 조각 (기계적) |
| 위치 정보 | **저장한다** | 저장하지 않는다 |
| 답하는 질문 | "이 **단어**가 들어 있는 문서" | "이 **문자열**이 들어 있는 문서" |
| 한국어 재현율(`simple`) | 7~38% (`:*` 로 74~92%) | 100% (정의상) |
| 랭킹 / 구절 | **있다** | 없다 |
| 어휘 중간 부분 문자열 | 못 한다 | **한다** |

**한 문장으로 — `tsvector` 는 "단어를 아는 대신 문자를 모르고", n-gram 은 "문자를 아는 대신 단어를 모른다."** 한국어에 형태소 사전을 붙이지 않은 상태라면 앞의 "단어를 안다"가 성립하지 않으므로, 부분 문자열 검색 요구에는 n-gram 이 사실상 유일한 답이다.

### 선택 기준

| 요구사항 | 선택 |
| --- | --- |
| 입력창에 친 **부분 문자열**이 든 행을 빠짐없이 | `pg_bigm` / `pg_trgm` |
| 영문·서구어 **단어** 검색 + 관련도 정렬 | `tsvector` |
| "A 다음에 바로 B" 구절 검색 | `tsvector` |
| 한국어 **단어** 검색을 제대로 | 형태소 분석기(은전한닢/mecab) + `tsvector` |
| 오탈자 허용 | `pg_trgm` (`%`, `<->`) |

## 한계

- **한국어 사전 없이(`simple`) 잰 것이다.** 형태소 분석기를 붙이면 재현율이 크게 오른다. 이 실험은 "코어만으로 되는가"에 답하지, 전문검색 일반을 평가하지 않는다.
- **정답을 `LIKE '%키워드%'` 로 정의한 것 자체가 n-gram 에 유리한 프레이밍**이다. "사용자가 원한 것이 정말 부분 문자열인가"는 도메인에 달렸다 — `배우` 를 찾는 사람이 `배우자` 를 원하지는 않을 것이다. **재현율이 높다고 정밀도가 높은 것은 아니다.**
- 속도는 각 칸 1회 측정이고 매치 행수가 서로 달라 **직접 비교할 수 없다.** 자릿수만 읽을 것.
- **속도 표는 1차 판에서 잘못 쟀다가 다시 쟀다**(§속도 표를 왜 다시 쟀나). 지금은 "쓴 인덱스" 열로 검증되지만, **1회 측정이라 시간은 여전히 머신 부하에 좌우된다.**
- 인덱스 크기 비교의 분모(291 MB)에 `tsv` 생성 컬럼이 포함되어 있다(위 §3 주의).
- 말뭉치가 영화 리뷰 한 도메인이다. 어휘 분포가 다른 도메인에서는 어휘소 변형 수가 달라진다.
- 한 규모(100만 행)에서만 쟀다.
