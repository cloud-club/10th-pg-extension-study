# 실험 10 — 1글자 검색은 왜 `pg_bigm` 에서만 되나

> **질문.** 이 카탈로그는 *"GIN 엔트리가 정렬돼 있으니 접두어 구간 탐색이 되고, 그래서 `pg_bigm` 은 1글자도 인덱스를 탄다"* 고
> 여러 곳에 써왔는데 **재본 적이 없었다.** 사슬을 한 칸씩 확인한다.

## 쉽게 먼저 — 한 문단

`pg_bigm` 은 두 글자씩 자르니 **한 글자짜리 검색어로는 조각을 만들 수 없습니다.** 그런데도 인덱스를 탑니다. 왜냐하면 조각을 하나 만들어 넘기는 대신 **"`클` 로 시작하는 조각을 전부 가져와라"** 라고 넘기기 때문입니다. 이게 가능한 이유는 `pg_bigm` 의 인덱스 항목이 **글자 그대로 사전순으로 정렬돼 있어서** `클` 로 시작하는 것들이 **한 덩어리로 모여 있기** 때문입니다. `pg_trgm` 은 조각을 숫자로 해싱해 저장하므로 그런 덩어리가 생기지 않고, 그래서 이 방법 자체를 쓸 수 없습니다.

## 재현

```sh
./bench.sh          # 빌드 -> 측정 -> 정리
REPEAT=1 ./bench.sh
```

PostgreSQL 16.15 / pg_bigm 1.2 / pg_trgm 1.6 / 200,000행.
주입 문자는 **`ퟛ`(U+D7DB)** 를 썼다 — 한글 음절 영역 끝이라 NSMC 말뭉치에 나오지 않아서 1글자 검색의 정답 행 수를 정확히 통제할 수 있다.

## A. 1글자로 조각이 나오는가 — **양쪽 다 나온다** (색인하는 쪽에서는)

```sql
SELECT show_bigm('클');   -- {" 클","클 "}
SELECT show_trgm('클');   -- {0x4e7d65,0x8ef03f}      해시 2개
```

**여기가 흔히 오해하는 자리다.** `show_bigm`/`show_trgm` 은 **색인하는 쪽**(`extractValue`)이다. 1글자짜리 *낱말* 이면 앞뒤에 패딩을 붙일 수 있으므로 양쪽 다 조각이 나온다.

갈리는 것은 **질의하는 쪽**(`extractQuery`)이다.

| | `LIKE '%클%'` 에서 질의가 만드는 것 |
| --- | --- |
| `pg_trgm` | **없다.** 양옆이 `%` 라 패딩을 못 붙이고, 3글자를 못 채운다 → `GIN_SEARCH_MODE_ALL` |
| `pg_bigm` | 조각 대신 **`클` 을 부분 일치(partial match) 키로** 넘긴다 |

## B. 그 부분 일치가 가능한 이유 — 카탈로그를 직접 읽었다

```sql
SELECT o.opcname,
       coalesce(kt.typname, it.typname || ' (opckeytype=0)') AS 엔트리_타입,
       (SELECT string_agg(ap.amproc::text, ', ')
        FROM pg_amproc ap
        WHERE ap.amprocfamily = o.opcfamily AND ap.amprocnum = 5) AS compare_partial
FROM pg_opclass o
JOIN pg_type it ON it.oid = o.opcintype
LEFT JOIN pg_type kt ON kt.oid = o.opckeytype
WHERE o.opcname IN ('gin_bigm_ops','gin_trgm_ops');
```

| 연산자 클래스 | 엔트리 타입 | `comparePartial` (GIN 지원 함수 5번) |
| --- | --- | --- |
| `gin_bigm_ops` | **`text`** (`opckeytype = 0` — 입력 타입 그대로) | **`gin_bigm_compare_partial`** |
| `gin_trgm_ops` | `int4` (CRC32 해시) | **없음** |

**두 칸이 사슬의 양 끝이다.**

1. 엔트리가 `text` 라 **엔트리 트리(B-tree)가 사전순으로 정렬**된다 → `클` 로 시작하는 bigram(`클가`, `클나`, … `클힣`, `클 `)이 **연속 구간**에 모인다.
2. GIN 은 그 구간을 훑을 수 있다. 다만 **어디서 멈출지**를 확장이 알려줘야 하는데, 그게 `comparePartial` 이다. `pg_bigm` 은 등록했고 `pg_trgm` 은 등록하지 않았다.
3. `pg_trgm` 이 등록하지 않은 것은 게을러서가 아니라 **등록할 수가 없어서다.** 엔트리가 CRC32 해시(`int4`)라 정렬 순서가 원문 순서와 무관하다 — `클` 로 시작하는 트라이그램들의 해시값은 정수 축 위에 흩어진다. 연속 구간이 아예 존재하지 않는다.

> 이것이 **`pg_bigm` 이 조각을 해싱하지 않는 대가로 얻는 것**이다. 해싱하지 않으니 엔트리가 커지고(9바이트 한글 조각 그대로) 인덱스도 커지지만, 순서가 살아남는다.

## C. 그래서 1글자 검색이 실제로 인덱스를 타는가 — **탄다**

플래너를 강제하지 않고 잰 값이다.

| 엔진 | 패턴 | 정답 | 플랜 | 쓴 인덱스 | 후보 | recheck 제거 | 버퍼 | ms |
| --- | --- | ---: | --- | --- | ---: | ---: | ---: | ---: |
| 없음 | `%ퟛ%` | 400 | Parallel Seq Scan | — | — | 0 | 3,225 | 27.12 |
| **bigm** | `%ퟛ%` | 400 | **Bitmap Index Scan** | `docs_bigm` ✔ | **400** | **0** | **404** | **1.42** |
| trgm | `%ퟛ%` | 400 | **Parallel Seq Scan** | — ✘ | — | 0 | 3,225 | 26.52 |

**버퍼 3,225 → 404 (8배), 시간 27.1 → 1.4 ms (19배).** 그리고 **후보 400 = 정답 400, recheck 0** 이다 — 부분 일치가 후보를 정답까지 정확히 좁혔다.

<sub>`recheck 0` 인 것도 우연이 아니다. `bigm_gin.c` 는 조각이 하나뿐이고 공백이 없으면 `*recheck = false` 로 둔다 — 조각 하나가 검색어 전체라 순서를 잃을 여지가 없기 때문이다.</sub>

## D. 길이를 늘려가며

| 길이 | 패턴 | 정답 | 없음 | **bigm** | trgm |
| ---: | --- | ---: | --- | --- | --- |
| 1글자 | `%ퟛ%` | 400 | Seq 3,225버퍼 · 27.1 ms | **404버퍼 · 1.42 ms** | **Seq 3,225버퍼 · 26.5 ms** |
| 2글자 | `%ퟛ가%` | 200 | Seq 3,225버퍼 · 25.4 ms | **204버퍼 · 0.71 ms** | **Seq 3,225버퍼 · 37.2 ms** |
| 3글자 | `%ퟛ가운%` | 200 | Seq 3,225버퍼 · 26.3 ms | 207버퍼 · 0.91 ms | 204버퍼 · 0.88 ms |

**3글자에서 두 확장이 만난다.** 1·2글자 구간이 `pg_bigm` 을 쓸 이유의 전부이고, 그 구간에서 `pg_trgm` 은 인덱스를 아예 쓰지 않는다(이 규모에서는 플래너가 전체 인덱스 스캔보다 Seq Scan 이 싸다고 판단했다 — [실험 08](../08-space-and-punctuation) 의 같은 관측).

**결정적 지표(정답·플랜·쓴 인덱스·후보·recheck·버퍼)는 2회 실행에서 전부 동일했다.**

## 정리

```
pg_bigm 은 조각을 해싱하지 않는다
   → GIN 엔트리 타입이 text 다
      → 엔트리 트리가 사전순으로 정렬된다
         → '클' 로 시작하는 조각이 연속 구간에 모인다
            → comparePartial 을 등록해 그 구간을 훑을 수 있다
               → 1글자 검색이 인덱스를 탄다 (버퍼 8배 · 시간 19배 이득)

pg_trgm 은 CRC32 로 해싱한다 → 정렬 순서가 원문과 무관 → 구간이 없다 → 등록할 수 없다
```

## 한계

- 200,000행 한 규모, 주입 문자 하나(`ퟛ`)로만 쟀다. 흔한 글자(예: `이`)로 1글자 검색을 하면 후보가 폭증해 이득이 사라질 것이다 — **선택도 축은 재지 않았다.**
- `comparePartial` 이 실제로 몇 개의 엔트리를 훑는지는 재지 않았다. 버퍼 404 로 미루어 짐작할 뿐이다.
- 1글자 검색의 **쓰기 쪽 비용**(엔트리가 text 라 인덱스가 큰 것)은 [실험 02](../02-index-build-size-and-write) · [실험 04](../04-storage-overhead-at-scale) 에 있다.
