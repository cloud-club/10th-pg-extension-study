# pg_bigm vs pg_trgm — 비교

> `pg_bigm` 을 정리하다 보니 문서 곳곳에서 `pg_trgm` 을 비교 대상으로 언급하고 있는데, **정작 그 비교의 근거가 대부분 인용이었다.** 직접 재보니 틀린 것도 있었다. 이 디렉터리는 두 확장을 같은 조건에서 나란히 놓고 **원리와 숫자로** 정리한 결과다.

## 1. 한 문장 결론

**`pg_bigm` 이 이기는 칸은 "2글자 이하 검색어" 하나이고, 거기서는 압도적이며, 한국어에서는 그 칸에 자주 들어간다.** 나머지 칸에서는 `pg_trgm` 이 같거나 낫고, 지원하는 기능은 훨씬 많다.

```
                   검색어 길이
              2글자          3글자 이상
           ┌──────────────┬─────────────────┐
   높음    │ bigm 압도적   │  동률            │
 (희귀)    │ 버퍼 1,274배  │ (trgm 근소 우위)  │
 선택도    ├──────────────┼─────────────────┤
   낮음    │ bigm 이 낫지만│  둘 다 힙 읽기가  │
 (흔함)    │ 둘 다 느리다  │  병목            │
           └──────────────┴─────────────────┘
```

## 2. 공통점 — 생각보다 많다

| | 내용 |
| --- | --- |
| **문제 해결 방식** | 문자열을 고정 길이 조각으로 쪼개 "조각 → 행 목록"을 인덱싱한다. `LIKE '%X%'` 를 집합 연산 문제로 바꾼다 |
| **인덱스 구조** | 둘 다 **GIN** 을 쓴다. 엔트리 트리 + 포스팅 리스트/트리 |
| **확장 방식** | 훅도, 백그라운드 워커도, 공유 메모리도 없다. **연산자 클래스만 등록**한다 |
| **`_PG_init()`** | 커스텀 GUC 만 등록한다 (bigm 4개 / trgm 3개) |
| **`EXPLAIN` 모습** | 전용 노드가 없다. `Bitmap Index Scan` + `Bitmap Heap Scan` + `Recheck Cond` |
| **Recheck** | 조각 집합이 같아도 원문이 다를 수 있어(`trial` vs `trivial`) 항상 힙을 다시 본다 |
| **조각을 못 뽑았을 때** | 둘 다 `GIN_SEARCH_MODE_ALL` 로 떨어진다 — **폴백 코드는 주석까지 같다** |
| **`triConsistent`** | 둘 다 2016년에 추가했다 (GIN 3상태 consistent) |
| **`FASTUPDATE`** | GIN 공통 기능. 끄면 쓰기가 3~4배 느려진다 (실측) |
| **공존** | 같은 DB 에 함께 설치할 수 있다 (pg_bigm 1.1 의 연산자 클래스 개명 이후) |

**"둘 다 GIN 을 쓴다"까지는 정말 같다.** 차이는 그 위에 무엇을 얹느냐다.

## 3. 차이점 — 근본 원인은 두 줄이다

### (a) 조각을 어떻게 저장하나

```c
/* pg_trgm: 고정 3바이트. 멀티바이트는 CRC32 로 눌러 담는다 */
typedef char trgm[3];

/* pg_bigm: 가변 길이 + 원본 바이트 + 부분 일치 플래그 */
typedef struct { bool pmatch; int8 bytelen; char str[8]; } bigm;
```

여기서 갈라지는 것:

| | pg_bigm | pg_trgm |
| --- | --- | --- |
| GIN 엔트리 타입 | `text` (원본 바이트) | `int32` (해시) |
| 엔트리 정렬 순서 | **사전순 — 접두어 구간이 성립한다** | 해시값 순 — 의미 없음 |
| `comparePartial` 지원 함수 | **있다** (`gin_bigm_compare_partial`) | 등록할 수 없다 |
| 해시 충돌 | 없다 | 가능 (Recheck 이 잡아준다) |

### (b) 조각이 n 보다 짧을 때

```c
/* pg_trgm */                      /* pg_bigm */
if (charlen < 3)                   if (charlen < 2) {
    return tptr;   /* 포기 */          compact_bigram(...);
                                       bptr->pmatch = true;  /* 부분 일치로 전환 */
                                   }
```

**(a) 가 (b) 를 가능하게 한다.** 엔트리가 정렬 가능한 원본 바이트라서 "이 글자로 시작하는 조각들"을 접두어 탐색할 수 있고, 그래서 1글자 검색까지 된다.

### (c) 나머지 차이

| | pg_bigm | pg_trgm |
| --- | --- | --- |
| n-gram | 2-gram (패딩 1+1) | 3-gram (패딩 2+1) |
| 문자 정규화 | 없음 (바이트 그대로) | `KEEPONLYALNUM` + `IGNORECASE` |
| 인덱스 | GIN 만 | GIN + **GiST** |
| 연산자 | `LIKE`, `=%` | `LIKE ILIKE ~ ~* % <% <<% <-> =` |
| KNN 정렬 | 없음 | **`ORDER BY <->` (GiST)** |
| 유사도 공식 | `공통 / max(len1,len2)` | `공통 / (len1+len2-공통)` 자카드 |
| Recheck 생략 | **1~2글자 무공백이면 자동 생략** | 없음 |
| 튜닝 손잡이 | `gin_key_limit` | `siglen` (GiST, PG13+) |
| 배포 | 소스 빌드 (PGXS) | contrib |
| 설치 권한 | **수퍼유저 필요** | **`trusted` — 비수퍼유저 OK** |
| 버전 관리 | git 태그 고정 | PostgreSQL 버전이 결정 |

## 4. 성능 — 실측

### 검색 ([`experiments/01`](experiments/01-keyword-length-and-selectivity), 200,000행)

| 검색어 | 글자 | 정답 | 인덱스 | 인덱스가 돌려준 후보 | Recheck 제거 | 인덱스 버퍼 | 실행 |
| --- | :-: | ---: | --- | ---: | ---: | ---: | ---: |
| 클라우드클럽 | 6 | 200 | bigm | 200 | 0 | 16 | 0.29 ms |
| 클라우드클럽 | 6 | 200 | trgm | 200 | 0 | **13** | 0.43 ms |
| 클둥이 | 3 | 200 | bigm | 200 | 0 | 7 | 0.96 ms |
| 클둥이 | 3 | 200 | trgm | 200 | 0 | **4** | 0.74 ms |
| **클클** | **2** | 200 | **bigm** | **200** | **0** | **4** | **0.52 ms** |
| **클클** | **2** | 200 | **trgm** | **200,000** | **199,800** | **5,097** | **231.57 ms** |
| 코아 | 2 | 60,006 | bigm | 60,006 | 0 | 13 | 13.8 ms |
| 코아 | 2 | 60,006 | trgm | 200,000 | 139,994 | 5,097 | 257.81 ms |

**2글자에서 trgm 의 후보가 테이블 전체와 같아진다** — `GIN_SEARCH_MODE_ALL` 이다. 인덱스를 통째로 읽고 나서 시퀀셜 스캔까지 하므로 **인덱스가 없느니만 못하다.**

**반대로 3글자 이상에서는 trgm 이 버퍼를 덜 읽는다.** 3-gram 조각이 더 희귀해 포스팅 리스트가 짧기 때문이다.

### 유지 비용 ([`experiments/02`](experiments/02-index-build-size-and-write), 200,000행)

| | `gin_bigm_ops` | `gin_trgm_ops` |
| --- | ---: | ---: |
| 인덱스 크기 (한국어) | **29.17 MB** | 39.03 MB |
| 인덱스 크기 (영문, Gutenberg) | **24.29 MB** | 35.00 MB |
| 빌드 시간 | 2.68s / 3.10s | 2.69s / 3.40s (동률) |
| INSERT (행당) | 18 µs | 19 µs (동률) |
| 유니크 조각 수 (한국어 2만행) | 50,398 | **121,558** |
| 유니크 조각 수 (영문 2만행) | **1,937** | 5,909 |
| 조각 수 (중복 제거 전) | 857,069 | 793,062 (비슷하다) |
| 조각 수 (문서별 중복 제거 후) | 791,053 | 763,255 |

**"2-gram 이라 조각이 많아서 인덱스가 크다"는 흔한 설명은 틀렸다.** 조각 수는 비슷하고(패딩까지 세면 단어당 둘 다 `L+1`), 인덱스는 오히려 bigm 이 25% 작다. 차이가 나타나는 지표는 **유니크 조각 수**이고, 그게 선택도를 결정한다.

<sub>`show_bigm()`/`show_trgm()` 이 돌려주는 것은 **문서별로 중복이 제거된** 조각이라, 그 숫자만 보면 영문에서 3-gram 이 더 많아 보인다. 생 조각 수는 오히려 2-gram 이 근소하게 많다 — 자세한 것은 [`experiments/02`](experiments/02-index-build-size-and-write).</sub>

<sub>**영문 대조군은 한 번 고쳤다.** 원래 어휘 12개 조합의 합성 데이터였는데 유니크 조각을 6.6배 적게(294 vs 1,937) 만들고 있었다. 지금은 Project Gutenberg 3권(퍼블릭 도메인)의 실제 산문이다. **같은 2-gram 인데 한국어 조각이 26배 다양하고 49배 희귀하다** — 이 실험에서 한국어 bigram의 선택도를 설명하는 요인이다.</sub>

### 저장 용량 ([`experiments/04`](experiments/04-storage-overhead-at-scale), 10만~500만 행)

**테이블 대비 배수**가 규모에 따라 떨어진다 — 유니크 엔트리(엔트리 트리)가 고정비이기 때문이다.

| 행 수 | `gin_bigm_ops` | `gin_trgm_ops` | `gist(siglen=256)` | `btree` (대조군) |
| ---: | ---: | ---: | ---: | ---: |
| 100,000 | 1.42× | 2.48× | 1.29× | 0.98× |
| 1,000,000 | 0.89× | 1.17× | 1.32× | 0.98× |
| 5,000,000 | **0.79×** | **1.01×** | 1.34× | 0.98× |

**용량 산정은 "테이블의 1~2.5배"** 로 잡되, 어휘가 다양한 데이터일수록 높은 쪽이다. `btree` 가 0.98× 로 일정한 것과 대비된다.

### 길이 · 패턴 ([`experiments/05`](experiments/05-pattern-and-length), 100만 행, 정답 500행)

순수 `LIKE`(인덱스 없음) 대비 — 3글자 이상 `%X%` 기준 **50~110배**. 그리고 **검색어 길이(3~20글자)는 거의 영향이 없다.**

| trgm, **2글자** | 인덱스 스캔 행 | 시간 |
| --- | ---: | ---: |
| `%클둥%` | **1,000,000** (전체) | **797 ms** |
| `클둥%` | 500 | **1.49 ms** |
| `%클럽` | 590 | **1.37 ms** |

**같은 2글자인데 패턴 모양만 바꾸면 535~580배 빨라진다** — `%` 로 감싸면 패딩을 못 붙여 트라이그램이 0개가 되기 때문이다. 3글자 이상에서는 패턴 모양이 무의미하고, **`pg_bigm` 은 어느 칸에서도 이 문제가 없다.**

<sub>인덱스가 전혀 없어도 `X%` 가 `%X%` 보다 3~4배 빠르다(15 vs 58 ms). 버퍼는 같고 CPU 비교 횟수만 다르다.</sub>

### 기능 ([`experiments/03`](experiments/03-operator-coverage-and-correctness), 100,014행)

| 조건 | bigm | trgm(GIN) | GiST |
| --- | --- | --- | --- |
| `LIKE '%6글자%'` | 후보 2 | 후보 2 | 후보 2 |
| `LIKE '%2글자%'` | **후보 1** | 후보 100,014 | 후보 100,014 |
| `ILIKE` | **Seq Scan** | 후보 2 | 후보 2 |
| `~` (ASCII) | **Seq Scan** | 후보 2 | 후보 2 |
| `~` (한글) | **Seq Scan** | 후보 100,014 | 후보 100,014 |
| `=` | **Seq Scan** | 후보 1 | 후보 1 |
| `ORDER BY <->` | 연산자 없음 | 정렬 불가 | **Index Scan** |

**한글 정규식은 두 확장 모두 인덱스로 가속되지 않는다** — trgm 은 `MAX_SIMPLE_CHR 0x7FF` 때문에(U+07FF 초과 문자는 정규식 컬러를 펼칠 수 없다), bigm 은 연산자 자체가 없어서.

### 유사도 점수

| 원본 → 변형 | `bigm_similarity()` | `similarity()` |
| --- | ---: | ---: |
| 신건 → 신컨 | **0.3333** | 0.2000 |
| 김신건 → 김신컨 | **0.5000** | 0.3333 |
| **클둥이 → 클동이** | **0.5000** | **0.1429** ← 기본 임계값 0.3 미달 |
| 클라우드클럽 → 클라으드클럽 | **0.7143** | 0.4000 |
| CloudClub → cloudclub | 0.6667 | **1.0000** |

**기본 임계값이 우연히 둘 다 0.3 이지만 재는 자가 다르다.** 한쪽에서 다른 쪽으로 옮길 때 임계값을 그대로 가져오면 안 된다.

### 전문검색으로 대신할 수 있나 ([`experiments/06`](experiments/06-fulltext-vs-ngram), 100만 행)

먼저 짚을 것 — **`tsvector`/`tsquery` 는 익스텐션이 아니라 PostgreSQL 코어다.** `CREATE EXTENSION` 이 필요 없다. 두 확장과 같은 층위에 놓고 "무엇이 빠른가"를 겨루는 것이 아니라, **"무엇을 못 하는가"** 를 봐야 한다.

`LIKE '%키워드%'` 를 정답으로 놓고 사전 없는 `'simple'` 설정으로 잰 재현율:

| 키워드 | LIKE(정답) | `tsquery` | 재현율 | `키워드:*` | 재현율 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 영화 | 313,428 | 118,437 | 37.8% | 239,651 | 76.5% |
| 배우 | 32,520 | 2,900 | **8.9%** | 24,100 | 74.1% |
| 재미 | 74,494 | 5,516 | **7.4%** | 67,524 | 90.6% |

**평균 20.4% → 접두어 `:*` 로 84.6%.** 조사가 붙어(`영화지만`) 별개 어휘소가 되기 때문이고, 키워드 하나가 실제 말뭉치에서 552~1,738가지 어휘소로 흩어진다. `:*` 로도 **키워드 앞에 뭔가 붙은 경우(`이영화`)는 원리상 못 잡는다.**

| | tsvector 만 | n-gram 만 |
| --- | --- | --- |
| 구절 검색 (`phraseto_tsquery`) | 45행 (`영화 <-> 연기`) — 위치를 저장하므로 | — |
| 관련도 랭킹 (`ts_rank`) | 있다 | 없다 (유사도는 랭킹이 아니다) |
| 어휘 중간 부분 문자열 (`%화가%`) | 445 (1.8%) | **25,366** |

**`tsvector` 는 "단어를 아는 대신 문자를 모르고", n-gram 은 "문자를 아는 대신 단어를 모른다."** 한국어에 형태소 사전을 붙이지 않았다면 앞의 "단어를 안다"가 성립하지 않는다.

<sub>인덱스 크기는 tsv 121 MB / bigm 123 MB / trgm 158 MB 로 앞 둘이 사실상 같다. 다만 분모인 테이블 291 MB 에 `tsv` 생성 컬럼이 이미 포함되어 있어 이 비교는 tsvector 쪽에 유리하게 기울어 있다.</sub>

<sub>**이 실험의 속도 표는 한 번 잘못 쟀다.** 인덱스 세 개를 동시에 둔 채 재서 "LIKE (bigm)" 줄 중 하나가 실제로는 trgm 을 타고 있었다 — 버퍼가 지문이 됐다. 다시 재면서 "쓴 인덱스" 열을 넣었고, 덤으로 **2글자 `영화` 를 trgm 으로 풀면 버퍼 2배·시간 17배**라는 것도 확인했다. 경위는 [`experiments/06`](experiments/06-fulltext-vs-ngram).</sub>

### 버전 ([`experiments/07`](experiments/07-postgres-version-matrix), 50만 행)

이 결론이 PostgreSQL 16 한정인지 확인하려고 16·17·18·19beta1 에서 다시 돌렸다.

| PG | bigm 인덱스 | trgm 인덱스 | bigm 빌드 | trgm 빌드 | 2글자 `%X%` trgm 후보 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 16 | 65.8 MB | 99.1 MB | 8.0s | 7.1s | 500,000 |
| 17 | 65.8 MB | 99.1 MB | 7.8s | 7.0s | 500,000 |
| 18 | 65.8 MB | 99.1 MB | **3.5s** | **3.7s** | 500,000 |
| 19beta1 | — | — | — | — | **pg_bigm 빌드 실패** |

**결정적 지표가 세 버전에서 한 자리도 다르지 않다.** 인덱스 크기·유니크 조각 수·recheck·버퍼 전부 동일하다. `GIN_SEARCH_MODE_ALL` 은 플래너의 선택이 아니라 `extractQuery()` 가 조건을 하나도 못 만든 결과이므로 **버전으로 해결되지 않는다.**

유일한 차이는 **인덱스 빌드 시간** — 17→18 에서 약 2배 빨라진다(2회 실행 모두 같은 방향, **원인은 확인하지 못했다**).

[`05`](experiments/05-pattern-and-length) 의 길이×패턴 격자 45칸도 버전마다 다시 쟀다. **2글자 `%X%` 에서 trgm 이 무너지는 것(447~480 ms)도, 인덱스가 없을 때만 접두어가 0.30 배로 빨라지는 것도 세 버전에서 그대로 재현된다.**

**그리고 `pg_bigm` 1.2 는 PostgreSQL 19beta1 에서 빌드되지 않는다.** PG19 에서 전역 `database_ctype_is_c` 가 `pg_locale_t` 의 필드로 옮겨지고 `char2wchar()` 가 헤더에서 빠졌다. 이 카탈로그의 Dockerfile 주석이 "PostgreSQL 16~19 지원"이라고 적고 있었는데 **그 서술은 사실이 아니다.**

## 5. 이번 조사로 정정한 것

| 흔한 서술 | 실측 결과 |
| --- | --- |
| "`pg_trgm` 은 `KEEPONLYALNUM` 때문에 한글을 걸러낸다" | **틀렸다.** `show_trgm('가나다라')` 는 조각 5개를 정상 생성한다. `ISWORDCHR` 가 쓰는 `t_isalnum_with_len()` 은 멀티바이트를 인식한다 |
| "`KEEPONLYALNUM` 이 한글 문제의 원인" | **구두점 문제다.** `192.168.0.1` 이 `192`/`168`/`0`/`1` 로 쪼개진다 |
| "2-gram 이라 조각이 많아 인덱스가 크다" | **틀렸다.** 생 조각 수는 857k vs 793k 로 비슷하고 bigm 인덱스가 25% 작다. 차이가 나타나는 지표는 **유니크 조각 수**(50,398 vs 121,558) |
| "pg_bigm 이 무조건 빠르다" | **3글자 이상에서는 trgm 이 버퍼를 덜 읽는다.** 그리고 "bigm 이 1.5~2배 빠르다"고 적었던 것도 20회 중앙값으로 재니 **노이즈여서 철회했다** |
| "인덱스 빌드/크기 차이는 5~13%" (이 카탈로그의 이전 실험) | 합성 데이터 탓이었다. **실제 말뭉치에서는 25%** |
| "`pg_bigm` 의 similarity 는 이름뿐" | **조각 기반 유사도 검색이고 GIN 인덱스도 탄다** |
| "`pg_bigm` 1.2 는 PostgreSQL 16~19 를 지원한다" | **19beta1 에서 빌드되지 않는다** (`database_ctype_is_c` 제거) |
| "버전을 올리면 2글자 함정이 나아진다" | **16·17·18 에서 지표가 한 자리도 다르지 않다** |
| "`trial` 을 찾으면 `trivial` 이 거짓 양성" (3-gram 기준) | **3-gram 에서는 아니다** — `ria` 가 없어 인덱스 단계에서 탈락한다. 2-gram 기준으로는 맞다 |

## 6. 어느 쪽을 고를 것인가

```
검색어가 2글자 이하가 흔한가?
├─ 예 → 수퍼유저 권한이 있고 소스 빌드가 가능한가?
│        ├─ 예 → pg_bigm
│        └─ 아니오 → pg_trgm + 패턴 우회 ('키워드%' 또는 '% 키워드 %')
└─ 아니오 → 정규식 / KNN 정렬 / ILIKE 가 필요한가?
            ├─ 예 → pg_trgm  (KNN 이면 GiST, 아니면 GIN)
            └─ 아니오 → 둘 다 무방. 설치가 쉬운 pg_trgm 이 기본값
```

**구두점이 의미를 갖는 검색(IP·버전·경로·식별자)이나 대소문자를 구분해야 하는 검색이면 길이와 무관하게 `pg_bigm` 이다.**

관련도 랭킹이나 어간 추출이 필요하면 애초에 n-gram 이 아니라 전문검색을 봐야 한다 — [`web/#/fulltext/tsvector`](../../web/README.md).
