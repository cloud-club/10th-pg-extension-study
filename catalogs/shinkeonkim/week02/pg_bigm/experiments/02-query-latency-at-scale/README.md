# 실험 02 — 규모별 LIKE 검색 실행 시간: 인덱스 없음 vs bigm vs trgm

## 질문

`labs/04-comparison-and-ops/` 는 20,000행 고정 규모에서 `EXPLAIN`(플래너 **추정 비용**)으로 "trgm 이 짧은 키워드에서 몇 백 배 비싸다"는 걸 보였다. 이 실험은 그 주장을 **실제 실행 시간**으로, 그것도 **데이터 규모를 늘려가며** 검증한다.

## ⚠️ 이 실험은 이 카탈로그의 '측정 원칙'이 나온 자리다

**1차 판은 세 번째 실행에서 결과가 재현되지 않아 핵심 주장을 철회해야 했다.** 사후 조사에서 원인을 둘 찾았다.

1. **`random()` 에 시드가 없어** 실행마다 데이터 자체가 달라졌다.
2. **"짧은 키워드"로 쓴 `검색` 이 어휘 15문장 중 5문장에 들어 있어 전체 행의 약 55.6% 와 매치됐다.** "흔치 않은 짧은 키워드"라는 의도한 시나리오가 전혀 아니었고, **선택도가 통제되지 않으니 "인덱스가 이득인가"를 물을 수 없는 상태였다.**

**2차 판에서 셋을 고쳤다.**

| | 1차 | 2차 |
| --- | --- | --- |
| 데이터 | 어휘 15문장 + `random()` | **NSMC 말뭉치 + `generate_series` 나머지** (완전히 결정적) |
| 짧은 키워드 | `검색` — **매치 55.6%** (통제 실패) | `클클` — **정확히 0.1%** 에 주입하고 실제 선택도를 다시 잰다 |
| 주 지표 | 벽시계 시간(3회 평균) | **`EXPLAIN` 의 결정적 지표**(후보 행·recheck·버퍼). 시간은 보조 |

## 방법

```bash
./bench.sh                     # 5만 / 20만 / 100만 행
INJECT_MOD=1000 ./bench.sh     # 주입 비율 조정 (기본 1/1000 = 0.1%)
./bench.sh down                # 정리만
```

- 데이터: NSMC 말뭉치를 `id` 나머지로 순환 참조. **난수를 쓰지 않는다.**
- 키워드 둘 다 **0.1% 에 정확히 주입**한다 — 길이만 변수로 남기기 위해서다.
  - **짧은 키워드** `클클`(2글자) — pg_trgm 이 조각을 못 만드는 구간
  - **긴 구절** `클라우드클럽`(6글자) — 둘 다 정상 동작하는 대조군
  - `클클` 은 `클라우드클럽` 의 부분 문자열이 **아니므로** 정답 행수가 오염되지 않는다.
- 각 규모 × 키워드마다 (A) 인덱스 없음 (B) `gin_bigm_ops` (C) `gin_trgm_ops` 를 잰다.
- 실제 선택도를 매 규모마다 다시 재서 함께 기록한다.

## 분석

### 1. 선택도를 통제하니 결과가 깨끗해졌다

1차 판에서 실행마다 자릿수가 달라지던 칸이 **이번에는 전부 안정적이다.** 결정적 지표를 보면 이유가 분명하다 — **인덱스 스캔이 돌려준 행이 정확히 정답 행 수(bigm)이거나 정확히 테이블 전체(trgm)** 다. 흔들릴 여지가 없는 값이다.

> **1차 판의 불안정은 "측정이 부정확해서"가 아니라 "재는 대상이 통제되지 않아서"였다.** 55.6% 가 매치되는 상태에서는 비트맵 힙 스캔의 무작위 I/O 패턴이 시간을 지배하는데, `random()` 탓에 그 물리적 배치가 실행마다 달랐다.

### 2. `gin_trgm_ops` 는 2글자 검색어에서 **인덱스가 없느니만 못하다** — 규모와 무관하게

| 행 수 | 인덱스 없음 | trgm | trgm 이 **더 느린 배수** |
| ---: | ---: | ---: | ---: |
| 50,000 | 8.27 ms | 84.3 ms | **10.2배** |
| 200,000 | 13.08 ms | 209.1 ms | **16.0배** |
| 1,000,000 | 61.44 ms | 736.0 ms | **12.0배** |

**1차 판의 "6~10배"라는 관찰은 그대로 재현됐다**(이번엔 10~16배). 그리고 이제 **왜** 그런지가 지표에 직접 보인다 — 인덱스 스캔이 **테이블 전체를 후보로 올리고**(50,000 / 200,000 / 1,000,000), Recheck 이 그 99.9% 를 힙에서 걸러낸다. **인덱스 읽기 비용을 낸 뒤에 시퀀셜 스캔까지 하는 셈**이다.

`GIN_SEARCH_MODE_ALL` 의 지문이 이것이다 — 자세한 것은 [`web/#/foundations/recheck`](../../../../web/README.md).

### 3. 6글자 구절에서는 둘이 동률이다

`클라우드클럽` 칸을 보면 세 규모 모두 bigm 과 trgm 이 사실상 같다(0.10~0.50 ms, 버퍼 13~18). **문제는 "짧은 검색어"에서만 나타나고, 길면 우열이 없다.**

### 4. 인덱스가 주는 이득은 규모에 비례해 커진다

`클라우드클럽` 기준으로 인덱스 없음 대비 bigm:

| 행 수 | 인덱스 없음 | bigm | 배수 |
| ---: | ---: | ---: | ---: |
| 50,000 | 8.74 ms | 0.10 ms | **87배** |
| 200,000 | 13.05 ms | 0.15 ms | **87배** |
| 1,000,000 | 59.73 ms | 0.50 ms | **119배** |

시퀀셜 스캔은 행 수에 선형으로 늘지만(8.7 → 13.1 → 59.7), 인덱스는 정답 행 수에만 비례하므로(0.10 → 0.15 → 0.50) **격차가 벌어진다.**

## 한계

- **정답 0.1% 한 점에서만 쟀다.** 선택도가 낮아지면(매치가 많아지면) 인덱스 이득이 줄어드는데, 그 축은 [`bigm-vs-trgm/experiments/01`](../../../bigm-vs-trgm/experiments/01-keyword-length-and-selectivity) 에서 다섯 점으로 따로 본다.
- 시간은 워밍업 1회 + 3회 평균이다. **결정적 지표는 흔들릴 수 없는 값이지만 시간은 머신 부하에 좌우된다** — 자릿수 차이만 해석할 것.
- 검색어가 길이별로 하나씩뿐이다.
- 시퀀셜 스캔 강제(`enable_bitmapscan/indexscan=off`)는 "인덱스가 아예 없는 테이블"을 정확히 흉내내지는 못한다. 다만 실제로 인덱스가 없어도 같은 경로가 선택되므로 해석에는 문제가 없다.
- 단일 Docker 컨테이너, 공유 CPU 환경이다.
