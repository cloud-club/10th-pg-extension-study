# 실험 01 — 인덱스 빌드 시간과 크기: pg_bigm vs pg_trgm

## 질문

`docs/01-what-and-why.md` 는 공식 문서를 인용해 "인덱싱 가능한 컬럼 최대 크기가 pg_bigm(~102MB)이 pg_trgm(~228MB)보다 작다"고만 적어뒀다. 그런데 **일상적인 테이블 크기에서 실제로 인덱스를 만드는 시간과 완성된 인덱스의 디스크 크기는 둘이 얼마나 다를까?**

## ⚠️ 이 실험은 한 번 갱신됐다

**1차 판은 어휘 15문장을 `random()` 으로 조합한 합성 데이터를 썼다.** 그 결과 "빌드 시간·크기 차이는 5~13% 수준"이라는 결론이 나왔는데, 실제 한국어 말뭉치로 다시 재보니 **크기 차이가 27~73%** 였다. **데이터가 결론을 바꾼 것이다.**

| | 1차 (합성, 어휘 15문장) | 2차 (NSMC 말뭉치) |
| --- | --- | --- |
| 100만 행 bigm 크기 | 103.7 / 115.2 MB | **208.0 MB** |
| 100만 행 trgm 크기 | 112.6 / 130.5 MB | **263.3 MB** |
| **크기 차이** | **+8~13%** | **+27%** |
| 5만 행 크기 차이 | 약 +6% | **+73%** |
| 재현성 | `random()` 탓에 실행마다 달랐다 | **완전히 결정적** |

두 가지를 동시에 고쳤다.

1. **데이터를 실제 말뭉치로** — [NSMC](https://github.com/e9t/nsmc)(CC0) 문장 두 개를 이어 붙여 평균 84자.
2. **`random()` 제거** — `generate_series` 값의 나머지 연산으로 순환 참조하므로 실행마다 바이트 단위로 같다.

## 방법

```bash
./bench.sh          # 5만 / 20만 / 100만 행
./bench.sh down     # 정리만
```

- 컨테이너: pg_bigm(소스 빌드, `v1.2-20250903`) + pg_trgm(contrib).
- 데이터: NSMC 말뭉치 문장 두 개를 `id` 나머지로 골라 이어 붙인다(평균 84자). **난수를 쓰지 않는다.**
- 각 규모마다 `CREATE INDEX ... gin_bigm_ops` 시간 측정 → 삭제 → `gin_trgm_ops` 측정. `pg_relation_size()` 로 크기도 기록.
- 환경: Docker Desktop / 랩톱. **다른 컨테이너와 CPU 를 공유하므로 절대 시간에는 노이즈가 있다.**

## 결과 (실측, NSMC 말뭉치)

| 행 수 | 평균 길이 | bigm 빌드 | **bigm 크기** | trgm 빌드 | **trgm 크기** | trgm / bigm |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 50,000 | 84자 | 1.34s | **16.94 MB** | 1.27s | **29.29 MB** | **1.73×** |
| 200,000 | 84자 | 5.27s | **50.34 MB** | 4.86s | **75.04 MB** | **1.49×** |
| 1,000,000 | 84자 | 28.12s | **208.00 MB** | 32.56s | **263.34 MB** | **1.27×** |

## 분석

### 1. 크기 차이는 "5~13%"가 아니라 **27~73%** 다

합성 데이터가 격차를 크게 줄이고 있었다. 이유는 [`bigm-vs-trgm/experiments/02`](../../../bigm-vs-trgm/experiments/02-index-build-size-and-write) 에서 밝힌 것과 같다 — **반복도가 극단적으로 높으면 두 인덱스 모두 유니크 조각이 적어져 격차가 사라진다.** 어휘 15문장이면 100만 행이어도 유니크 조각은 수백 개뿐이다.

실제 말뭉치에서는 3-gram 의 유니크 조각이 2-gram 의 2.4배(121,558 vs 50,398)이고, **그 차이가 엔트리 트리 크기에 그대로 나타난다.**

### 2. 격차가 규모에 따라 **줄어든다** (1.73× → 1.27×)

이것도 구조로 설명된다. 인덱스는 **엔트리 트리(유니크 조각 수 = 고정비) + 포스팅(총 조각 수 = 변동비)** 이다.

- 5만 행: 고정비 비중이 크다 → 유니크 조각이 2.4배 많은 trgm 이 크게 불리 → **1.73×**
- 100만 행: 변동비가 지배한다 → 총 조각 수는 두 확장이 비슷하므로 격차가 줄어든다 → **1.27×**

같은 구조를 규모별로 본 것이 [`bigm-vs-trgm/experiments/04`](../../../bigm-vs-trgm/experiments/04-storage-overhead-at-scale) 다.

### 3. 빌드 시간은 사실상 동률이다

| 행 수 | bigm | trgm |
| ---: | ---: | ---: |
| 50,000 | 1.34s | 1.27s |
| 200,000 | 5.27s | 4.86s |
| 1,000,000 | 28.12s | 32.56s |

**어느 쪽이 확실히 빠르다고 말할 근거가 없다.** 순서가 규모마다 뒤집히고, 차이도 5~15% 로 이 환경의 노이즈 범위다. **1차 판의 "빌드 시간은 동률"이라는 결론은 그대로 유효하다** — 바뀐 것은 크기 쪽이다.

### 4. 문서의 "~102MB vs ~228MB" 는 다른 이야기였다

이건 **컬럼 하나의 최대 허용 크기 제한**(인덱싱 가능한 값의 상한)이지, "같은 데이터를 넣었을 때 인덱스가 몇 배 커지는가"가 아니다. 이번 실험으로 그 구분이 분명해졌다 — 실제 배수는 **1.27~1.73배**다.

### 5. 그래서 무엇을 골라야 하나

**빌드 비용만 보면 여전히 둘 중 하나를 고를 이유가 없다.** 크기는 bigm 이 확실히 작지만(27~73%), 그것만으로 결정할 문제는 아니다. 실제 선택 기준은 **검색어 길이**이고, 그건 [`bigm-vs-trgm/experiments/01`](../../../bigm-vs-trgm/experiments/01-keyword-length-and-selectivity) 에서 답한다.

## 한계

- **크기 차이가 문서 길이에 의존한다.** 여기는 평균 84자(문장 2개)인데, 문장 1개(평균 35자)로 잰 [`bigm-vs-trgm/02`](../../../bigm-vs-trgm/experiments/02-index-build-size-and-write) 에서는 20만 행에서 25% 였다. **같은 20만 행인데 49% vs 25%** — 문서가 길수록 격차가 커진다.
- 각 조건 1회 측정이다. 데이터 생성은 완전히 결정적이므로 **크기는 재현되지만**, 시간은 머신 부하에 좌우된다.
- 한국어 말뭉치 하나(NSMC, 영화 리뷰)로만 쟀다. 영문은 유니크 조각 분포가 크게 달라 결과가 달라진다([`bigm-vs-trgm/02`](../../../bigm-vs-trgm/experiments/02-index-build-size-and-write) 의 Gutenberg 대조군).
- 500만 행 이상은 재지 않았다. 규모별 추세는 [`bigm-vs-trgm/04`](../../../bigm-vs-trgm/experiments/04-storage-overhead-at-scale) 참고.
- `pg_relation_size()` 만 봤다 — TOAST·FSM·VM 은 제외했다.
