# 실험 00 — Before / After 의 실행 계획은 실제로 언제 바뀌는가

## 질문

[`docs/01-what-and-why.md`](../../docs/01-what-and-why.md) 의 Before/After 는 이렇게 적혀 있었다.

```sql
-- Before: 인덱스 없이 - 테이블 전체를 훑는다
SELECT * FROM docs WHERE doc LIKE '%클둥이%';

-- After: 쿼리는 그대로, 인덱스만 얹는다
CREATE INDEX docs_idx ON docs USING gin (doc gin_bigm_ops);
SELECT * FROM docs WHERE doc LIKE '%클둥이%';
```

**그런데 정말 그렇게 되는가?** 플래너는 "인덱스가 있으니 쓴다"가 아니라 **비용을 비교해서 더 싼 쪽을 고른다.** 그러면:

- 테이블이 작으면 인덱스가 있어도 `Seq Scan` 이 더 쌀 텐데, **몇 행부터 뒤집히나?**
- 매치되는 행이 너무 많으면(선택도가 낮으면) 어차피 다 읽어야 하니 `Seq Scan` 이 더 쌀 텐데, **그 경계는?**

문서에 EXPLAIN 이 한 줄도 없었다. 그래서 **행 수와 선택도를 격자로 놓고 전환점을 실제로 찾았다.**

## 방법

```bash
./bench.sh          # 빌드 -> 측정 -> 정리
./bench.sh keep     # 컨테이너를 남긴다 (psql 로 더 파보고 싶을 때)
```

- **`enable_seqscan` 을 절대 건드리지 않는다.** 다른 lab 들은 인덱스 경로를 보려고 강제로 껐지만, 이 실험의 질문은 정확히 **"플래너가 자유롭게 골랐을 때 무엇을 고르나"** 다. 강제로 끄면 질문 자체가 사라진다.
- **데이터: 실제 한국어 말뭉치.** [NSMC](https://github.com/e9t/nsmc)(Naver Sentiment Movie Corpus, **CC0**) 199,993문장을 `bench.sh` 가 내려받아 쓴다. [Korpora](https://github.com/ko-nlp/Korpora) 가 소개하는 말뭉치 중 라이선스·접근성 때문에 이걸 골랐다. 말뭉치 파일은 저장소에 커밋하지 않고 `.corpus/` 에 캐시한다.
- **행 수**: 100 / 1,000 / 10,000 / 100,000 / 1,000,000. 전환점이 작은 쪽에 있을 것으로 보고 아래를 촘촘히 잡았다.
- **검색어**: 스터디 공용 예시 문자열을 **정해진 비율로 주입**한다.

  | 검색어 | 글자 수 | 주입 조건 | 의도 |
  | --- | :-: | --- | --- |
  | `클둥이` | 3 | `id % 1000 = 0 OR id = 50` | 희귀 (약 0.1%) |
  | `클클` | 2 | `id % 1000 = 1` | 희귀 (약 0.1%) — 2글자여도 pg_bigm 은 조각을 만든다 |
  | `코아` | 2 | `id % 10 BETWEEN 0 AND 2` | **흔함 (30%)** ← 선택도 축 |

  주입에 `random()` 이 아니라 **`id` 나머지**를 쓴다. 시드와 무관하게 항상 정확히 같은 비율, 같은 물리적 배치가 나오므로 실행마다 결과가 흔들리지 않는다. ([`../02-query-latency-at-scale/`](../02-query-latency-at-scale) 가 겪은 재현 실패의 원인이 바로 이 지점이었다.)
- 각 (행 수 × 검색어)마다 **정답 행 수와 실제 선택도를 먼저 측정해 기록**한 뒤, 인덱스 없이 / 있이 각각 `EXPLAIN` 을 떠서 스캔 방식을 비교한다.

## 결과 (실측)

말뭉치 출처: **NSMC** · PostgreSQL 16 / pg_bigm 1.2 (`v1.2-20250903`) · Docker (3 CPU / 4 GB)

| 행 수 | 검색어 | 정답 행 수 | 선택도 | **인덱스 없음** | **인덱스 있음** | 인덱스 스캔이 돌려준 행 |
| ---: | --- | ---: | ---: | --- | --- | ---: |
| 100 | 클둥이 | 1 | 1.000% | Seq Scan | **Seq Scan** | — |
| 100 | 클클 | 1 | 1.000% | Seq Scan | **Seq Scan** | — |
| 100 | 코아 | 30 | 30.000% | Seq Scan | **Seq Scan** | — |
| 1,000 | 클둥이 | 2 | 0.200% | Seq Scan | Bitmap Heap Scan | 2 |
| 1,000 | 클클 | 1 | 0.100% | Seq Scan | Bitmap Heap Scan | 1 |
| 1,000 | 코아 | 300 | 30.000% | Seq Scan | **Seq Scan** | — |
| 10,000 | 클둥이 | 11 | 0.110% | Seq Scan | Bitmap Heap Scan | 11 |
| 10,000 | 클클 | 10 | 0.100% | Seq Scan | Bitmap Heap Scan | 10 |
| 10,000 | 코아 | 3,000 | 30.000% | Seq Scan | Bitmap Heap Scan | 3,000 |
| 100,000 | 클둥이 | 101 | 0.101% | Seq Scan | Bitmap Heap Scan | 101 |
| 100,000 | 클클 | 100 | 0.100% | Seq Scan | Bitmap Heap Scan | 100 |
| 100,000 | 코아 | 30,003 | 30.003% | Seq Scan | Bitmap Heap Scan | 30,003 |

| 1,000,000 | 코아 | 300,035 | 30.004% | **Parallel Seq Scan** | Bitmap Heap Scan | 300,035 |

`Rows Removed by Index Recheck` 는 **모든 칸에서 0** 이고, **인덱스 스캔이 돌려준 행이 정답 행 수와 정확히 일치한다** — 인덱스가 후보를 정답까지 완전히 좁혔다는 뜻이다.

**이 표는 두 번 연속 실행에서 15개 칸 전부 동일했다.**

## 분석

### 1. "인덱스를 만들면 인덱스를 탄다"는 문서의 서술은 **틀렸다**

**100행에서는 인덱스가 있어도 세 검색어 모두 `Seq Scan` 이다.** 100행짜리 테이블은 한두 페이지라 통째로 읽는 게 인덱스를 뒤지는 것보다 싸고, 플래너가 그걸 정확히 계산한다. 문서의 Before/After 예시를 작은 테이블에서 그대로 따라 하면 **After 에서도 `Seq Scan` 이 나오고, "인덱스가 안 먹네?" 하고 오해하기 딱 좋다.**

### 2. 전환점은 행 수 하나로 정해지지 않는다 — 선택도가 같이 결정한다

1,000행 칸을 보면 답이 나온다.

| 1,000행 | 선택도 | 인덱스 있을 때 |
| --- | ---: | --- |
| 클둥이 / 클클 | 0.1~0.2% | **Bitmap Heap Scan** |
| 코아 | 30% | **Seq Scan** |

**같은 테이블, 같은 인덱스인데 검색어에 따라 플랜이 갈린다.** 30%가 매치되면 어차피 힙 페이지를 거의 다 읽어야 하므로, 인덱스를 거치는 건 순수한 추가 비용이다. 30% 짜리가 인덱스를 타기 시작하는 건 **10,000행부터**였다.

즉 전환점은 대략 이렇게 그려진다.

```
          선택도 30%  |  ~1,000행: Seq Scan     |  10,000행~: Bitmap Heap Scan
          선택도 0.1% |  ~100행:   Seq Scan     |   1,000행~: Bitmap Heap Scan
                      +-------------------------+------------------------------
```

**희귀한 검색어일수록 더 작은 테이블에서부터 인덱스가 이긴다.** 당연해 보이지만, "몇 행부터 인덱스를 만들어야 하나?"라는 질문에 행 수만으로 답할 수 없다는 뜻이기도 하다.

### 3. 100만 행에서 인덱스 없는 쪽은 `Parallel Seq Scan` 이 된다

비교 대상이 "느린 순차 스캔"에서 "여러 코어가 나눠 읽는 순차 스캔"으로 바뀐다. **인덱스의 상대적 이득이 그만큼 줄어든다**는 뜻이라, 벤치마크를 읽을 때 주의해야 할 지점이다.

### 4. 2글자 `클클` 이 1,000행 규모부터 정확히 정답만 집어낸다

`pg_bigm` 이 2-gram 이라 **2글자 검색어에서도 온전한 조각을 만들 수 있기 때문**이다. 같은 조건에서 `pg_trgm` 은 조각을 하나도 못 만들어 인덱스 전체를 훑는다 — 그 대조는 [`../../../bigm-vs-trgm/experiments/01-keyword-length-and-selectivity/`](../../../bigm-vs-trgm/experiments/01-keyword-length-and-selectivity) 에서 나란히 잰다.

## 측정 과정에서 고친 것 (방법론 버그)

**처음에는 `CREATE INDEX` 뒤에 `ANALYZE` 만 돌렸다.** 그랬더니 100만 행에서 `클둥이`/`클클` 둘 다 인덱스 스캔이 정답의 약 2배(2,000 / 1,997)를 돌려줬다. seed 단계의 `UPDATE` 들이 남긴 죽은 튜플이 원인이었는데, **죽은 튜플은 가시성 검사에서 조용히 걸러지므로 `Rows Removed by Index Recheck` 에 잡히지 않아** 표만 봐서는 원인을 알 수 없었다.

`CREATE INDEX` 뒤에 `VACUUM ANALYZE` 를 한 번 더 돌리도록 고쳤고, `클클` 은 1,997 → 1,000 으로 정상화됐다. 측정하려는 것은 "인덱스가 후보를 얼마나 좁히나"이지 "죽은 튜플이 얼마나 끼나"가 아니므로, 깨끗한 인덱스에서 재는 것이 맞다.

## 측정 과정에서 고친 것 (방법론 버그) — 그리고 그 해결

**처음에는 `CREATE INDEX` 뒤에 `ANALYZE` 만 돌렸다.** 그랬더니 100만 행에서 `클둥이`/`클클` 둘 다 인덱스 스캔이 정답의 약 2배(2,000 / 1,997)를 돌려줬다. seed 단계의 `UPDATE` 들이 남긴 죽은 튜플이 원인인데, **죽은 튜플은 가시성 검사에서 조용히 걸러지므로 `Rows Removed by Index Recheck` 에 잡히지 않아** 표만 봐서는 원인을 알 수 없었다.

`CREATE INDEX` 뒤에 `VACUUM ANALYZE` 를 한 번 더 돌리도록 고쳤다. 측정하려는 것은 "인덱스가 후보를 얼마나 좁히나"이지 "죽은 튜플이 얼마나 끼나"가 아니므로, 깨끗한 인덱스에서 재는 것이 맞다.

**고친 직후 실행에서는 `클클` 만 1,997 → 1,000 으로 정상화되고 `클둥이` 는 여전히 2,000 이어서, 한동안 "미해결"로 기록해뒀다.** 그런데 **재현성 검증을 위해 다시 두 번 연속 돌려보니 두 실행 모두 1,001(= 정답)** 이 나왔다.

| 시점 | 100만 행 `클둥이` 인덱스 스캔 행 |
| --- | ---: |
| `VACUUM` 추가 전 | 2,000 |
| `VACUUM` 추가 직후 (머신에 다른 실험 컨테이너가 동시 실행 중) | 2,000 |
| 재현성 검증 1회차 (머신 유휴) | **1,001** |
| 재현성 검증 2회차 (머신 유휴) | **1,001** |

**즉 `VACUUM` 수정이 옳았고, 그 직후 실행에서 안 먹힌 것은 다른 컨테이너들이 CPU 를 점유한 상태에서 정리가 덜 된 탓으로 보인다.** 다만 그 인과를 직접 확인하지는 못했으므로(예: `pg_stat_user_tables.n_dead_tup` 을 단계별로 찍어보지 않았다), **"머신 부하가 낮을 때 두 번 연속 정답과 일치했다"는 사실만 기록한다.**

<sub>이 카탈로그는 [`../02-query-latency-at-scale/`](../02-query-latency-at-scale) 에서 재현되지 않은 주장을 철회한 적이 있고, 여기서는 반대로 **"미해결"로 남겨둔 것이 재현 검증에서 해결된** 사례다. 어느 쪽이든 원칙은 같다 — **한 번 재고 결론 내지 않는다.**</sub>

## 한계

- Docker 컨테이너에 3 CPU / 4 GB 만 할당된 랩톱 환경이다. **전환점의 정확한 행 수는 `random_page_cost`, `effective_cache_size`, `shared_buffers`, 병렬 설정에 따라 달라진다** — 이 표의 값을 프로덕션 임계값으로 그대로 쓰면 안 된다. 읽어야 할 것은 **"두 축(행 수 · 선택도)이 함께 전환점을 정한다"는 구조**다.
- 선택도는 0.1% 와 30% 두 점만 봤다. 그 사이(1%, 5%, 10%)를 촘촘히 보면 경계가 더 선명해질 것이다.
- **각 조건을 2회 측정했고 15개 칸 전부 동일했다.** 다만 경계에 아주 가까운 조건(예: 선택도 30% 가 1,000행과 10,000행 사이에서 뒤집히는 지점)에서는 통계 갱신 타이밍에 따라 흔들릴 수 있다.
- `LIKE` 만 봤다. 유사도 검색(`=%`)은 선택도 추정 방식이 달라 전환점도 다를 수 있다.
- 검색어를 `UPDATE` 로 주입하므로 죽은 튜플이 생긴다. 위 "방법론 버그" 참고 — `INSERT` 시점에 주입하도록 바꾸면 더 깨끗할 것이다.
