# 실험 02 — `pg_stat_statements.max` 크기와 eviction 의 지연시간 영향

## 질문

`docs/02-internals-and-source.md` 는 소스 코드(`entry_dealloc()`)를 근거로 "해시테이블이 가득 차면 한 번의 GC 가 `max(10, 전체의 5%)` 개를 한꺼번에 정리한다"고 설명한다. 그런데 이 GC 가 **실제로 그 순간의 쿼리 실행을 눈에 띄게 느리게 만드는가?** `pg_stat_statements.max` 를 작게 잡아 GC 가 자주 도는 상황과, 크게 잡아 GC 가 아예 안 도는 상황을 비교하면 답을 알 수 있다.

## 방법

- `labs/04-dba-playbook-and-pitfalls` 에서 쓴 트릭을 재사용: `SELECT length('a'), length('a'), ...` 처럼 함수 호출 개수를 1개씩 늘려 매번 다른 "쿼리 모양"(= 다른 `queryid`)을 만든다. PostgreSQL 은 타겟리스트 컬럼 수를 **최대 1664개**로 제한하므로, 이 방식으로 만들 수 있는 서로 다른 모양의 최대 개수도 거기서 막힌다 - 그래서 N=1600 으로 실험했다(N=3000 으로 처음 시도했다가 `TooManyColumns` 에러를 실제로 만나고 나서 줄인 것 - 아래 "겪은 시행착오" 참고).
- `measure.py` (psycopg2) 가 컨테이너 **안에서** 1600개의 문장을 순서대로 실행하며 **문장 하나하나의 왕복 시간**을 `time.perf_counter()` 로 잰다 (클라이언트가 컨테이너 밖에 있으면 호스트-컨테이너 네트워크 왕복이 노이즈로 섞인다).
- 두 설정을 비교: `pg_stat_statements.max=200`(1600개 중 처음 200개를 채운 뒤부터는 계속 GC 가 돎) vs `max=5000`(1600 < 5000 이라 GC 가 단 한 번도 안 일어남).
- 재현성 확인을 위해 **동일 조건으로 2회 반복 실행**했다 - 아래 표는 그중 대표 1회, 본문에 두 번째 실행값도 함께 적어 결과가 일관적임을 보인다.

**환경**: 실험 01 과 동일 (Docker Desktop on macOS/arm64, `nproc`=12, 공유 개발 머신).

## 결과

| 설정 | dealloc (GC 횟수) | 최종 저장 항목수 | 평균 지연 (ms) | p95 (ms) | 최대 (ms) |
| --- | --- | --- | --- | --- | --- |
| `max=200` (1회차) | **141** | 192 | 1.417 | 2.551 | 5.034 |
| `max=5000` (1회차) | **0** | 1602 | 1.457 | 2.560 | 7.390 |
| `max=200` (2회차, 재현) | **141** | 192 | 1.404 | 2.518 | 4.948 |
| `max=5000` (2회차, 재현) | **0** | 1602 | 1.468 | 2.635 | 8.133 |

두 설정 모두 실제로 실행 도중 전체 문장의 절반 지점(테이블이 이미 다 찬 이후 구간)만 따로 봐도 마찬가지였다 (`max=200`: 평균 2.04ms / `max=5000`: 평균 2.13~2.16ms - 오히려 `max=200`쪽이 근소하게 더 빠르다).

## 분석

**이 단일 세션 실험에서 GC에 기인한 지연 증가를 분리해 검출하지 못했다.** 141번의 GC 가 실제로 일어난 `max=200` 쪽이 평균·p95·최대 지연 모두 GC 가 한 번도 없었던 `max=5000` 쪽과 사실상 같거나(오히려 최대 지연은 `max=200` 쪽이 더 작았다). 두 반복에서 같은 방향을 관찰했지만, 이것만으로 비용이 없거나 우연이 아니라고 확정할 수 없다.

`entry_dealloc()`은 배타적 LWLock을 보유한 상태에서 usage를 기준으로 항목을 정렬하고 낮은 usage 항목을 제거한다. 메모리 안에서 처리하더라도 정렬·잠금 비용은 존재한다. 이 실험은 GC 구간을 직접 계측하지 않아 전체 문장 시간과 그 비용을 분리할 수 없다. **dealloc은 통계 커버리지 손실 신호이며 동시성 하의 락 경합 비용을 배제하는 지표가 아니다.**

## 겪은 시행착오 (그대로 남긴다)

처음에 N=3000 으로 설계했으나 `psycopg2.errors.TooManyColumns: target lists can have at most 1664 entries` 로 실패했다 - PostgreSQL 자체의 타겟리스트 컬럼 수 제한(1664)에 부딪힌 것이다. `labs/04` 에서는 1200개로 이 한계 근처까지 갔지만 넘지는 않았어서 발견되지 않았던 제약이다. N=1600 으로 줄여 재현했다.

## 한계

- 이 GC는 인메모리·락 보유 상태의 연산이지만, 비용을 직접 측정하지 않았으므로 "eviction은 항상 공짜"라고 일반화할 수 없다. `pg_stat_statements.max` 가 훨씬 크고(예: 수십만) 한 번에 정리할 항목 수(5%)도 그만큼 커지는 극단적인 상황에서는 락을 오래 쥐는 시간이 늘어나 다른 세션의 대기시간에 영향을 줄 수 있다 - 이 실험은 그 극단적인 크기까지는 다루지 않았다.
- 단일 세션에서 순차 실행했다 - **동시에 여러 세션이 몰릴 때** GC 가 잡는 LWLock 경합이 지연시간에 미치는 영향은 이 실험으로 확인할 수 없다. 운영 부하를 평가하려면 동시 세션의 락 대기도 측정해야 한다.
- 컬럼 개수를 늘리는 방식이라 실험 후반부 문장일수록 파싱/플래닝 자체의 비용도 함께 늘어난다(컬럼이 많을수록 파싱할 게 많다) - 그래서 "뒤쪽 50%" 구간의 평균이 전체 평균보다 높게 나온다. 이건 GC 비용이 아니라 문장 자체가 더 커진 데 따른 자연스러운 증가로, 두 설정 모두에 똑같이 적용되므로 GC 유무를 비교할 수는 있지만 쿼리 크기 효과를 분리 계측한 실험은 아니다.

## 재현

```bash
./bench.sh          # N=1600 (기본값)
./bench.sh 800       # N 을 직접 지정 (최대 1664 - 함수 호출 몇 개를 더 쓰는 부가 문장 여유를 두려면 1600 이하 권장)
```
